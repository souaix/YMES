## 清單畫面

WinForms ClientSize 為 1008×591。共用 frmBasisTemplate 提供 IssueState 篩選與 OPType 查詢；資料 Grid 位於左側主區，右側垂直按鈕為 ADD、EDIT、DEL、Copy、Approve、Property，右下角為 Close。網頁保留四種狀態篩選、OP Type 查詢、左側資料表、右側縱向操作鈕，窄螢幕才改為按鈕格狀排版。DEV 欄位使用 MES/KD 黃色系。

Grid 顯示 OPTYPE、DESCRIPTION、CREATOR、CREATEDATE、REVISER、REVISEDATE；ISSUESTATE 與 DATASTAMP 作為操作資料，不顯示為 Grid 欄。日期格式為 yyyy/MM/dd HH:mm:ss。預設狀態是未簽核 0；查詢服務可取得全部狀態後由畫面篩選，搜尋欄位為 OPType。

## 定義視窗

frmOPTypeDef ClientSize 為 497×277，中央顯示 OP Type Data 群組，欄位為 OP Type 黃底文字框及 Description 多行文字框；下方顯示建立/修改資訊；按鈕為確定、關閉、套用。

- Add：OPType 必填、轉大寫；Description 可空。成功後 IssueState=0，由服務設定 Creator/CreateDate。
- Edit：只有 IssueState=0 可開啟；OPType 唯讀，只修改 Description；送入 DataStamp 做更新版本檢查。
- Copy：帶入來源 OPType 與 Description，但 OPType 可改；寫入一筆新的 UNFROZEN 類別。
- WinForms 沒有明確 MaxLength；資料庫欄位限制 OPType 20、Description 255，網頁/API 須明確拒絕超長輸入，不能截斷。
- Apply 與 Confirm 共用 Add/Edit 服務；Apply 留在視窗，Confirm 成功後關閉。Audit 欄由服務管理，瀏覽器不得將 Creator/Reviser/時間當成可信輸入。

## 操作與狀態規則

狀態碼：0 未簽核、1 簽核中、2 已簽核、-1 不使用。

| 操作 | 規則 |
| --- | --- |
| Delete | 狀態 0 或 -1 硬刪；狀態 2 改為 -1，帶 DataStamp；狀態 1 拒絕。舊 Core 硬刪前先刪 TBLOPPROPERTY 中 OPNO=OPTYPE 的屬性資料，再刪 TBLOPTYPE。家用端須在單一交易重現並以實際 live schema 核對共用屬性資料刪除範圍。 |
| Approve | 僅狀態 0；IssueNo=OP TYPE。Issue Job/Detail 不存在時直接改為 2；存在簽核流程時建 Issue Master、狀態改 1、通知第一關群組；流程通過改 2、退回改 0。此狀態轉移由 API/共用 Issue Service 管理，不由前端自行假定。 |
| Property | 呼叫 OP_OPProperty，以 OPType 作為 OPNo 維護屬性。Production 子功能 API 未完成時必須清楚提示，不可把 DEV localStorage 假資料送到正式 API。 |

OPTYPE 與 TBLOPBASIS.OPNO 共用作業站屬性 namespace：舊 AddOPType 會先以不分大小寫方式拒絕任何已存在的 OPNo。不得只依 TBLOPTYPE PK 驗證唯一；新增端點應同時檢查已存在的 OPNo。TBLOPTYPE 本身無 FK；刪除屬性前先確認 YMES 的屬性表及其他 OPType/OPBasis 使用規則。

## Oracle 結構

- 原始 DDL：[Oracle source DDL](../../../database/reference/mestest_op103_optype_source_ddl.sql)。
- PostgreSQL 結構參考：[CREATE SQL](../../../database/reference/mestest_op103_optype_create.sql)。這只是 CREATE-only 對照，家用端須先比對 YMES live schema/migrations，再新增 forward migration；不可直接在 Oracle 執行。
- 欄位：OPTYPE VARCHAR2(20) NOT NULL、DESCRIPTION VARCHAR2(255)、CREATOR VARCHAR2(10)、CREATEDATE DATE、ISSUESTATE NUMBER(1,0) DEFAULT 0 NOT NULL、DATASTAMP NUMBER(11,0) DEFAULT 0 NULL、REVISER VARCHAR2(10)、REVISEDATE DATE。

## Production API handoff

公司端原交接尚無正式 API；家用端已查明沒有重複端點，草稿採下列 query-key 路由。相較原提案以 `/{opType}` 放鍵，改以 query 編碼可保留來源允許的 slash、pipe、star 等文字鍵，前後端同步更新：

| 方法 | 路徑 | 用途 |
| --- | --- | --- |
| GET | /api/operation-types?issueState=&opType= | 不帶狀態時載入全部；明確 -1 只取不使用，0/1/2同理。opType為literal不分大小寫包含查詢，不將%/_當SQL萬用字元。 |
| GET | /api/operation-types/item?opType= | 讀單筆真八欄DTO；不使用清單舊stamp開EDIT/Copy。 |
| POST | /api/operation-types | 新增 {opType, description}；伺服器大寫/驗證 OPType、檢查 TBLOPBASIS.OPNO namespace 衝突，設定 audit/state/DataStamp。 |
| PUT | /api/operation-types/item?opType= | body {opType,description,issueState,dataStamp}，state/stamp皆必須明確出現；僅狀態0可改說明。 |
| DELETE | /api/operation-types/item?opType= | body必須有 {issueState,dataStamp}；2→-1回UNUSED，0/-1硬刪回DELETED及真DTO，1拒絕。 |
| POST | /api/operation-types/approve?opType= | body必須有 {issueState,dataStamp}；只允許0。沒有Job時直接2，有Job但共用服務未接則503不變更，不偽造簽核成功。 |

Production API 要求既有登入，SQL 參數化；Actor、狀態、時間、DataStamp 由 server 控制。若 YMES 缺少 TBLOPTYPE 才建立 migration；不要重建 TBLOPBASIS、TBLOPPROPERTY 或共用 Issue/Job 表。

### 真實結構與交付範圍

- HOME 以 PPK/plink SSH 在 PostgreSQL `BEGIN READ ONLY` 查 pg_catalog，沒有連 Oracle或讀業務資料。`tbloptype`、`tblopproperty` 在所有schema都缺；既有 `YMES.tblopbasis` 為26欄、PK(opno)、只有PK索引、無FK/user trigger，ymes_app CRUD及row-lock所需UPDATE均有。共用 `tblsyselementbasis` 已存在且有SELECT，不另建共用目錄。
- `0049_op103_operation_type.sql` 準備來源八欄 `tbloptype`，OPType20、Description255、Actor10、IssueState NOTNULL DEFAULT0、DataStamp nullable DEFAULT0、原PK。`0050_op_shared_property.sql` 準備原生共用11欄 `tblopproperty`，PK(opno,propertyno)、IssueState NOTNULL DEFAULT0、DataStamp nullable DEFAULT0；其餘nullable及長度依原DDL。兩者目前只是forward migration草稿，尚未套用，不以repo有SQL當成正式表存在。
- Type表授予CRUD；真共用Property表只授予SELECT/DELETE，支援來源已知的Type硬刪清理。沒有新增INSERT/UPDATE provider、FK、額外index、假表或Issue/Job表，沒有複製MES業務資料。來源Property完整維護／元素值及簽核規格未接入，不由這個cleanup表冒充完成。
- API新檔為 `src/YMes.Api/Operations/Op103Controller.cs`、`Op103Models.cs`、`Op103Repository.cs`、`Op103IdentifierGuard.cs`。Controller直接用既有NpgsqlDataSource建repository，明確Authorize，不改Program/DI或root共用MasterDataController。App既有apiBaseUrl prop沿用，前端URL為環境base後的 `/api/operation-types`。

### 主檔狀態、CAS與稽核

- DTO回原八欄及真NULL；不把nullable Description/Creator/CreateDate/DataStamp/Reviser/ReviseDate壓成0或假日期。新增uppercase/trim，Copy依已核實來源只以新主鍵及說明新增state0主列，不複製Property。操作成功使用真回傳DTO，沒有假Copy endpoint。
- PUT/Approve/Delete的IssueState及nullable DataStamp皆JsonRequired；省略400，explicitNULL stamp只匹配DBNULL，0不是NULL的別名。來源state非nullable，explicitNULL state拒400；先鎖原列再驗狀態/stamp，UPDATE/DELETE以canonical key與 `IS NOT DISTINCT FROM` 再CAS，衝突409。
- 修改/核准只允許state0，核准無Job直接2；若pg_catalog發現現有四個Issue/Job來源表，未接服務即503且不寫入。state2 Delete只改-1並保留Property，state1拒絕，0/-1硬刪才進Property清理。需遞增時檢numeric(11,0)上限，max拒409；實體刪除不需遞增，最大stamp仍可精確刪除。
- 所有write明確ReadCommitted；actor取登入principal且最多10字，Create/Revise時間採 `now() AT TIME ZONE 'UTC'`，reader對非NULL指定UTC、JSON帶Z、前端顯示使用者當地時間。沒有變更DB/role timezone或回填歷史列。Controller記動作/主鍵/actor/實際版本，Npgsql錯誤乾淨503、唯一鍵409，不暴露SQL或連線秘密。

### OPNo／OPType namespace及既有作業站writer

- 來源明確OPNo與OPType共用Property namespace，兩方Create先取得相同PostgreSQL trim/lower identifier advisory lock，再查兩表所有狀態編號及重複，避免同時各自查不到對方。TypeCreate不掃刪任何既有OP。OP新建仍保留已知OPNo不可逗號/LOTCREATE規則。
- `PostgresOperationRepository.Create` 改為同一ReadCommitted交易，namespace查重→真Type唯一存在性 `FOR SHARE`→INSERT→真DTO→commit，避免INSERT先提交、其後Get失敗才回錯的ghost。沒有approved-only限制：來源尚未證實OPType selector必須state2，所以只核對真實唯一存在。
- OP Update在同交易先取得實際OP row鎖，重查原state及既有long版本，再比不可改鍵；讀raw optype判斷是否真的變更，未變時保留server原始大小寫／空白／空字串／失效／缺主檔值，rawDBNull也不透過DTO COALESCE改成空字串。真正改Type才持真Type SHARE到commit，使用canonical主檔值。此整合不全面改寫既有OP的long command/token／COALESCE stamp契約。
- 來源/live `tblopbasis.optype` 目前NOTNULL；新建仍按既有必填契約拒絕空Type，沒有為了測試製造NULL列或改nullable。保留legacy raw的分支不等於開放新增無效Type；其他原型欄位及Property provider也未因此完成。
- `OperationDto.OperationType` 與 `OperationWriteRequest.OperationType` 的契約標記為真正 `string?`；request保留20字限制並由server新建／真正換Type驗證，沒有model層implicit nonnullable必填先擋住explicitNULL。Update以獨立raw欄讀值決定未變更分支，rawNULL回寫仍為DBNull，不用空字串或DTO預設取代；既有OP的long狀態／版本命令未在本批改型。live NOTNULL不為回歸而更動，不能把程式的NULL保存分支說成已讀到正式NULL業務列。
- Type硬刪以Type namespace→Type UPDATE鎖，接著普通MVCC SELECT查OPbasis.optype實際引用與同名OPNo。存在引用或Property歸屬不明則409保留；**擋分類引用是YMES明確保守完整性延伸，不冒稱舊Core有相同guard**。確認無引用後，只刪本TypeNo等值的共用Property，再以CAS刪Type，同交易失敗全部回滾。無法讀取/清理Property即503，不當成空設定。
- OP Create/改Type的Type SHARE與Type刪除UPDATE協作：前者先提交，後者重新查到引用就409；Type先刪則等待中的Type lookup失敗。Type刪除不反向鎖OP row，避免與OP Update的OP row→Type SHARE形成死鎖。未來正式Property writer也必須先依同namespace/parent lock協作，不能單靠cleanup SQL宣稱未知外部writer已被保護。
