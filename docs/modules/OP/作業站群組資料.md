## 主檔新增、修改、複製與刪除

### 主檔定義視窗

WinForms ClientSize 566×431，標題 OP Group Basis Define，資料框包含：

- OPGroupNo：必填，Oracle VARCHAR2(20)；離開欄位轉大寫。修改時唯讀；Copy/新增可輸入新編號。
- OPGroupName：必填，VARCHAR2(50)。
- PSNo：必填，VARCHAR2(50)；由既有生產區段選擇視窗帶入。修改時仍可更改。
- OPGroupOrder：整數 NumericUpDown，預設 0、範圍 0–999999。
- Description：多行文字，VARCHAR2(255)。
- 底部顯示建立/修改人及日期；按鈕為確定、關閉、套用。

Confirm 與 Apply 均檢查群組編號、名稱、生產區段必填。Add/Copy 呼叫 AddOPGroupBasis；Edit 呼叫 EditOPGroupBasis 並帶 DataStamp。複製只建立新的群組主檔資料，不會複製原群組的明細成員。API 必須核對欄位長度及 PK，並由登入使用者建立 audit 欄位。

### 刪除主檔

支援選取多筆，操作前顯示確認。WinForms clsOpBasis.DelOPGroupBasis 先將該群組的 TBLOPGROUPDETAIL 刪除，再刪除 TBLOPGROUPBASIS；兩個 SQL 陳述式被收集後一次交給 ExecuteSQLNoneQuery_UPD。新 API 應在同一資料庫交易中完成明細與主檔刪除，以避免留下半套資料。這是實體刪除，沒有 IssueState 軟刪除流程。

## 群組作業站明細

WinForms ClientSize 484×381，標題 OP Group Detail Define：

- OPGroupNo：由目前選取的主檔帶入，唯讀。
- OPNo：由選擇視窗帶入；修改時唯讀。
- 作業站選擇服務只載入 IssueState=2 已核准 OP，且依群組 PSNo 限定；群組 PSNo='*' 時可載入全部已核准 OP。
- OPRoleFlag 必須選一種：General=0、Entry OP=1、Exit OP=2。
- WeightRate 必填、數值範圍 0–100；來源欄位 NUMBER(5,2)。
- Add 呼叫 AddOPGroupDetail；Edit 只可修改角色與權重，呼叫 EditOPGroupDetail 並帶 DataStamp。主鍵 (OPGroupNo, OPNo) 不可重複。
- Delete 支援多筆選取和確認，呼叫 DelOPGroupDetail 實體刪除。
- Audit 欄位由服務寫入；瀏覽器不得自行決定 Production 的 Creator/Reviser/日期。

## Check 按鈕規則

WinForms 在清單端以目前群組載入的所有明細檢核，不呼叫資料庫服務：

1. 同一群組的 Entry OP (OPRoleFlag=1) 最多一筆。
2. 同一群組的 Exit OP (OPRoleFlag=2) 最多一筆。
3. WeightRate 合計必須等於 100。
4. 舊 Form 在沒有 active 主檔或沒有 active 明細列時不執行檢核；網頁保留此選取條件。它沒有要求 Entry/Exit 必須各有一筆。

檢核只回報結果，不會阻止明細儲存，也不會改變資料。

## 家用端實作草稿與維護規則（2026-11-19）

### 真實 schema 稽核與最小 migration

家用端經已授權 PPK SSH，以 `BEGIN READ ONLY` 查 PostgreSQL catalog／grants，未讀業務列、未執行 DDL/DML：

- `tblopgroupbasis` 11 欄、`tblopgroupdetail` 9 欄的欄序、型別、nullable 與 PK 均符合 Oracle 來源；各只有一個 PK index，無 FK／額外 index／user trigger。
- live 只缺五個來源 DEFAULT 0：Basis 的 OPGroupOrder／DataStamp，Detail 的 OPRoleFlag／WeightRate／DataStamp。`ymes_app` 對 Basis 沒有 SELECT／INSERT／UPDATE／DELETE，對 Detail 只有 SELECT；既有 OP／PS 有必要讀取與共享鎖權限。
- `database/migrations/0053_op105_source_defaults_and_permissions.sql` 只有五個 `ALTER COLUMN SET DEFAULT 0` 與兩個 owner 表 CRUD grants，不重建、不回填真 NULL、不建立 FK／新 index，也不重複建立 OP／PS／使用者／簽核表。主流程獨立核對20欄後，備份 `/opt/ymes/backups/ymes_before_0053_op105_20261119.dump`（625213 bytes、600，目錄700）並通過pg_restore清單，再套用成功；獨立after readback20欄、五個default、PK／index／trigger及CRUD差異0。證據在 `.tools/op105-root-before-audit-20261119.json`／`op105-root-after-audit-20261119.json`；這不代表API／GUI驗收完成。

### 來源規則與明載 YMES 延伸

- 原生主檔 Copy 只建立新群組，不複製成員。新主檔 ERPNo 為 NULL，主檔修改不動隱藏 ERPNo。所有建立／修改時間使用 server UTC，來源舊 NULL 日期維持 NULL，JSON 明確標 UTC `Z`；Creator／Reviser 來自登入者，不採用 body audit。
- 群組邏輯鍵以 PostgreSQL `lower(btrim(...))` 判定；寫入先取得 `YMES:OP105:Group:` 識別碼鎖，再鎖群組父列 UPDATE。多筆主檔別名、明細 owner raw key 與唯一父列不一致、同群組成員 OPNo 或被查找主檔有別名歧義時拒絕 409，不任選第一筆、不搬移或清洗舊列。新編號若已有無主檔明細也拒絕接管。GroupNo 與 OPNo 沒有原生共享 Property namespace，不套用 OP103 的跨主檔碰名限制。
- 新／變更 PSNo 重用真正 PS master，檢查唯一性、state2，持有 SHARE 鎖到 commit。`LoadPSDefine` 的精確狀態條件尚待公司端來源補證；state2 是明載的 YMES 保守規則，不宣稱原 Core 已證實。未變的既有 raw／失效／缺目錄／NULL PS 可保留，不要求先整理字典；`*` 沿來源全區段語意。
- 原生允許編輯主檔 PSNo，但未交代已有成員的完整性處理。YMES 延伸：改成特定 PS 前，依 PostgreSQL 固定順序鎖住所有既有成員的真 OP，確認其實際 PS 都相符；無法確認或有不符則 409，全交易不改。改成 `*` 沒有區段限制。API 不自動搬移 OP 或刪成員。
- 新增成員鎖住真正 OP 到 commit，重驗 state2 及群組 PS 範圍；OP 的既有 `tblopgroupdetail` 引用檢查因此能在實刪前看見新關聯。既有成員的角色／權重編輯不重選 OP、不重驗其已失效狀態，保留原始 PK；刪除不要求舊 OP 仍有 master。來源既有 OP 停用 2→-1 不等於實刪，仍可保留群組引用；後續 0/-1 物理刪除受既有引用檢查保護。
- 寫入鎖順序為 group namespace → group UPDATE → 必要 PS／OP SHARE → member UPDATE。群組 cascade delete 只鎖父列、精準刪除 own 明細與主檔，不反向鎖 OP。舊系統沒有 FK，只有採相同父鎖／識別碼協定的 API writer 受協定保護；外部直接 SQL 不在此範圍。
- 每次 member 新增／修改／刪除在同交易將父 Group DataStamp 遞增一次並更新父 audit，回傳新 Group DTO。這是 YMES 延伸，使過期的主檔刪除 CAS 能發現後來增改的成員；UI 不可只更新 member stamp 而忽略父版本。
- nullable stamp 用 `IS NOT DISTINCT FROM` CAS，NULL ≠ 0；匹配 NULL 更新後成為 1。省略 stamp 400、過期 409、非整數／超出 `numeric(11,0)` 400。需要遞增的父／成員 stamp 達 99999999999 時 409，不重置版本；匹配最大版本的主檔仍可 cascade delete，成員刪除只需父版本可遞增。負數來源整數保持可比對，不回填或轉成 0。
- API 只限制角色 0/1/2、單筆權重 0–100 且最多兩位小數，不把 Entry／Exit 數量或權重合計當作儲存條件。Check 以整數百分之一相加，避免二進位小數造成 0.07 等合法值被拒。
