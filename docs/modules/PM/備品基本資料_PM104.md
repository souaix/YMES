## 查詢與畫面欄位

- 預設 IssueState 為 Unfrozen `0`，搜尋欄位只有 `SubstitutionNo`。狀態頁籤為 Unfrozen `0`、Pending `1`、Active `2`、Unused `-1`。
- 主 Grid 顯示 `SubstitutionNo`、`SubstitutionName`、`SubstitutionType`、`SafeQty`、`UnitNo`、`Description`、`Creator`／`CreateDate`、`UnitType`、`Reviser`／`ReviseDate`；`IssueState` 與 `DataStamp` 隱藏。SafeQty 顯示格式為 `0.####`。
- WinForms 將主檔依 `SubstitutionNo` 排序。DEV 沿用此排序；Core Load SQL 本身沒有 `ORDER BY`、分頁或結果筆數上限。
- 編輯表單必填：`SubstitutionNo`、`SubstitutionName`、`SubstitutionType`、`UnitType`、`UnitNo`。代碼在 Leave 時轉大寫；必填檢查使用 Trim 判空。沒有找到可確認的欄位長度限制。
- `SubstitutionType` 由 `LoadSubstitutionType` picker 載入；`UnitType` picker 僅載入 `IssueState=2` 的單位類別；選好 UnitType 後，UnitNo picker 依 UnitType 篩選。
- SafeQty 可空，儲存時空值改為 `0`；非數字或小於 `0` 會拒絕。Core 接收 double，Grid 顯示最多四位小數。

## 主檔操作與狀態

- 新增建立 IssueState `0`，Creator／CreateDate 使用目前登入者及時間。
- 修改只允許 IssueState `0`；`SubstitutionNo` 唯讀。保留 Creator／CreateDate，更新 Reviser／ReviseDate，依 `SubstitutionNo + DataStamp` 版本更新。
- 複製可從目前主檔開啟，複製原欄位後輸入新 `SubstitutionNo`；成功新增後，再以另一個 Service 呼叫複製供應商映射。新資料為 IssueState `0`。
- 刪除允許 Unfrozen `0`／Unused `-1` 硬刪；Active `2` 改成 Unused `-1` 並更新 DataStamp；Pending `1` 拒絕。Core 硬刪 Basis 時也刪除 `tblPMSubstitutionVendorMap` 與 `tblPMSubstitutionGroupDetail` 對應列，這會直接影響備品群組內容。
- 核准只接受 Unfrozen。Service 以 Issue Management 的 `SUBSTITUTION BASIS` 判斷：未設定簽核工作時直接改 Active `2`；有簽核明細時建立簽核工作並改 Pending `1`，核准後為 `2`、退回後回到 `0`。DEV 提供本機切換控制以示範兩種分支。
- 主檔批次刪除／核准由 WinForms 逐筆呼叫，遇到第一筆失敗就停止，前面成功的列不會自動回復。DEV 模擬順序處理與部分成功提示。

## 供應商映射子表

- 選取主檔後，WinForms 依 SubstitutionNo 載入供應商映射。欄位為 `SubstitutionNo`、`VendorNo`、`Description`、Creator／CreateDate、Reviser／ReviseDate；DataStamp 隱藏。
- 映射識別為 `(SubstitutionNo, VendorNo)`。新增用 `LoadSubstitutionVendor` 載入供應商 picker；修改時兩個代碼不可修改，只能改 Description。修改使用 DataStamp；刪除 Service 只接收兩個代碼，沒有傳 DataStamp。
- 子表新增、修改、刪除事件只檢查是否選到父列，沒有依父資料 IssueState 限制；DEV 保留此舊畫面行為。
- 子表批次刪除逐筆呼叫 Service，遇失敗可能部分成功。Core 寫入採 SQL 字串串接。
- `CopySubstitutionVendorMap` 呼叫 Core 複製映射；Service 內層有空白 `catch`，Core 映射複製失敗可被吞掉，外層仍回傳成功。加上主檔 Add 與映射 Copy 分成兩次呼叫，舊畫面可能留下沒有完整供應商映射的複製資料。

## 已知來源風險與家用端 handoff

1. Oracle 同版 DDL／metadata 尚未取得。家用端先查 PostgreSQL live schema／migration，以及 `tblPMSubstitutionBasis`、`tblPMSubstitutionVendorMap`、`tblPMSubstitutionGroupDetail` 的實際欄位、PK／unique、FK、索引及現存引用；缺表時只依可信 DDL 證據新增 CREATE-only migration，不由選單 seed 推測欄位。
2. Core 中「SubstitutionNo 不可與 `tblPMSubstitutionType.SubstitutionType` 共用代碼」檢查已註解；PM103 也有對應的反向檢查被註解。正式 schema／API 應確認兩者確實共用 Property namespace，並以大小寫正規化的資料庫約束或序列化交易保證跨表唯一。
3. Create／Update 接受最小必要欄位與 audit 資料；伺服器重新驗證必填、SafeQty 非負、有效 Type／UnitType／UnitNo 組合。查詢需授權、參數化、bounded paging、穩定排序與筆數上限。
4. Update／Approve／Active→Unused 使用 `SubstitutionNo + DataStamp` 做 optimistic concurrency，檢查受影響列數；不可只比對版本後仍回報成功。
5. Copy 應由單一授權 API 在一個資料庫交易內新增 Basis 與所有 VendorMap，回報實際映射筆數及失敗原因；不可重現 Service 吞錯的成功回覆。
6. Hard delete 需明確決定 GroupDetail 與 VendorMap 的清理規則，先核對其他業務參照；將群組內容移除是破壞性連帶效果，應原子執行並留下 audit。Active 只轉 Unused，Pending 拒絕。
7. 核准接既有 Issue Management 工作流；沒有簽核定義時才直接 Active。批次操作應全有全無或回傳逐列結果，避免舊 WinForms 的部分成功但整體狀態不清楚。
