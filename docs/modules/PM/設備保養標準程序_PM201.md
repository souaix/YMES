## 主畫面與設定欄位

- 主畫面查詢欄位只有 `PMEQPSOPNo`，WinForms 以該欄排序。沒有 IssueState 頁籤或核准按鈕；載入後 `IssueVisable=False`。
- Grid 顯示 `PMEQPSOPNo`、`PMYearNo`、`EquipmentType`、`FrequencyNo`、`PMSOPNo`、`FrequencyName`、`PMSOPName`、`AutoCreateWO`、`CreateAndReleaseWO`、`BeforehandDay`、`LockEquipment`、`EquipmentState`、`StateName`、`AutoEmail`、Creator/CreateDate、Reviser/ReviseDate、Description。
- `PMYearNo`、`EquipmentType`、`FrequencyNo`、`PMSOPNo` 必填。新增時 Core 以 `EQPSOP` + 當年兩位數 + 五位流水號產生 `PMEQPSOPNo`，並依 FrequencyNo、PMSOPNo 讀回名稱；Copy 預填來源欄位，再新增一個新編號，不複製既有計畫。
- `AutoCreateWO` 控制 `BeforehandDay` 與 `CreateAndReleaseWO`；關閉時 WinForms 清空提前天數並關閉立即下線選項。提前天數可空，填值須為大於 0 的整數。`LockEquipment=Yes` 時必須選 EquipmentState；切回 No 時狀態欄位清空。`AutoEmail` 是 Yes／No。
- `HurryTime`、`OverDueTime`、`ToleranceQty` 控制項在原 Form 中隱藏。HurryTime／OverDueTime 仍以預設或載入值送 Service；ToleranceQty 未由 Form 序列化，新增沿用 Service 預設 0、修改不更新此欄。DEV 不顯示這三欄並保留相同限制。
- Edit 會傳 DataStamp，Core 依主鍵及版本條件更新 Reviser/ReviseDate。空 Description 在舊 Core 修改時等同未提供，不能清空。新增、Copy 不檢查自然鍵組合唯一性；主鍵由 Core 產生。

## 操作流程與相關計畫

- Add、Edit、Copy 使用同一個設定視窗。Edit 會停用年度、設備類型、頻率與 SOP 的 lookup 按鈕；Copy 可由目前資料預填後新增。
- Delete 可多選，Form 逐筆呼叫 Service，遇錯停止而保留之前成功項目。Core 先把該 `PMEQPSOPNo` 的 `tblPMEQPMaintenancePlan` 資料複製到 `tblPMEQPMaintenancePlanLog`（ExecuteState 設 5、填 LogCreator/LogCreateDate），再刪除計畫與 Basis，並檢查 SQL 影響筆數。
- `保養計劃資料`、`計劃設定` 由 `ObjectFileHandler` 開啟獨立的 `PM_EQPMaintenancePlan`、`PM_EQPMaintenancePlanSet` 視窗。這兩個視窗不是本 Form 的子表編輯，本次 DEV 只提供唯讀計畫樣例與設定摘要；未宣稱完成其獨立功能。
- `批次複製` 開啟 `PM_EQPTypeSOPBatchCopy`。該視窗依來源年度／設備類型載入 Basis，支援全選／取消、目標 PMYearNo 與 PlanLaunchDate；執行時要求至少選一列且啟動日年份等於新年度。Core 複製每列設定，依來源既有計畫的 distinct EquipmentNo 與 Frequency Basis 規則，在新年度 EndDate 前產生計畫。每列分開執行 SQL；部分錯誤以 ErrMsg 回報，整體仍可能回 success。
- DEV 批次複製可選來源列、目標年與啟動日，複製主檔設定並以 localStorage 的頻率假資料近似產生計畫日期；日期算法受限於假年度（2025–2028）及簡化的假參照值。正式計畫維護、實際資料筆數、日期規則與批次錯誤復原待家用端重建。

## Oracle DDL／metadata 狀態

- Repo 的 `database/` 與 `docs/` 沒找到 `tblPMEQPTypeSOPBasis` 的可核實 CREATE／metadata。公司桌機受保護 Oracle profile 在目前 `User` 與筆電帳號 `11019` 的已知 attachment 路徑均不存在；因此本項沒有使用 PowerShell 5.1／ODP.NET 連 Oracle，沒有輸出憑證，也未猜測或新增 PostgreSQL CREATE SQL。
- 待核表：`tblPMEQPTypeSOPBasis`；參照 `tblSYSYearDefinitionBasis`、`tblEQPTypeBasis`、`tblPMFrequencyBasis`、`tblPMSOPBasis`、`tblEQPStateBasis`；排程與歷史 `tblPMEQPMaintenancePlan`、`tblPMEQPMaintenancePlanLog`。欄位型別、nullable/default、PK/FK、索引、唯一性及計畫表精度都要以受保護 Oracle dictionary／DDL 與家用端 live schema 核實。

## 家用端 API／schema handoff

- 先讀 PostgreSQL live schema／migration，再取得可用的 Oracle source metadata；不得把 WinForms 欄位表或 DEV fixture 當成 DDL。家用端決定是否需 CREATE-only migration，並核對是否已存在計畫、歷史、年度及參照表。
- 建議主檔查詢支援 bounded `PMEQPSOPNo`、年度、設備類型、頻率、SOP 條件，並以 `PMEQPSOPNo` 穩定排序／分頁；參照選項使用有權限且 bounded 的查詢。
- 新增交易內確認年度、EquipmentType、FrequencyNo、PMSOPNo、EquipmentState 參照有效，產生唯一 `PMEQPSOPNo`；修改以主鍵 + DataStamp 條件更新並回傳衝突；所有 SQL 參數化並保存 audit。
- Delete 必須交易式複製計畫至歷史（保留舊資料、執行狀態、log 使用者及時間）、再刪計畫與 Basis；用 FK 與 affected rows 保護資料一致性，不可把舊 Core 的未參數化 SQL 原樣移植。
- 批次複製需逐筆回報成功／失敗，或採明確全成全敗交易；建立設定與生成新年度計畫應遵守 Frequency Basis 的固定週／月／年、Period、StartDate/EndDate 與「今日開始改從明日」規則。來源設備集合取自來源 `PMEQPSOPNo` 的既有計畫。明確處理目標重複、來源無設備、空年度、跨午夜與重跑 idempotency。
- 舊 `PM_EQPMaintenancePlan` 與 `PM_EQPMaintenancePlanSet` 是獨立工作流程，應分模組/API 設計；不要把本 DEV 的唯讀摘要視為計畫維護 API。
- 公司端僅完成 DEV 假資料與規格；未連 PostgreSQL、未建立 schema／migration、未實作或驗收正式 API、未部署。
