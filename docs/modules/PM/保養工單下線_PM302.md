# PM302 保養工單下線

## 功能與來源

- MES 選單為「保養工單 → 保養工單下線」，FunctionNo `PMWO RELEASE`、FunctionKey `PM302`，Form `frmPMWORelease`，ExecutionFile `PM_WORelease_EQM_THEIL.dll`。
- 已核對 `D:\iMES\CSiMES\STD\MESWin\PM\PM_WORelease\frmPMWoRelease.vb`（含 inline Designer）、`MESws_STD/wsSTD/wsPM/wsPM.cs` 的 `ReleaseWoDetail`，以及 `MESkc/kcPM/clsPMBasis.cs` 的 `ReleaseWoDetail`。
- 畫面以 `LoadPMWoBasis` 載入主檔、`LoadPMWoDetail(WONo)` 載入目前工單明細；SOP 檢視另讀設備類型 SOP 與 PM SOP 細節。

## WinForms 查詢和畫面

- 篩選有多選 PMWONo、Creator 清單，Create Date From／To（Designer 初始未勾選），PM Order／REQ Order（Designer 初始皆未勾選，代表不限制 WOType）。主檔查詢額外固定限制 `IssueState=2`，且需至少一筆 `WOStatus=1` 明細。
- 主檔 Grid 顯示 WONo、WOType、Description、Creator、CreateDate；選取主檔後載入明細。明細列以五個預設全勾的狀態核取方塊過濾：0 待簽核、1 待料、2 已下線、3 已完成、4 已撤線。
- 當 Chamber Manage 未啟用時，畫面會依設備設定排除子設備明細；啟用時允許一起顯示／下線。`Show Detail` 開啟目前明細的 PM SOP 步驟、工具及替代備品資料。
- `Release` 使用明細 Grid 的選取列；作用中的明細狀態 >= 2 時 Form 會先拒絕。`Release All` 從目前已載入工單資料中取出所有 `WOStatus=1` 列，因此不受畫面狀態核取方塊的可見範圍限制。隱藏的 `Remove` 按鈕只刪除本機 DataTable 列，不呼叫 Service／Core。

## 下線流程與資料異動

- Form 以作用中明細的 `PMEQPSOPNo` 載入設備類型 SOP。若該 SOP 未提供 EquipmentState，表單不要求改設備狀態；否則查 `ControlNo=PMWoReleased`、`ControlType=PM Work Order` 的設備狀態控制。未設定控制時可選擇繼續但不改狀態。
- Service `wsPM.ReleaseWoDetail` 逐列重讀 SOP 的 `LockEquipment`，讀目前 EquipmentState 並檢查禁止轉換；`LockEquipment=0` 的列不改設備狀態。Core 下線完成後，Service 再逐列呼叫 EQP `EditEquipmentState`；有啟用 Chamber Manage 時會傳 `UpdateChamberState=true`。
- Core `clsPMBasis.ReleaseWoDetail` 對每筆明細批次更新 `tblPMWODetail`：限定目前 WONo、WOItemNo 和 `WOStatus=1`，寫 `ReleaseDate`、`WOStatus=2`，預期影響 1 列。若 `WOType=0`，再將 `tblPMEQPMaintenancePlanLog` 依 `SerialNo` 設 `WOReleaseDate`、`ExecuteState=3`；所有類型都將 `tblPMEquipmentState` 的 `SincePMQty`、`SincePMTimes` 歸零並更新 `LastPMDate`。這些更新均要求預期影響 1 列。舊程式沒有更新 DataStamp。
- Core 的下線 SQL 與後續 EQP 狀態變更分屬先後呼叫；EQP 狀態更新失敗時，工單／PM 累計可能已先寫入，存在部分完成風險。Service 也以作用中 SOP 決定傳入的 EquipmentState，再依各列 LockEquipment 執行更新；多選不同 SOP 時需重新驗證每列的適用狀態。
- 查詢與下線程式有字串串接 SQL／未分頁讀取；正式 API 需參數化、限定狀態與主鍵，並採有界分頁。不可只信任前端傳來的 WOType、SerialNo 或 EquipmentNo。

## 家用端 API、schema 與 CREATE-only handoff

- 建議 `GET /api/pm/work-orders` 提供 WONo／Creator 多選、CreateDate 區間、WOType、IssueState 與是否含待料明細條件，回傳有界分頁；`GET /api/pm/work-orders/{woNo}/items` 依 WOItemNo 排序，支援 WOStatus 過濾。
- 建議 `POST /api/pm/work-orders/{woNo}/release` 接受明確的 WOItemNo 清單與冪等鍵。伺服器重新確認父單 `IssueState=2`、所有明細屬於該 WONo 且 `WOStatus=1`，由資料庫推導 WOType／SerialNo／EquipmentNo；PM 工單還需確認 PlanLog 對應此工單明細且 `ExecuteState=2`。以條件式更新及 row count 防止重複下線，更新明細、PM PlanLog、設備 PM 累計並寫稽核紀錄。
- 對 EQP 狀態，正式 API 應重新載入 SOP LockEquipment、狀態控制與違規轉換規則。因舊系統在 Core 寫入後才另呼叫 EQP Service，建議改用同一交易可涵蓋的資料操作，或以 outbox／可重試命令確保設備狀態失敗時不留下難以辨識的部分完成。啟用 Chamber Manage 時亦須明確處理子設備。
- 直接資料表：`tblPMWOBasis`（查詢）、`tblPMWODetail`、`tblPMEQPMaintenancePlanLog`（PM 工單）、`tblPMEquipmentState`；參照 `tblPMEQPTypeSOPBasis`、EQP 狀態控制／設備主檔、PM SOP 與 Chamber 設備設定。
- repo 內沒有上述直接表可核實的 Oracle source DDL／CREATE-only SQL；桌機沒有受保護 Oracle profile，筆電 attachment 路徑在本機不存在，因此本次未連 MESTEST。欄位型別、PK/FK、索引、預設值、nullable 與時間精度待家用端依 live schema 及安全取得的 Oracle metadata 核對。未依欄位名稱猜測 CREATE。
- 家用端完成正式 API/schema、遷移及驗收；公司端未連 YMES PostgreSQL、未設定 `ConnectionStrings__YMes`、未部署，也未執行 build／test／browser。
