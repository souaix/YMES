# PM106 工作形式設定

## 復刻範圍與來源

- 功能：PM106 `JOB TYPE`／工作形式設定；Form 是 `frmJobType`，資料表由導覽快照確認為 `tblPMJobTypeBasis`。
- WinForms：`D:\iMES\CSiMES\STD\MESWin\PM\PM_JobType\frmJobType.vb`、`frmJobTypeDef.vb`。
- Service：`D:\iMES\CSiMES\STD\MESws_STD\wsSTD\wsPM\wsPM.cs` 的 `Load/Add/Edit/Del/ApproveJobTypeBasis`。
- Core：`D:\iMES\CSiMES\STD\MESkc\kcPM\clsPMBasis.cs` 的新增、硬刪、查詢；`D:\iMES\CSiMES\STD\MESkc\kcBasis_UPD\clsBasis_UPD.cs` 的帶 DataStamp 修改與 IssueState 更新。
- DEV 頁：`web/src/components/PmJobType.vue`、`PmJobTypeDevPreview.vue`，路由鍵為 `function:PM:JOB TYPE`。

## 畫面與欄位

- 預設狀態為 IssueState 0「未凍結」；頁籤為 0 未凍結、1 簽核中、2 已生效、-1 未使用。Grid 依 PMJobNo 升冪排序。
- 搜尋欄只有 PMJobNo。舊 Load Service/Core 另外接受 PMJobName，但 Form 沒有使用該條件。
- Grid 顯示 PMJobNo、PMJobName、Memo、Description、Creator/CreateDate、Reviser/ReviseDate；IssueState 與 DataStamp 隱藏於資料列。
- 編輯欄位：PMJobNo、PMJobName、Memo、Description。PMJobNo 和 PMJobName 以空字串檢查必填，舊表單不 Trim；PMJobNo 離開欄位時轉大寫。未查到長度上限驗證。
- 新增與複製建立 IssueState 0。複製可從任一狀態列開啟，只複製四個業務欄位，不複製審核／稽核欄位。
- 舊 Edit Service 對空 PMJobName 會拒絕；空 Memo／Description 會被當作未傳欄位，因此不能用清空文字的方式清除既有值。DEV 預覽保留此行為。

## 狀態與操作

- 修改只允許 IssueState 0；PMJobNo 在修改模式唯讀。Apply 呼叫新增／修改後保持定義視窗開啟；Confirm 呼叫相同服務並關閉。
- 刪除逐筆處理所選列：IssueState 0 或 -1 由 Core 硬刪 Basis；IssueState 2 以 PMJobNo + DataStamp 將狀態改為 -1；IssueState 1 或其他狀態拒絕。硬刪 Core 只刪 `tblPMJobTypeBasis`，未見引用檢查；DB constraint／外部引用需家用端核對。
- 核准只接受 IssueState 0，逐筆送 `ApproveJobTypeBasis`。Service 查 Issue Management 的 IssueNo `JOB TYPE`：沒有映射或沒有明細時直接設為 2；有完整流程時建立核准 SQL（2）及退回 SQL（0）、開啟流程並將目前列設為 1，之後通知第一關群組。
- Form 的刪除與核准是多列逐筆呼叫；遇錯即停止，先前成功列不回滾。
- `clsBasis_UPD` 的一般修改及直接 IssueState 更新以 PMJobNo + DataStamp 更新，增加 DataStamp 並更新 Reviser/ReviseDate。Issue Management 後續的 ApproveSQL/RejectSQL 是直接改 IssueState，這段 SQL 本身未更新 DataStamp 或稽核欄位。

## 家用端 API／schema handoff

- 本模組僅可由選單快照確認 `tblPMJobTypeBasis` 表名；repo 內沒有可核實的業務表 DDL／metadata。公司桌機沒有受保護 Oracle MESTEST profile，本次未查 Oracle，也不提供猜測的 PostgreSQL CREATE SQL。
- 家用端先檢查 PostgreSQL live schema／migration，再依實際 WinForms DTO 映射 PMJobNo、PMJobName、Memo、Description、IssueState、Creator/CreateDate、Reviser/ReviseDate、DataStamp。確認欄位型別、nullable、主鍵與預設值後才補 CREATE-only migration。
- 建議 API：授權且 bounded 的依 IssueState 篩選、PMJobNo contains 搜尋與穩定排序查詢；新增；以 PMJobNo + DataStamp 原子修改；依狀態刪除／轉未使用；核准命令接既有 Issue workflow。避免舊 Service/Core 的 SQL 字串串接。
- 實作硬刪前先查 live schema 與程式呼叫端對 PMJobNo 的引用，確認 FK／使用中保護策略；狀態、資料修改、稽核與 DataStamp 應在交易內一致更新。需保留舊流程無 Issue map 時直接 Active 的語意，並讓 workflow 完成／退回時更新版本與稽核欄位。
