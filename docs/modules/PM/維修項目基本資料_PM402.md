## 畫面、欄位與查詢

- Form 載入所有狀態，預設 IssueState 0「未凍結」；另有 1「簽核中」、2「已生效」、-1「未使用」頁籤。Grid 依 RepairNo 排序。
- 查詢欄位只有 RepairNo；Designer 的 Find 按鈕隱藏，使用共用 Form 的搜尋／Query。DEV 即時篩選 RepairNo。
- Grid 顯示 RepairNo、RepairName、Description、Creator／CreateDate、Reviser／ReviseDate；IssueState 與 DataStamp 隱藏。
- 編輯窗欄位 RepairNo、RepairName、Description；RepairNo、RepairName 必填，編輯時 RepairNo 唯讀。RepairNo 離開欄位時轉大寫；RepairName 不轉大寫。Designer 沒有明確 MaxLength。
- 新增／Copy 產生狀態 0，填 Creator／CreateDate；Copy 從選取列預填三個欄位，但不複製關聯或簽核資料。

## 狀態與操作規則

- Edit 僅允許 IssueState=0。`clsBasis_UPD.EditRepairBasis` 以 RepairNo + DataStamp 更新 RepairName／Description／Reviser／ReviseDate 並遞增 DataStamp；空 Description 會被舊 Core 當成「未提供」，無法清除既有描述。
- 多選 Delete 逐列處理：0／-1 硬刪 `tblPMRepairBasis`；2 使用 DataStamp 版本更新轉為 -1 並寫修改者／時間；1 或其他狀態拒絕。遇到錯誤即停止，之前成功列不回滾。
- 硬刪 Service 會解析 DataStamp，但呼叫 `clsPMBasis.DelRepairBasis` 時未傳該版本條件，因此沒有併發保護。程式碼未見應用層引用檢查；家用端應先查設備修復登錄及資料庫約束，再決定刪除政策。
- Approve 只接受狀態 0；IssueNo 為 `REPAIR BASIS`。無 Issue Job Map 或 Job 無明細時直接轉 2；存在流程明細則建立簽核、更新為 1，核准 SQL 設 2、退回 SQL 設 0。啟動／略過流程時 `clsBasis_UPD` 依 DataStamp 更新狀態、修改者及時間；簽核結束 SQL 不遞增 DataStamp／稽核欄。
- 新增、編輯、刪除、核准都有 Service EventLog／ErrorLog。舊 Core 以字串組 SQL，正式 API 必須用參數化語句、認證使用者、伺服器時間和受控狀態轉移。

## 家用端 API／schema／Create SQL handoff

- 選單快照只證實功能關聯表名 `tblPMRepairBasis`；repo 沒有可信的該業務表 Oracle source DDL／metadata，桌機受保護 Oracle profile／attachment 不存在。本次不猜型別、長度、PK／FK／索引或產生 CREATE SQL。
- 由 Form／Service／Core 確認欄位名稱為 `RepairNo`、`RepairName`、`Description`、`IssueState`、`Creator`、`CreateDate`、`Reviser`、`ReviseDate`、`DataStamp`。精確型別、長度、nullable/default、唯一鍵與索引須先由 PostgreSQL live schema 和同版 Oracle metadata 核實。
- 建議列表 API 可依 RepairNo 搜尋、穩定排序並限制分頁；Create 接受兩個必填代碼／名稱及可空 Description；Update 僅允許狀態 0 並要求 expected DataStamp；Approve、停用／硬刪採逐筆版本檢查，伺服器端控制所有狀態和稽核欄位。
- Repair No 被設備修復登錄作為多選項目。Active=2 刪除轉 -1；未凍結／未使用硬刪前需確認 PM405 設備修復登錄及其子明細的引用與 FK，不可只依舊 Core 成功即刪除。多選操作需回傳逐筆結果或採原子契約，避免舊式部分成功。
- RepairBasis DEV 假資料供未來 PM405 候選維修項目流程重用；PM405 正式候選集合須維持只含 IssueState=2。
