# PM403 設備與故障原因對應

## 復刻範圍與來源

- MES 選單列：`FunctionName=EQPTYPE BREAKDOWN MAP`、`FunctionKey=PM403`、畫面 `frmEQPTypeBreakDownMap`、模組 `PM_EQPTypeBreakDownMap.dll`、分類「設備維修」。`PM_ACCPLAN` 也使用 FunctionKey `PM403`；Vue 依功能名稱路由為 `function:PM:EQPTYPE BREAKDOWN MAP`，不與保養計劃頁混用。
- WinForms：`D:\iMES\CSiMES\STD\MESWin\PM\PM_EQPTypeBreakDownMap\frmEQPTypeBreakDownMap.vb`（含 inline Designer）、`frmEQPTypeBreakDownMapDef.vb`。
- Service：`D:\iMES\CSiMES\STD\MESws_STD\wsSTD\wsPM\wsPM.cs` 的 `Load/Add/Edit/DelEQPTypeBreakDownMap`，以及 `LoadBreakDownBasis`。
- Core：`D:\iMES\CSiMES\STD\MESkc\kcPM\clsPMBasis.cs` 的新增、硬刪、讀取；`D:\iMES\CSiMES\STD\MESkc\kcBasis_UPD\clsBasis_UPD.cs` 的版本化新增／修改。
- 下游 PM404：`D:\iMES\CSiMES\STD\MESWin\PM\PM_EQPBreakDownRegister\frmEQPBreakDownRegisterDef.vb` 依設備類型呼叫 `LoadEQPTypeBreakDownMap`，把對應故障原因列為故障登錄可勾選項目。
- Vue DEV：`web/src/components/PmEqpTypeBreakDownMap.vue`、`PmEqpTypeBreakDownMapDevPreview.vue`；localStorage key `ymes.dev.pm.eqp-type-breakdown-map.v1`；故障原因 lookup 讀取 PM401 的 `ymes.dev.pm.breakdown-basis.v1`。

## 畫面、欄位與查詢

- 主畫面上方先載入 `wsEQP.LoadEquipmentType`，依 EquipmentType 排序；可查 EquipmentType。設備類型 Grid 顯示 EquipmentType、Capacity、PictureName、Description、Creator、CreateDate。
- 啟用設備類型列後，下方呼叫 `LoadEQPTypeBreakDownMap`，只帶 EquipmentType。Core 查 `tblPMEQPTypeBreakDownMap a LEFT JOIN tblPMBreakDownBasis b ON a.BreakDownNo=b.BreakDownNo`，回傳 `a.*` 與 BreakDownCause；左連接不會因故障原因主檔已不存在而隱藏既有對應。
- 對應 Grid 顯示 EquipmentType、BreakDownNo、BreakDownCause、Description、Creator、CreateDate、Reviser、ReviseDate；DataStamp 隱藏。畫面隱藏共用 IssueState 分頁（`IssueVisable=False`），本功能沒有簽核狀態／核准流程。
- 對應明細支援 Add、Edit、Delete（多選）、Copy。新增／複製以目前設備類型為唯讀值；編輯時 EquipmentType、BreakDownNo 都唯讀，只能修改 Description。Copy 從目前列帶入設備類型、故障原因代碼和描述，需換成尚未對應的故障原因。
- Def 的 EquipmentType、BreakDownNo 為必填；BreakDownNo 離開欄位時轉大寫。新增／複製的 `LoadBreakDownBasis` 未傳 IssueState，Service 預設 `IssueState=2`，故選擇器只提供已生效故障原因。DEV 由 PM401 假資料同樣只列 IssueState=2；找不到主檔的歷史對應仍顯示並標示。
- 新增／編輯窗有 Apply 與 Confirm；Apply 儲存後保留視窗，Confirm 儲存後關閉。桌機 DEV 假設備類型、故障原因與映射是模擬資料，不代表 MES 實際設備清單或 Oracle 業務資料。

## Service／Core 規則與差異

- `tblPMEQPTypeBreakDownMap` 的欄位由程式可確認：EquipmentType、BreakDownNo、Description、Creator、CreateDate、Reviser、ReviseDate、DataStamp。新增由 `clsBasis_UPD.AddEQPTypeBreakDownMap` 寫入鍵、描述及建立者／時間。
- Edit 要求並解析 DataStamp；`clsBasis_UPD.EditEQPTypeBreakDownMap` 以 EquipmentType + BreakDownNo + DataStamp 更新，寫 Reviser／ReviseDate 並遞增 DataStamp。WinForms 儲存成功後本地版本加一。舊 helper 以 `defString` 表示欄位未提供，因此空白 Description 可能被當成未提供，DEV 沿用「空白不清除既有描述」並留給正式 API 明確定義。
- Delete 是立即硬刪，UI 逐筆呼叫 Service，沒有 DataStamp 條件；Service 允許只傳 EquipmentType 或只傳 BreakDownNo，Core 會按收到的條件刪一筆或多筆。正常 UI 每列同時傳組合鍵，但正式 API 應要求完整組合鍵並採版本檢查。
- 新增／修改／刪除都寫 Service EventLog，錯誤寫 ErrorLog。Core SQL 以字串組合，正式 API 應改用參數化 SQL。
- 程式以 EquipmentType + BreakDownNo 作為修改／刪除篩選條件；這是程式行為可推得的候選複合鍵，尚未由資料庫 PK／唯一索引 metadata 證實。

## 家用端 API／schema／Create SQL handoff

- 桌機受保護 Oracle attachment 在本機不存在；repo 內沒有 `tblPMEQPTypeBreakDownMap` DDL／metadata。公司端未連 PostgreSQL、未查 Oracle，也未猜欄位型別或產生 CREATE SQL。家用端先核對 live PostgreSQL、再取得可信同版 MESTEST metadata 後，才提交經核實的 CREATE-only DDL。
- 先核實映射表欄位型別、長度、NULL/default、主鍵／唯一鍵、FK、索引及 DataStamp 預設值。設備類型的實際來源表名／約束亦待查；不要依 Vue 假資料推定。
- 建議查詢 API 以 EquipmentType 為必填條件並回傳故障原因名稱；新增接受 EquipmentType、BreakDownNo、可空 Description，建立者與時間由伺服器填入；修改以完整複合鍵及 expected DataStamp 限定，只有改變時寫 Reviser／ReviseDate 並遞增版本；刪除也要求完整複合鍵及 expected DataStamp。
- PM404 設備故障登錄會以 EquipmentType 載入映射，讓使用者勾選故障原因。正式硬刪前需查映射是否已被故障登錄／明細使用，並核實 FK 與保留政策；不能複製舊 Service 對單欄條件執行多筆刪除的行為。多選應回傳逐筆結果或用明確原子交易。
- PM401 的候選查詢預設只取 IssueState=2；正式 API 必須保留這項 lookup 規則。故障原因名稱由 `tblPMBreakDownBasis.BreakDownCause` 左連接取得，須核對兩張表間資料庫約束。
