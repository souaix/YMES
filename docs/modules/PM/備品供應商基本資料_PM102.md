## 畫面與資料規則

- 預設在 Unfrozen（`IssueState=0`），主檔搜尋欄位只有 `VendorNo`。狀態頁籤是 Unfrozen `0`、Pending `1`、Active `2`、Unused `-1`。
- 主 Grid 顯示 VendorNo、VendorName、Description、Creator／CreateDate、Reviser／ReviseDate；IssueState、DataStamp 隱藏。舊 UI 將主檔排序為 VendorNo。
- 選取主檔後，以 VendorNo 載入下方聯絡人。聯絡人欄位為 VendorNo、ContactorName、TelNo、FaxNo、Title、EMail、Address、Description、Creator／CreateDate、Reviser／ReviseDate；DataStamp 隱藏。
- `VendorNo` 離開欄位時轉成大寫；供應商代碼與名稱必填。修改時 VendorNo 唯讀。
- 聯絡人複合鍵為 `(VendorNo, ContactorName)`。VendorNo 與 ContactorName 必填；修改時 ContactorName 唯讀。TelNo 使用 WinForms `TWPhone` 驗證，EMail 使用通用 Email 驗證，兩者非必填。
- Contactors 沒有 IssueState；主畫面聯絡人新增／修改／刪除按鈕事件不檢查供應商狀態。DEV 允許在各主檔狀態檢視聯絡人並執行子檔維護，資料只存在本機。

## 操作與狀態

- 新增建立 Unfrozen 供應商；修改只允許 Unfrozen，保留 VendorNo、Creator、CreateDate，更新 Reviser／ReviseDate／DataStamp。
- 複製可從所選供應商開始，畫面會複製主檔內容；操作者需輸入新的 VendorNo。儲存先呼叫 AddSubstitutionVendor，再另呼叫 CopySubstitutionVendorContactor 複製整組聯絡人。
- 核准只接受 Unfrozen。Service 查 Issue Management 中 `SUBSTITUTION VENDOR` 對應簽核設定：找不到可用工作／明細時直接改為 Active；有簽核明細時建立簽核流程、狀態改 Pending，並寄信給第一簽核群組。
- 刪除主檔：IssueState 0／-1 硬刪；2 改為 -1；1 拒絕。舊 Core 硬刪依序刪除 `tblPMSubstitutionVenContactor` 聯絡人、`tblPMSubstitutionVendorMap` 備品對應，再刪 `tblPMSubstitutionVendor` 主檔。
- 聯絡人新增／複製、修改與刪除使用子檔獨立 Service；修改以 VendorNo + ContactorName + DataStamp 更新，刪除用 VendorNo + ContactorName。
- 主檔 Email 按鈕會啟動 `mailto:` 郵件程式。舊 handler 以共用 `ugrRow` 取聯絡人鍵，而非從目前 ActiveRow 取值，可能取到舊選取列；DEV 僅顯示 Email 預覽，不啟動外部程式。
- 聯絡人表單在 ContactorName Leave handler 會清空 Email 欄位，可能清除使用者已輸入或載入的 Email。DEV 不清空欄位，保留值並使用瀏覽器 Email 欄位驗證。

## 已知來源限制與風險

- Vendor／Contactor Core SQL 多處以字串組合條件與欄位。正式 API 必須使用參數化查詢、驗證主檔與子檔關聯、限制查詢數量並提供穩定排序。
- Vendor 硬刪、批次刪除與整家複製是多個 SQL／Service 操作；主檔新增與聯絡人複製更是兩次 Service 呼叫。舊失敗可能留下主檔已新增但聯絡人未完成、或部分批次完成的狀態。家用端需在一個交易內檢查版本、引用與來源，並原子寫入；刪除備品對應前需確認業務上允許解除哪些關聯。
- Vendor 0／-1 硬刪路徑雖解析 DataStamp，傳給舊 Core 的硬刪未使用版本條件；正式 API 應以版本條件避免刪除過期畫面資料。聯絡人批次刪除也逐筆呼叫，遇錯即停止，可能部分完成。
- `tblPMSubstitutionVendor`、`tblPMSubstitutionVenContactor`、`tblPMSubstitutionVendorMap` 的可信同版 DDL／metadata 均未在 repo 找到。選單快照只提供主表名稱，不能證明欄位型別、長度、PK、FK 或索引；桌機受保護 Oracle profile 不存在，未猜 CREATE。

## 家用端 API／schema handoff

1. 先核對 PostgreSQL live schema／migration 是否已有三張表及現行外鍵、索引；不得直接依 Core 欄位列表補造正式 schema。若缺表，先取得可信欄位／型別依據，再新增 CREATE-only migration。
2. Vendor 清單以授權範圍查詢，接受 `vendorNo`、`issueState` 與 bounded paging；穩定排序為 VendorNo。聯絡人查詢必須以授權後的 VendorNo 作父鍵範圍。
3. Vendor Create／Update DTO 對應 VendorNo、VendorName、Description 與 audit fields；Contact DTO 對應複合鍵與電話、傳真、職稱、Email、地址、說明。伺服器驗證必填欄位、Email／電話格式及主檔狀態政策。
4. Vendor 修改／核准／Unused 轉換以 VendorNo + DataStamp 在交易內更新。Issue Management 決定直接 Active 或 Pending；簽核流程與通知需由家用端整合現有 workflow 能力。
5. Vendor Copy 需在同一交易新增主檔與複製來源聯絡人；明確決定聯絡人 audit 欄位是否記為新建立。不可直接沿用舊 Service 的兩段式呼叫。
6. Vendor hard delete 應在一個交易內重新驗證 IssueState／DataStamp、檢查 PM 計畫等引用，再明確處理聯絡人及 VendorMap；回報引用限制，不可默默刪除使用者未預期的映射。Contactor 修改／刪除需以 `(VendorNo, ContactorName)` 完整複合鍵及 DataStamp 控制併發。
7. Email 操作由登入使用者明確觸發；API 不可自動寄信。DEV 預覽按鈕不會開啟系統郵件程式。
