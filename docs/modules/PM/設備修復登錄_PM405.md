## 主清單與維修視窗

- 主畫面初始化設備資料、`ChamberManage` 參數，再呼叫 `LoadEQPBreakDownStateByUser` 傳入登入者與 `State=1`。Core 對 UserNo 的工程群組過濾已註解，實際 SQL 只按 `EquipmentNo IS NOT NULL` 及 State 條件查詢；主畫面再按 ChamberManage 過濾 Chamber。主 Grid 顯示 BreakDownSerialNo、EquipmentNo、State、BreakDownStartTime、Description、Creator、CreateDate；選列載入原因明細，顯示 BreakDownSerialNo、BreakDownNo、BREAKDOWNCAUSE。
- 主畫面只有單筆 `Repair Register` 操作。按下後以目前列建立 `frmEQPRepairRegisterDef_THEIL_BU1`，成功後重新載入 State=1 清單及明細。
- 視窗欄位包括 EquipmentNo、BreakDownStartTime、RepairUserNo、RepairStartTime、RepairEndTime、Idle／Continue to Produce、Repair Item 勾選清單、Description。設備與故障開始時間由選取故障單帶入；RepairStartTime 預設該列 CreateDate、可修改；RepairEndTime 預設 AP Server 現在時間且唯讀；RepairUserNo 預設登入者，可用人員選擇器。
- 設備狀態選項在 PM404 `ChangeState_Flag=N` 時停用；此類故障單修復不變更 EMS 狀態。其他單據可選 Idle（RepairState=0）或 Continue to Produce（RepairState=1）。視窗至少勾選一項維修項目；清單只載入 PM402 已生效（IssueState=2）的 RepairNo／RepairName，寫入明細只存 RepairNo。
- WinForms 驗證 RepairUserNo、EquipmentNo、RepairStartTime 必須晚於 BreakDownStartTime、RepairStartTime 必須早於 RepairEndTime，且至少勾選一項 Repair Item。Service 再驗證時間格式、RepairStartTime < RepairEndTime，以及有傳入 State 時只接受 0／1。
- 原始表單允許設備查找器改寫 EquipmentNo 顯示欄，但儲存 XML 的目標 BreakDownSerialNo 仍取自原選取的 `EditDataRow`，不使用畫面 EquipmentNo；DEV 固定使用所選故障單的設備以避免欄位與寫入目標錯位。原始 Form 載入 User 清單的呼叫已註解，雖保留選擇器方法，桌機 DEV 以假人員清單呈現選擇操作。

## Service／Core 寫入流程與差異

- 客製 `UpdEQPRepairRegister` 依 BreakDownSerialNo 重新載入故障單及明細，`RepairSerialNo` 直接使用同一 BreakDownSerialNo。
- 儲存順序為：新增 `tblPMEQPBreakDownLog`（BreakDownEndTime=RepairStartTime）及其原因明細；新增 `tblPMEQPRepairLog` 及 `tblPMEQPRepairLogDetail`；若 `ChangeState_Flag=Y`，透過 `EQP Break Down` 狀態控制取得 Idle／ContinueToProduction 的實際設備狀態，並以 RepairEndTime、RepairUserNo 寫入 EMS，ChamberManage=1 時一併要求更新子設備；刪除 `tblPMEQPBreakDownState` 待修復單及其明細；最後寄送設備工程群組郵件。
- 多個 Core 寫入、EMS 更新、待修單刪除及郵件按順序獨立執行，沒有整體交易或可重試機制。任一後段失敗可能留下已建立的部分歷史、已變更 EMS 狀態但待修單仍在，或完成記錄已刪除而郵件失敗。標準 Core SQL 以字串組合，正式 API 必須改用參數化 SQL。
- Service 的 RepairState 宣告使用 C# `default(int)`，實值為 0；旁邊註解卻表示預設值已改為 -999。若 `ChangeState_Flag=Y` 且表單兩個 RadioButton 都未勾選，XML 不帶 State，Service 仍會落到 0（Idle）分支。DEV 保留未勾選 UI，儲存時模擬此實際預設並在規格標示此程式碼／註解不一致。
- Main Form 呼叫名稱含 `ByUser`，但 Core 原有依 UserNo 的群組限制目前整段註解；現行查詢實際只限制 State=1 與設備欄非空。視窗內使用者選擇會更新 RepairUserNo 並重新載入該方法，但該 Core 查詢仍未按 UserNo 限定。部署前家用端需決定要維持現行全體待修清單，或按權限重新設計。

## 表格欄位候選與家用端 API／schema／Create SQL handoff

Core SQL 可見此次流程涉及下列表及欄位；這只是程式使用欄位，不是已核實 schema：

- `tblPMEQPBreakDownLog`：EQPSerialNo、BreakDownSerialNo、EquipmentNo、BreakDownStartTime、BreakDownEndTime、Creator、CreateDate、Description。
- `tblPMEQPBreakDownLogDetail`：EQPSerialNo、BreakDownSerialNo、BreakDownNo。
- `tblPMEQPRepairLog`：EQPSerialNo、BreakDownSerialNo、EquipmentNo、BreakDownStartTime、Creator、CreateDate、RepairSerialNo、RepairStartTime、RepairEndTime、RepairUserNo、Description。
- `tblPMEQPRepairLogDetail`：EQPSerialNo、RepairSerialNo、RepairNo。
- 流程完成後會從 `tblPMEQPBreakDownState` 移除該待修單與原因明細。各表型別、nullable/default、PK／唯一鍵、FK、索引與完整欄位待 metadata 核實。

公司桌機受保護 Oracle profile 不存在，repo 沒有上述四張歷史表可信 DDL／metadata；公司端未查 Oracle、未連 YMES PostgreSQL，也未猜測 CREATE SQL。家用端先核實 live PostgreSQL 與同版 MESTEST 欄位型別、鍵／索引／FK、歷史保留政策及 EMS／Chamber 交易邊界，再建立參數化 API 及 CREATE-only DDL。建議以單一交易完成四張歷史表寫入與 State=1 待修單刪除；EMS 與通知以 outbox／可重試工作處理，避免流程重複寫入或漏信。對待修單使用 expected DataStamp 或狀態條件做一次性消耗，防止重複登錄。
