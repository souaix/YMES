## 畫面與資料規則

- GroupBasis Grid 顯示 GroupNo、SubstitutionType、Description、Creator／CreateDate、Reviser／ReviseDate；DataStamp 隱藏。IssueVisable 設為 False，沒有狀態頁籤或簽核操作。
- 唯一搜尋欄位為 GroupNo。舊 Core Load SQL 沒有 `ORDER BY`、分頁或筆數上限；DEV 保留 fixture／新增順序，不承諾穩定排序。
- 編輯表單必填 GroupNo 與 SubstitutionType，Description 選填。GroupNo 在修改時唯讀；SubstitutionType 由 `LoadSubstitutionType` picker 選取。沒有找到明確欄位長度限制或代碼正規化。
- 成員編輯清單只載入 `IssueState=2` 的 SubstitutionBasis，再以目前群組的 SubstitutionType 過濾；已屬於目前群組的代碼放在右側，其餘同類別已生效備品放在左側。雙擊或方向按鈕移動，確認時回傳完整成員清單。
- Core 的 `UpdSubstitutionGroupDetail` 會檢查同一 SubstitutionNo 是否已出現在其他 GroupNo；比對為字串相等。通過後刪除該 GroupNo 原有全部 Detail，再依新清單重建。此檢查不是資料庫 DDL 證據。

## 操作與舊程式副作用

- 新增建立 GroupBasis，Creator／CreateDate 使用目前登入者與時間；新增時尚無群組成員。
- 修改 GroupNo 唯讀，更新 SubstitutionType／Description 與 Reviser／ReviseDate／DataStamp。若 SubstitutionType 改變，Core 會在同批 SQL 中刪除該 GroupNo 全部 `tblPMSubstitutionGroupDetail`；舊畫面不另問確認。
- 複製先呼叫 AddSubstitutionGroupBasis，再獨立呼叫 CopySubstitutionGroupDetail。複製不是跨兩次呼叫的單一交易；Copy Service 對 Core 複製呼叫有空白 catch，內層複製失敗仍可能回報外層成功。Core Copy 路徑未執行成員跨群組唯一性檢查，可能與一般成員更新規則不一致；實際結果還受未取得的 DB constraint 影響。
- 刪除群組時 Core 先刪該 GroupNo 的 Detail，再刪 Basis；WinForms 多選逐筆呼叫，遇錯停止，先前刪除不會自動回復。
- 成員確認以目前 ActiveRow 的 SubstitutionType 建立一份清單，然後逐筆套用給所有 Selected Group。Core 不驗證成員 SubstitutionType 是否與每個目標群組一致；多選到不同類別群組時，可能把錯類別資料寫入。多群組更新分開呼叫，遇錯也可能部分成功。
- GroupBasis 修改使用 GroupNo + DataStamp；成員明細全量更新沒有自己的 DataStamp。家用端應以資料庫交易與受影響列數避免併發覆寫。

## 家用端 API／schema handoff

1. 先核 PostgreSQL live schema／migration 的 `PMSubstitutionGroupBasis`、`PMSubstitutionGroupDetail`（舊表名 `tblPMSubstitutionGroupBasis`、`tblPMSubstitutionGroupDetail`），以及 SubstitutionType／SubstitutionBasis 的實際鍵與 FK。選單 seed 的 IssueTable 是 NULL；repo 未找到兩張業務表同版 DDL／metadata。缺表時只在取得可信欄位、型別、PK／unique、FK、索引證據後新增 CREATE-only migration。
2. 查詢 API 加登入授權、GroupNo 搜尋、bounded paging、筆數上限、參數化 SQL 與明確排序。Group member lookup 只取 Active SubstitutionBasis 並依授權 scope 篩選。
3. Create／Update 驗證 GroupNo 唯一、SubstitutionType 存在；Update 用 GroupNo + DataStamp。Type 變更時舊程式會清空明細，正式 API 應明確回報並留下 audit，再交易式執行清空與主檔更新。
4. 成員整份替換需單一交易：每個 SubstitutionNo 仍屬 Active、SubstitutionType 與目標群組一致、同一備品至多屬於一個群組，再鎖定／更新 Detail。資料庫需具備相應的唯一性保護，不能只依賴舊 Core 的先查後寫。
5. Copy 應單一交易新增主檔及成員；先驗證每個複製成員是否已屬其他群組，衝突時拒絕整筆並回傳具體代碼。不可吞掉複製例外或照搬目前 Service 的空白 catch。
6. Delete 群組與全部 Detail 原子處理並保留 audit。舊 UI 多選需全有全無或明確逐列回報，不複製其模糊部分成功。
