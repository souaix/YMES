## 畫面、欄位與查詢

- Form 載入全部 IssueState 後，預設選 0「未凍結」；另可切換 1「簽核中」、2「已生效」、-1「未使用」。Grid 依 BreakDownNo 排序。
- 查詢欄位只有 BreakDownNo；WinForms 的 Find 按鈕在 Designer 隱藏，查詢由共用 Form 搜尋／Query 流程完成。DEV 以即時文字篩選該欄位。
- Grid 顯示 BreakDownNo、BreakDownCause、Description、Creator／CreateDate、Reviser／ReviseDate；IssueState 與 DataStamp 隱藏。
- 編輯窗欄位為 BreakDownNo、BreakDownCause、Description。前兩者必填；編輯時 BreakDownNo 唯讀。BreakDownNo 離開欄位會轉大寫；原始 Designer 沒有設 MaxLength。
- 新增／Copy 寫入 Creator／CreateDate，狀態為 0。Copy 從目前選取列帶入三個業務欄位，不複製簽核或附屬紀錄。

## 狀態與操作規則

- Edit 僅接受 IssueState=0；以 BreakDownNo + DataStamp 作版本條件，更新 BreakDownCause／Description／Reviser／ReviseDate，並將 DataStamp 加一。空白 Description 在舊更新 Core 被視為「未提供」，無法用它清空舊值。
- Delete 多選逐筆處理：狀態 0／-1 呼叫 `clsPMBasis.DelBreakDownBasis` 硬刪；狀態 2 由 `clsBasis_UPD.SetBreakDownBasisIssueState` 設為 -1 並更新稽核欄及 DataStamp；狀態 1 或其他值拒絕。逐筆遇錯即停止，之前成功列不回滾。
- 狀態 0／-1 硬刪時，Form 雖傳 DataStamp，Service 會讀取但沒有把版本條件交給 Core；此路徑沒有樂觀併發檢查。程式未見應用層引用檢查，正式 API 應核實設備類型對應、設備故障登錄與資料庫約束後再允許硬刪。
- Approve 僅接受狀態 0，IssueNo 為 `BREAKDOWN BASIS`。沒有 Issue Job Map 或沒有流程明細時直接轉 2；存在流程明細時先建立簽核主檔，狀態轉 1，完成後簽核 SQL 將狀態改為 2，退回則回 0。
- 進入／略過簽核流程時以 DataStamp 版本更新並留下 Reviser／ReviseDate；簽核完成／退回 SQL 直接改 IssueState，沒有同步增 DataStamp／更新稽核欄。DEV checkbox 僅模擬「是否有簽核流程」；進入狀態 1 後不模擬簽核子系統處理。
- 新增、編輯、刪除、核准均有 Service EventLog／ErrorLog；舊 Core 以字串組 SQL，正式 API 必須改參數化查詢並控制權限、併發與完整交易。

## 家用端 API／schema／Create SQL handoff

- 先從 PostgreSQL live schema 核實 `tblPMBreakDownBasis` 及其欄位、主鍵／唯一鍵、FK、索引、nullable/default、資料版本欄位；本次桌機找不到受保護 Oracle attachment/profile，repo 也沒有此表可信 Oracle DDL／metadata。故不猜資料型別、長度、鍵或產生 CREATE SQL。
- 已由選單快照及 WinForms／Service／Core 確認欄位名稱：`BreakDownNo`、`BreakDownCause`、`Description`、`IssueState`、`Creator`、`CreateDate`、`Reviser`、`ReviseDate`、`DataStamp`。除必填欄位及程式使用外，長度、精確型別、nullable、預設、唯一約束及 FK 均待 live schema／Oracle metadata 核實。
- 建議正式 API 提供 BreakDownNo 限定且分頁／穩定排序的列表；新增；狀態 0 + expected DataStamp 的修改；逐筆核准／送簽；逐筆停用／硬刪。服務端需驗證 IssueState，不接受客戶端任意狀態轉換，Audit 使用認證使用者與伺服器時間。
- Active=2 刪除應依舊規則停用為 -1；硬刪 0／-1 前先確認 PM403 對應及 PM404 故障登錄是否引用，並依 PostgreSQL FK／保留規則拒絕或受控清理。不要重現多筆逐項部分成功；每批操作以明確逐筆結果或原子交易契約實作。
- Issue workflow 應整合共用簽核能力：直接生效與進入 Pending 需同一交易記錄 DataStamp／稽核；簽核核准／退回也需一致更新稽核欄、版本及狀態，補足舊簽核 SQL 未更新版本的缺口。
- UI DEV 以假資料模擬 CRUD、複製、四狀態、核准、軟停用／硬刪與 DataStamp；它不是正式 API／schema 驗收。
