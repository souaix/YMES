## 畫面與欄位

- 預設 IssueState 0「未凍結」；頁籤為 0 未凍結、1 簽核中、2 已生效、-1 未使用。Grid 依 MaintainNo 升冪排序。
- 搜尋欄只有 MaintainNo；舊 Load Service/Core 也接受 MaintainName，但 Form 沒有使用該搜尋條件。
- Grid 顯示 MaintainNo、MaintainName、Memo、Description、Creator/CreateDate、Reviser/ReviseDate；IssueState 與 DataStamp 隱藏。
- 編輯欄位為 MaintainNo、MaintainName、Memo、Description。MaintainNo、MaintainName 只以空字串檢查必填、不 Trim；MaintainNo 離開欄位時轉大寫。原始碼未見長度上限驗證。
- 新增與複製建立 IssueState 0。複製可從任一狀態資料開啟，複製四個業務欄位，不複製審核與稽核欄位。
- Edit Service 拒絕空 MaintainName；空 Memo／Description 被視為未傳，因此不能以清空文字方式清除舊值。DEV 預覽保留此行為。

## 狀態與操作

- 修改僅允許 IssueState 0；MaintainNo 在修改模式唯讀。Apply 儲存後保持視窗開啟，Confirm 使用相同服務並關閉。
- 刪除逐筆執行：IssueState 0 或 -1 硬刪 Basis；IssueState 2 透過 MaintainNo + DataStamp 改為 -1；IssueState 1 等其他狀態拒絕。Core 硬刪僅刪 `tblPMMaintenanceTypeBasis`，未先檢查引用。
- `tblPMMaintenanceItemBasis` 以 MaintainNo 關聯到維護方式，`clsPMBasis.LoadMaintenanceItemBasis` 會 Join 本表取得 MaintainName；家用端硬刪須先查 live schema、FK 與引用資料。
- 核准僅允許 IssueState 0，逐列呼叫 Service。Issue Management 的 IssueNo 為 `MAINTENANCE TYPE`：沒有 mapping 或沒有流程明細時直接設 2；有流程明細時建核准 SQL（2）與退回 SQL（0）、啟動流程並將目前列設 1，之後寄信通知第一關群組。
- 多筆刪除／核准遇第一個失敗就停止；已成功的前列不回滾。
- `clsBasis_UPD` 修改與直接 IssueState 更新都以 MaintainNo + DataStamp 更新，DataStamp +1 並寫 Reviser/ReviseDate。Issue Management 流程完成／退回的 SQL 直接更改 IssueState，該 SQL 本身未更新 DataStamp 或稽核欄位。

## 家用端 API／schema handoff

- 本地選單清冊及舊 Core 可確認主表名稱，沒有可信的業務表 DDL／metadata。桌機受保護 Oracle MESTEST profile 不存在，本次未連 Oracle，也未臆造 PostgreSQL CREATE SQL。
- 家用端先核 live PostgreSQL schema／migration，確認 MaintainNo、MaintainName、Memo、Description、IssueState、Creator/CreateDate、Reviser/ReviseDate、DataStamp 型別、nullable、PK 與 default，再決定是否新增 CREATE-only migration。
- 建議授權且 bounded 的狀態／MaintainNo 查詢、建立命令、以 MaintainNo + DataStamp 原子修改、狀態式刪除、Issue workflow 命令；採參數化 SQL 與穩定排序，避免舊 Service/Core 動態串接 SQL。
- 刪除維護方式前查核 `tblPMMaintenanceItemBasis` 的 MaintainNo 引用、FK 與已建立保養計劃等其他實際呼叫端；若仍被引用應拒絕硬刪或依確認過的產品政策處理。Issue 完成／退回需同步維護 DataStamp、Revision audit 與狀態，且交易式避免 workflow 重複套用。
