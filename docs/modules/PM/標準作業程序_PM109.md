## 畫面與欄位

- 主清單預設 IssueState 0「未凍結」，另有 1「簽核中」、2「已生效」、-1「未使用」頁籤；僅以 PMSOPNo 搜尋，依 PMSOPNo 排序。
- Grid 欄位：PMSOPNo、PMSOPName、SOPFilePath、EstDoneTime、Description、Creator/CreateDate、Reviser/ReviseDate；IssueState、DataStamp 隱藏。
- 主檔欄位 PMSOPNo、PMSOPName 必填；SOPNo 離開輸入欄位時轉大寫，兩欄各 MaxLength 50，編輯時 SOPNo 鎖定。SOPFilePath 由檔案選取器帶入，非必填；舊程式只保存用戶端路徑字串，沒有上傳檔案。EstDoneTime 必填數值且 Confirm 檢查不得小於 0；Description 可空。
- 編輯主檔時 Core 將空 SOPFilePath、Description 視為「未提供」，所以不能靠清空欄位移除舊值。Apply 的工時檢查沒有負數檢查，Confirm 才有；DEV 兩者皆採 `>= 0` 驗證。
- Detail 開啟獨立明細視窗，顯示 PMSOPNo、PMSOPSerialNo、PMItemNo、PMITEMNAME、Creator/CreateDate、Reviser/ReviseDate。PMITEMNAME 由 `tblPMMaintenanceItemBasis` Left Join 得到。PM Item picker 讀完整 MaintenanceItem 清單，未依 IssueState 篩選；編輯時鎖 PMItemNo，新增與複製可選項目。
- 明細以 (PMSOPNo, PMItemNo) 作為舊 Core Edit／Delete 條件。PMSOPSerialNo 必填數值，欄位 MaxLength 7，鍵盤只允許數字與小數點。Add Service 將輸入先向下取一位小數再轉 `int`，因此新增／複製實際落庫會截成整數；Edit 使用 double 並保留一位小數。Core 的自動重排呼叫已註解。舊 Form 將 Grid Sort 設為 PMSOPNo（同一主檔值），沒有明確按步驟序號排序；DEV 為了可讀性依 serial number 顯示並記錄此差異。

## 狀態與操作

- 主檔新增為 IssueState 0。修改只允許 0，以 DataStamp 更新 Reviser/ReviseDate；主鍵唯讀。主檔複製可從任一狀態執行：先用 Add 建立新主檔（欄位從來源預填），再另外呼叫 `CopySopDetail` 複製步驟及重設明細 Creator/CreateDate；兩次呼叫不是同一個 Service 操作，需注意部分成功。
- 主檔刪除逐筆執行：0／-1 硬刪，2 改為 -1，1 拒絕。Core 以 CollectionSQL 先刪 `tblPMSOPDetail` 再刪 SOP Basis；家用端仍須核實交易 helper 與 live FK／DataStamp 條件，避免父列版本衝突時子列先被刪。
- 核准只接受 IssueState 0，IssueNo 為 `SOP BASIS`。無簽核設定／流程明細時直接 Active=2；有流程則送 Issue 並設 Pending=1，核准 SQL 設 2、退回 SQL 設 0。流程完成時的原始 SQL 直接改 IssueState，沒有更新 DataStamp／audit。多選核准／刪除逐列呼叫，遇首筆錯誤停止，前面成功列不回滾。
- Detail 視窗可從主檔任一 IssueState 開啟；舊 Form／Service／Core 沒有檢查父 SOP 狀態，因此 DEV 保留獨立明細 CRUD。明細 Delete 不自動補排序號；明細多選刪除逐列執行，可能部分成功。
- DEV 以本機 sample path 取代 Windows 檔案選擇器；路徑只作文字假資料，不讀檔、不上傳。新增／複製 serial 沿用舊 Service 的整數落庫行為，編輯保留 1 位小數。

## 家用端 API／schema handoff

- repo `database/`、`docs/` 沒有可核實的 `tblPMSOPBasis`／`tblPMSOPDetail` 業務 DDL／metadata；選單資料只確認 Basis 表名。公司桌機受保護 Oracle MESTEST profile 不存在，本項未查 Oracle，未猜 PostgreSQL CREATE SQL。
- 家用端先查 live PostgreSQL schema／migration，確認主表欄位 PMSOPNo、PMSOPName、SOPFilePath、EstDoneTime、Description、IssueState、Creator/CreateDate、Reviser/ReviseDate、DataStamp；明細 PMSOPNo、PMItemNo、PMSOPSerialNo 與 audit/DataStamp。確認資料型別、nullable/default、PK／唯一鍵、FK、索引及數值精度後，再新增必要的 CREATE-only migration。
- API 建議提供有權限且 bounded 的 IssueState／PMSOPNo 搜尋、穩定排序主檔查詢；主檔 create、以 PMSOPNo + DataStamp 修改、狀態命令；依 PMSOPNo 載入步驟、以 (PMSOPNo, PMItemNo) 新增／修改／刪除／複製明細。所有 SQL 參數化，列表穩定排序／分頁。
- SOP No 應交易內唯一。新增／修改步驟前交易內驗證 SOP、PM108 MaintenanceItem 存在，並依 live schema 決定複合唯一鍵及 PMSOPSerialNo 精度。複製 SOP 應在單一交易建立主檔及步驟；硬刪先重驗 DataStamp，再原子刪步驟及主檔。子步驟 API 應核實並限制父 IssueState，避免舊 UI 可在 Pending／Active／Unused 狀態直接編修。
- SOPFilePath 在舊客戶端只是路徑文字。正式系統若要提供跨端文件存取，需另定受控文件儲存／授權方案；不要將公司端本機路徑誤當已上傳文件，也不要在此模組自行建立上傳端點。
- 正式 Issue workflow 應透過 YMES Issue service 管理；不可照搬舊 Service 結尾直接更新狀態而略過 DataStamp／稽核。
