## 畫面與資料規則

- 預設載入 Unfrozen（`IssueState=0`）；唯一搜尋欄位為 `SubstitutionType`。狀態頁籤為 Unfrozen `0`、Pending `1`、Active `2`、Unused `-1`。
- Grid 顯示 SubstitutionType、Description、Creator／CreateDate、Reviser／ReviseDate；IssueState 與 DataStamp 隱藏。
- SubstitutionType 必填；舊表單離開欄位時去除前後空白並轉大寫，沒有找到明確的欄位長度限制。Description 可輸入多行。
- Core 新增程式保留一段已註解的檢查：SubstitutionType 不應與 `tblPMSubstitutionBasis.SubstitutionNo` 相同，理由是兩者共用 Property。這段檢查目前不會執行；家用端應核實 Property 的共用識別空間，並以資料庫約束或交易內檢查避免衝突。

## 操作與狀態

- 新增與複製均建立 `IssueState=0`，Creator／CreateDate 使用目前登入者與時間。複製沿用原代碼和 Description，操作者需換成新代碼。
- 修改只允許 Unfrozen；SubstitutionType 唯讀，修改 Description，保留 Creator／CreateDate 並更新 Reviser／ReviseDate／DataStamp。
- 刪除允許 Unfrozen／Unused 硬刪單一類別；Active 改成 `IssueState=-1`；Pending 拒絕。舊 Core hard delete 只刪 `tblPMSubstitutionType` row，若備品、群組或其他 PM 資料引用該類別，可能受 FK／應用層完整性限制。
- 核准只接受 Unfrozen。Service 查 Issue Management 的 `SUBSTITUTION TYPE BASIS`：沒有可用 job/detail 時直接改 Active；有簽核明細時建立簽核工作、狀態轉 Pending 並通知第一簽核群組；簽核退回會把狀態回復 Unfrozen。
- 修改與狀態變更經 `clsBasis_UPD` 以 SubstitutionType + DataStamp 更新，成功筆數不符時回報失敗。DEV 在 localStorage 做本機版本比較，不能保證跨使用者併發。
- 批次刪除／核准由 WinForms 逐筆呼叫；遇第一筆失敗會停止，先前已成功的項目不會自動回復。DEV 將所選列在一次本機操作中處理，未模擬服務逐筆部分成功。

## 已知來源限制與風險

- Core Load/Add/Del 以字串組合 SQL 條件與欄值；查詢沒有伺服器分頁或穩定排序。正式 API 必須參數化、限制筆數、授權範圍並穩定排序。
- 已註解的跨表重複檢查讓相同代碼可能與 SubstitutionBasis 編號衝突；另外要核實 SubstitutionGroup／MaintenanceItem 等引用。不要把舊程式未執行的檢查當成資料庫 constraint。
- `TBLPMSUBSTITUTIONTYPE` 的可信同版 DDL／metadata 未在 repo 找到。選單快照僅證明表名與 FunctionKey，不證明欄位型別、長度、PK、索引、FK 或預設值。桌機受保護 Oracle profile 不存在，未猜 CREATE。

## 家用端 API／schema handoff

1. 先核對 PostgreSQL live schema／migrations 是否已有 `PMSubstitutionType`；再確認實際引用它的 SubstitutionBasis、SubstitutionGroup、MaintenanceItem 等資料與鍵。若缺表，取得可信欄位／型別證據後才新增 CREATE-only migration。
2. 提供登入授權查詢，接受 `substitutionType`、`issueState` 及 bounded paging；以正規化代碼做 case-insensitive 搜尋與唯一性檢查，回傳穩定排序與總筆數上限。
3. Create／Update DTO 包含 SubstitutionType、Description 與 audit 欄位；伺服器 trim／uppercase。交易內驗證代碼未與 SubstitutionBasis 的共用 Property 識別衝突，並保護相關參照。
4. Update／Approve／Unused transition 以 SubstitutionType + DataStamp 交易式更新；Issue Management 決定 Active 或 Pending，接入既有正式 workflow 及退回流程。
5. Delete 依 IssueState 分流：0／-1 硬刪前檢查所有引用；2 改 -1；1 拒絕。批次操作需在一個交易內全有全無，或明確回傳逐列結果；不可複製舊 WinForms 逐筆停止但回報整體模糊成功的行為。
