## 查詢畫面與操作

- 主畫面 `IssueVisable=False`，依 `BreakDownSerialNo` 搜尋；Service／Core 查詢只列 `State=0` 未確認登錄。若 `SYSParameter.ChamberManage` 不等於 `1`，排除 Chamber 設備。主 Grid 顯示 BreakDownSerialNo、EquipmentNo、State、BreakDownStartTime、Description、Creator、CreateDate、Reviser、ReviseDate；選取列後載入原因明細。
- 明細由 `tblPMEQPBreakDownStateDetail` 連故障原因主檔，顯示 BreakDownSerialNo、BreakDownNo、BreakDownCause、Description。Core 使用 inner join；沒有對應故障原因主檔的明細不會顯示。
- 工具列提供 Add、Edit、Delete（可多選）、Copy、Confirm（可多選）。Add／Copy 產生新序號、預設故障開始時間與 Next_PM_Date 為目前時間，設備可選；Edit 時設備欄位唯讀，僅可修改未確認單。Copy 沿用設備、原因、狀態選擇及說明，但重新取號並重設日期。
- 設備選擇器只列非 Chamber，除非 ChamberManage=1。DEV 以開關模擬此系統參數；此開關和設備清單都是假資料。
- 故障原因選擇依所選 EquipmentType 讀 PM403 映射，並以 PM401 `IssueState=2` 為新選項。至少勾選一項原因才能儲存。歷史明細仍按原因主檔代碼連回原因名稱及 Description。
- `BreakDownStartTime` 必須早於現在。序號由 `wsPM.NewEQPBreakDownSerialNo` 取得，WinForms 提供重新取號及轉大寫；序號實際格式／產生器規則尚未從呼叫鏈完整確認，DEV 的 9 位流水號只為操作樣例。
- 狀態控制選項由設備狀態主檔 Description 含 `CHANGED` 的資料載入；Description 含 `NOCHANGED` 時存 `ChangeState_Flag=N`，確認時不改 EMS 設備狀態。未選擇時客製 Service 讀 ES102（ControlNo=`BreakDown`、ControlType=`EQP Break Down`）作為預設故障狀態。DEV 對應 PM 假資料中的 ES102 與 NOCHANGE 選項。

## 狀態、資料寫入與已知行為

- 新增寫 `tblPMEQPBreakDownState`，State=0、EQPSerialNo=`-9999`；可見欄位包括 BreakDownSerialNo、EQPSerialNo、EquipmentNo、State、BreakDownStartTime、Description、ChangeState_Flag、ChangeState、Next_PM_Date、RepairSerialNo、RepairStartTime、RepairUserNo 及建立／修改稽核欄位。實際 nullable、型別、預設值與完整欄位仍須查可信 DDL。
- Add Service 以 `GetEQPBreakDownState(EquipmentNo)` 查重，查詢沒有 State 條件，因此任何既存狀態的故障登錄都會阻擋該 EquipmentNo 再新增；此規則比畫面僅列 State=0 更廣。開始時間必須嚴格早於現在。
- 新增／修改父列成功後，WinForms 另呼叫標準 `UpdEQPBreakDownStateDetail` 更新明細：Add 寫入勾選原因；Edit 先刪除該序號所有明細再逐筆重建。父列和子列不是一個原子交易，逐筆子列失敗可能留下部分結果。
- Edit XML 有 DataStamp，但客製 Service 雖解析該欄位，呼叫的客製 Core Edit 沒有 DataStamp 參數；此路徑沒有樂觀併發條件。客製 Core Edit 也沒有 Reviser／ReviseDate 參數，故未更新這兩個稽核欄。
- Delete 僅由目前 State=0 主畫面操作；標準 Service／Core 先刪該序號明細，再刪父列。多筆由 UI 逐筆呼叫，會有部分成功可能，且是硬刪。
- Confirm 逐序號呼叫客製 Service：若 ChangeState_Flag=Y 且 ChangeState 有值，先更新 EMS 設備狀態；ChamberManage=1 時亦要求更新 Chamber；接著把登錄改為 State=1、將 EQPSerialNo 換成目前 EMS 設備序號，最後寄送設備工程群組郵件。步驟分開執行，沒有整體交易，設備狀態更新或郵件失敗可能發生部分完成。DEV 只模擬可見狀態改變，不連 EMS、不寄信。
- 確認後記錄從此畫面的 `State=0` 清單消失；它進入下游待處理狀態，並非故障已修復。

## 家用端 API／schema／Create SQL handoff

- 桌機本機受保護 Oracle profile 不存在，repo 無 `tblPMEQPBreakDownState`／`tblPMEQPBreakDownStateDetail` 的可信業務 DDL／metadata。公司端未查 Oracle、未連 YMES PostgreSQL；不根據 Core SQL 猜欄位型別、索引、FK 或產生 CREATE SQL。
- 家用端先核對 live PostgreSQL 與可信同版 MESTEST DDL／metadata，確認完整欄位、型別長度、PK／唯一鍵、索引、FK、DataStamp、`-9999` 暫存值、State 編碼、序號產生器和刪除限制，再提供 CREATE-only DDL。
- 正式 API 建議拆查詢、建立、修改、刪除、確認及原因明細操作；新增設備重複檢查須按舊 Service 語義明確決定要檢查所有 State 或只檢查未確認，並加資料庫唯一性／併發保護。查詢需包含狀態與 ChamberManage 規則，並連回原因名稱／說明。
- 修改與刪除應使用 expected DataStamp，設備與明細需在單一交易內維護；確認應設計可重試流程或 outbox，避免 EMS 狀態已更新但登錄未確認／郵件遺失。外寄郵件及 EMS 狀態同步由家用端服務負責，不由公司端 DEV 執行。
- 家用端需核 PM403 映射、PM401 故障原因、設備主檔、設備狀態主檔、EMS 設備狀態與 `SYSParameter` 的資料庫關聯及刪除限制。
