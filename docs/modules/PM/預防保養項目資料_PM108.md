## 畫面與欄位

- 預設 IssueState 0「未凍結」；狀態頁籤為 0 未凍結、1 簽核中、2 已生效、-1 未使用。主 Grid 依 PMItemNo 升冪排序，只搜尋 PMItemNo。
- 主 Grid 顯示 PMItemNo、PMItemName、MaintainNo／MaintainName、PMJobNo／PMJOBNAME、Creator/CreateDate、Description、Reviser/ReviseDate；IssueState、DataStamp 隱藏。Core Load 以 Left Join 從 `tblPMMaintenanceTypeBasis`、`tblPMJobTypeBasis` 取得名稱。
- 主檔欄位 PMItemNo、PMItemName、MaintainNo、PMJobNo 必填（WinForms 以空字串檢查，不 Trim）；Description 可空。PMItemNo 離開欄位時轉大寫，編輯時唯讀。新增／編輯表單載入全部維護方式與工作形式 lookup，未在 Form 限制只選 Active。
- 每次選取主列，自動載入該 PMItemNo 的 Tool Used 與 Substitution Used 兩個子 Grid。兩個明細視窗可獨立新增、修改、複製、刪除。
- Tool 欄位 PMItemNo、ToolNo、ToolQty 及 audit/DataStamp；ToolNo 由 `wsEQP.LoadToolBasis` lookup，編輯時不可換 ToolNo。ToolQty 必填、數值、整數且 >0。
- Substitution 欄位 PMItemNo、SubstitutionNo、UnitNo、SubstitutionQty 及 audit/DataStamp；SubstitutionNo 從整份 SubstitutionBasis lookup 選取，選取時帶出該備品 UnitNo。SubstitutionQty 必填數值、整數且 >0。Form 另載入 IssueState 2 的 Unit lookup，但其 Unit 搜尋按鈕程式碼已註解，實際選擇備品時直接帶入 UnitNo。

## 狀態與操作

- 主檔新增與複製建立 IssueState 0。複製可由任一狀態列操作，先新增主檔，再以另一個 `CopyMaintenanceItem` Service 呼叫複製 Tool／Substitution 明細。
- 主檔修改只允許 IssueState 0，使用 PMItemNo + DataStamp；Core Update 增加 DataStamp 並更新 Reviser/ReviseDate。空 Description 會被當成未傳欄位，不能以留白清除舊值。
- 主檔刪除逐列執行：0／-1 硬刪；2 改為 -1；1 及其他狀態拒絕。Core 硬刪在同次 CollectionSQL 中先刪 Tool Used、Substitution Used，再刪 Basis。Active→Unused 保留子明細。
- 核准僅接受 IssueState 0。Issue Management 的 IssueNo 是 `MAINTENANCE ITEM`：無 mapping 或無流程明細時直接 Active=2；有流程時建立核准=2／退回=0 SQL，送簽並改為 Pending=1，通知第一關群組。workflow 最終 SQL 直接更新狀態，該 SQL 本身沒有更新 DataStamp／audit。
- 主檔批次刪除／核准逐筆呼叫，遇第一個失敗即停止，已成功列不回滾。
- Tool Used 明細以 `(PMItemNo, ToolNo)` 定位；Substitution Used 以 `(PMItemNo, SubstitutionNo)` 定位。兩種子明細各自用 DataStamp 保護 Edit；Form 可從任何主檔狀態開啟明細視窗，舊 Service/Core 未見檢查父主檔 IssueState。
- 複製 Service 的 Core 分別複製兩種明細，但 Service 對每一種複製各自使用空 catch 吞掉例外，可能只複製主檔或只複製部分明細仍回傳 success。

## 家用端 API／schema handoff

- 本地選單及原始程式碼可確認三張表名、欄位呼叫與操作鍵，但 repo `database/`／`docs/` 沒有這三表的可核實業務 DDL／metadata。公司桌機受保護 Oracle MESTEST profile 不存在，本次未連 Oracle，未猜 PostgreSQL CREATE SQL。
- 家用端先比對 PostgreSQL live schema／migration，確認三表欄位型別、nullable、預設值、PK／FK、唯一鍵及 audit 欄位後，再決定需要的 CREATE-only migration。來源呼叫可見主欄位：Basis `(PMItemNo, PMItemName, MaintainNo, PMJobNo, Description, IssueState)`；Tool `(PMItemNo, ToolNo, ToolQty)`；Substitution `(PMItemNo, SubstitutionNo, UnitNo, SubstitutionQty)`。
- 建議授權且 bounded 的狀態／PMItemNo contains 查詢及穩定排序；主檔建立、以 PMItemNo + DataStamp 修改／狀態命令；兩個子資源依完整父鍵與複合鍵查詢／寫入。採參數化 SQL，不沿用舊 Service/Core 的 SQL 字串串接。
- 建立／修改主檔時在交易內驗證 MaintainNo、PMJobNo references；子項目在交易內驗證父項目存在與可編輯狀態，避免舊頁從 Pending／Active／Unused 父列直接改子表。硬刪主檔時原子刪兩種子明細與主列，或核 live FK 後明確拒絕；不要讓孤兒列風險落到偶發 constraint error。
- 將主檔＋兩種明細 Copy 改成同一交易，任何子複製失敗都回滾主檔；Issue workflow 成功／退回也同步 DataStamp、Reviser/ReviseDate 與狀態，避免目前舊流程版本資訊未變。
