# PM301 開立保養工單

## 功能與來源

- MES 選單為「保養工單 → 開立保養工單」，FunctionNo `PMWO BASIS`、FunctionKey `PM301`，Form `frmPMWoBasis`，ExecutionFile `PM_WOBasis.dll`。DEV 入口 `/YMES/PM/WorkOrderBasis`。
- 已核對 `STD/MESWin/PM/PM_WOBasis/frmPMWoBasis.vb`、`frmPMWoCreate.vb`、`frmPMWoDetailDef.vb`、`frmShowSopDetail.vb`（均含 inline Designer），Service `MESws_STD/wsSTD/wsPM/wsPM.cs`，Core `MESkc/kcPM/clsPMBasis.cs` 與 `MESkc/kcBasis_UPD/clsBasis_UPD.cs`；簽核流程另經 `kcISSUE.clsIssue`。
- Service 包含 `LoadPMWoBasis`、`LoadPMWoDetail`、`AddPMWoBasis`、`DelPMWoBasis`、`ApprovePMWoBasis`、`EditPMWoDetail`、`DelPMWoDetail`。PM 計畫建立另呼叫 `LoadEQPMaintenancePlan`，SOP 檢視會載入 SOP 步驟、工具及備品。

## WinForms 主畫面與狀態

- 主 Form 是上方工單主檔 Grid、下方所選工單明細 Grid。上方有 Add／Delete／Approve、SOP Detail；下方有明細 Edit／Delete、單項 SOP Detail。搜尋欄位設為 `WONo`。
- 主檔查詢由 `wsPM.LoadPMWoBasis` 載入並於 Form 依 IssueState 篩選、依 WONo 排序；狀態值為 0 未凍結、1 簽核中、2 已生效、-1 未使用。明細由 `LoadPMWoDetail(WONo)` 載入，依 WOItemNo 排序。`ChamberManage` 與設備清單會決定是否從畫面明細排除子設備。
- 主 Grid 顯示 WONo、WOType、Description、Creator、CreateDate，IssueState 欄隱藏，由狀態 Radio 切換；Detail Grid 隱藏 WONo、PMSerialNo、PMEQPSOPNo、DataStamp，顯示 Item、Equipment、SOP、預計日期、WOStatus、下線／完成日期、執行人／說明及稽核欄位。
- WOStatus：0 待簽核、1 待料、2 已下線、3 已完成、4 已撤線。PM302／PM303 後續流程會更新已下線及完成等欄位。

## 可見的 PM Work Order 建立流程

- 主畫面 Add 開啟 `frmPMWoCreate`，預設顯示 PM Work Order 頁。Form 提供設備與 SOP 多選條件、預計保養日期起迄、計畫查詢、計畫加入工單明細及移除。可選 SOP 先讀 PM SOP 與設備類型 SOP 關聯；計畫查詢可帶 EquipmentNo、PMSOPNo 及日期界限。
- 確認至少有一筆明細後，Service 傳 `WOType=0` 呼叫 `AddPMWoBasis`。Core 建立主檔 `IssueState=2`；每筆 detail 初始 `WOStatus=1`，保存 WOItemNo、來源 SerialNo、PMSerialNo、EquipmentNo、PMEQPSOPNo、PMSOPNo 及 PMEstDateTime。
- 開單同時為每筆來源保養計畫新增 `tblPMEQPMaintenancePlanLog`，設 `ExecuteState=2` 並記錄 PMWONo／PMWoItemNo／工單日期／LogCreator，再刪除 `tblPMEQPMaintenancePlan` 活動列。此行為會消耗所選計畫，不可只新增工單明細而保留可重複開單的活動計畫。
- `funInitPMWONo` 依 `tblPMWOBASIS` 與歷史表的最大號碼產生 `EWyyMM####`；月份變更或當月序號到上限時重設月序號。舊程式由最大值推序號，正式 API 需用資料庫序號／鎖定避免併發撞號。
- 建立成功後主畫面切到已生效狀態並定位新工單。建立視窗可選擇繼續開下一批；DEV 只建立一次並關閉視窗。

## 隱藏的 Required Work Order 程式路徑

- `frmPMWoCreate` 另有 Required Work Order 頁及設備／SOP／預計日期手動新增明細的程式碼，但 Designer 將 `tabRequiredWorkOrder.Visible = False`，目前這版 UI 不會顯示該頁。若透過 Service 建立 `WOType=1`，Core 會建立 `IssueState=0`、明細 `WOStatus=0`；PM301 DEV 不提供隱藏頁的新增入口，但保留既有特殊需求工單的假資料以檢視狀態頁。

## 簽核、刪除與明細規則

- Approve 僅處理 IssueState=0。Service 查 `IssueNo=PMWO BASIS`：未設定 IssueJobMap（或沒有流程明細）時直接將主檔改為 Active；有流程時以 `clsIssue.StartIssueProcess` 建立簽核、寄送第一簽核群組郵件並轉 Pending。流程核准會把主檔設為 2、Detail WOStatus 設為 1；退回設回 0 並把 Detail WOStatus 設為 0。
- Delete 對 IssueState=0 或 -1 實體刪除 Detail 與主檔；對 IssueState=2，Form 先要求該工單全部明細皆為 `WOStatus=1`，Service 再將 IssueState 設為 -1，Core 同時將明細狀態改為 4（撤線），而非實體刪除。IssueState=1 不允許刪除。舊 Form 多選逐筆呼叫，前面成功而後續失敗時可能部分完成。
- Detail Edit／Delete 僅在主檔未凍結時允許。Edit 視窗只提供 PMSOPNo 與 PMEstDateTime，帶 DataStamp 並由 UPD Core 條件更新；刪除後 Core 另呼叫 `ReArrangeWoItemOrder` 重排 ItemNo。其他完成／下線欄位由後續工單模組處理。
- 上方 SOP Detail 顯示工單中的 SOP；下方 SOP Detail 依目前選取明細顯示該 SOP。檢視表單載入 SOP Basis、SOP Item Detail、Tools Used、Substitutions Used。
- 舊 Core `AddPMWoBasis` 對 PMType=0 以一組批次 SQL 寫主檔、明細、計畫歷史並刪計畫；確認 helper 的資料庫交易語意需再查其執行實作。家用端應在單一交易鎖定仍未開單的計畫，原子寫入主檔／明細／歷史並刪活動計畫。

## 家用端 API、schema 與 SQL handoff

- 建議 `GET /api/pm/work-orders?woNo={no}&issueState={state}&page={n}&pageSize={n}` 以 WONo、狀態索引並分頁；`GET /api/pm/work-orders/{woNo}` 回傳主檔及有序明細。
- 建議 `POST /api/pm/work-orders` 接受明確 `workOrderType` 與明細來源。PM 計畫型建立需在單一交易鎖定／重驗計畫仍未被消耗、主檔號碼唯一、設備與 SOP 關聯有效後寫入主檔、明細、PlanLog，再刪除活動 Plan；回傳新 WONo。即時簽核另由 `POST /api/pm/work-orders/{woNo}/approve` 協調 Issue Management 與狀態轉換，不能只直接修改主檔狀態。特殊需求型資料入口目前在這版舊 UI 隱藏，需家用端確認是否要提供對應 API／UI。
- 未凍結明細可用 `PATCH /api/pm/work-orders/{woNo}/items/{itemNo}` 帶 DataStamp 更新 SOP／預計日期；明細刪除由 `DELETE` 命令在驗證父單狀態後刪除並重排或由伺服器維持排序。未凍結／未使用主檔可走刪除命令；已生效主檔只能在所有明細為待料時執行 phase-out，保留主檔與 WOStatus=4 明細；簽核中拒絕刪除。
- 直接表與核心相依：`tblPMWoBasis`、`tblPMWODetail`、`tblPMWoBasis_His`、`tblPMWoDetail_His`、`tblPMEQPMaintenancePlan`、`tblPMEQPMaintenancePlanLog`、SOP Basis／Detail／Tools Used／Substitutions Used、Equipment Basis、Issue Management。History 表在本功能號碼產生及 Grid ValueList 有引用，但目前 Form CRUD 主要使用活動表。
- 本桌機沒有可用受保護 Oracle profile，repo 無可核實的 PM Work Order 直接表 DDL／索引／約束；本次未查 MESTEST metadata，也未產生猜測 CREATE-only SQL。家用端先比 live PostgreSQL schema／migration 與可信 Oracle metadata，再確認歷史表與交易邊界。
- 公司端未連 YMES PostgreSQL、未實作或驗收正式 API／schema、未部署；未執行 build、test 或 browser。此次為來源靜態檢閱與 DEV 假資料交付。
