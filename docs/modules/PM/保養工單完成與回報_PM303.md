## 功能與來源

- MES 選單為「保養工單 → 保養工單完成與回報」，FunctionNo `PMWO COMPLETE`、FunctionKey `PM303`，Form `frmPMWoFinish`，ExecutionFile `PM_WOFinish_EQM_THEIL.dll`。
- 已核對 `D:\iMES\CSiMES\STD\MESWin\PM\PM_WOFinish\frmPMWoFinish.vb`、`frmPMWoFinishDef.vb`（含 inline Designer）、`MESws_STD/wsSTD/wsPM/wsPM.cs` 的 `RepayForWoDetail`，以及 `MESkc/kcPM/clsPMBasis.cs` 的 `RepayForWoDetail`、`funCheckWOAndMoveToHistory`、`funMoveWoToHistory`。
- 主畫面用 `LoadPMWoBasis` 載入工單、`LoadPMWoDetail(WONo)` 載入明細；SOP Detail 視窗提供該明細的 PM SOP 步驟、工具及替代備品。

## WinForms 查詢和回報操作

- 查詢條件為多選 WO No、Creator、Create Date From／To（Designer 初始未勾選）及 PM Order／REQ Order（初始皆未勾選，代表不限制 WOType）。主檔固定限制 `IssueState=2` 且至少一筆 `WOStatus=2` 明細；主檔 Grid 顯示 WONo、WOType、Description、Creator、CreateDate。
- 選取工單後，明細查詢只載入 `WOStatus=2`（已下線）明細，並依 Chamber Manage 設定於 Grid 隱藏子設備。明細顯示設備、SOP、預計日期、狀態、下線／完成日期、Executor 及 ExecuteDesc。
- `Repay by Item` 回報目前作用中明細；`Repay by WO` 回報目前工單已下線明細。對話框顯示 WO No、WO Type、Repay By（登入者、唯讀）、完成日期／時間及 Execute Description；逐項回報才顯示 Item No。整張工單回報共用一個完成時間與說明。
- `FinishedDate` 不可早於 `ReleaseDate` 的檢查只顯示提示，舊 Form 沒有中止送出。Designer 的日期選擇器初始 `Checked=False`，但送出程式仍直接讀 `Value.Date`，所以實際會送入 DateTimePicker 的預設日期與時間，而非空日期。
- 表單查詢 `ControlNo=PMWoFinished`、`ControlType=PM Work Order` 以決定回報後設備狀態。沒有狀態控制時可選擇繼續且不更新設備狀態。Service 對每筆重新讀 SOP `LockEquipment`、檢查目前設備狀態與違規轉換；`LockEquipment=0` 的明細略過設備狀態變更。Core 完成後，Service 才逐列呼叫 EQP `EditEquipmentState`；Chamber Manage 啟用時傳 `UpdateChamberState=true`。

## Service／Core 資料異動

- `wsPM.RepayForWoDetail` 解析 WONo、WOType、EquipmentState、ExecuteDesc、明細 Item／Serial／Equipment／FinishedDate，再驗證狀態轉換與 SOP 鎖定，接著呼叫 Core。一般使用者不可直接指定 Executor；Service 以登入者作為 Executor。
- Core 將 `tblPMWODetail` 中指定 WONo／WOItemNo 且目前 `WOStatus=2` 的列更新為 `WOStatus=3`、寫入 `FinishedDate` 與 `Executor`；只有收到非空 `ExecuteDesc` 才更新說明。每筆預期影響 1 列。
- `WOType=0` 時，另將相同 SerialNo 且 `ExecuteState=3` 的 `tblPMEQPMaintenancePlanLog` 更新為 `ExecuteState=4` 並寫 `WOFinishedDate`，每筆預期影響 1 列。REQ Order 不更新 PM PlanLog。
- 回報後 Core 檢查該工單是否仍有 `WOStatus<>3` 的明細。若已全部完成，將工單主檔／全部明細複製至 `tblPMWOBasis_His`／`tblPMWODetail_His`，再刪除活動主檔／明細；PM PlanLog 留在歷史執行狀態 4。其他未完成項目存在時，工單留在活動表。
- 舊 Core 沒有更新 DataStamp。回報更新、完成度檢查、歷史搬移與 EQP Service 是分開的執行階段；最後一項歷史搬移或設備狀態更新失敗時可能留下部分完成。舊程式亦以字串組 SQL，讀取沒有有界分頁。

## 家用端 API、schema 與 CREATE-only handoff

- 可沿用 `GET /api/pm/work-orders` 與 `GET /api/pm/work-orders/{woNo}/items` 的狀態過濾、有界分頁查詢。建議 `POST /api/pm/work-orders/{woNo}/finish` 接受 WOItemNo 清單、FinishedDate、ExecuteDesc 及冪等鍵；Executor 從已驗證的登入身分取得，不採信前端欄位。
- 交易內重新確認父單 `IssueState=2`、每筆明細屬於 WONo 且 `WOStatus=2`、FinishedDate 不早於 ReleaseDate；PM 工單還要驗證該明細 SerialNo 對應的 PlanLog 為 `ExecuteState=3`。條件式更新明細／PlanLog 並核對影響筆數，再判斷全部完成後將主檔與明細原子搬入 History 並刪除活動列。重複請求須回傳可辨識結果而非二次更新。
- EQP 狀態設定與禁止轉換應由伺服器重讀；將完成事件與狀態更新納入同一交易邊界，或以 outbox／可重試命令維持狀態一致。Chamber Manage 開啟時明確更新子設備，處理 EQP 更新失敗，不可讓成功回報被誤認為完整成功。
- 直接表：`tblPMWOBasis`、`tblPMWODetail`、`tblPMWOBasis_His`、`tblPMWODetail_His`；PM 工單另更新 `tblPMEQPMaintenancePlanLog`。設備狀態依賴 EQP 主檔／狀態控制與 Chamber 設定。
- repo 沒有上述直接表可核實的 Oracle source DDL／CREATE-only SQL；桌機受保護 Oracle profile 不存在，筆電 attachment 路徑在本機不存在，因此本次未連 MESTEST。欄位型別、PK/FK、索引、nullable/default、trigger 與時間精度待家用端依 live schema 及安全取得的 Oracle metadata 核對；不依欄位名稱猜 CREATE。
- 家用端負責 live PostgreSQL schema、migration、正式 API、部署及驗收；公司端未連 YMES PostgreSQL、未設定 `ConnectionStrings__YMes`、未部署，也未執行 build／test／browser。
