## WinForms 主畫面

- 主清單為 1008×591。預設 IssueState=0，四個狀態為未簽核 0、簽核中 1、已簽核 2、不使用 -1。WinForms 一次載入主檔，再於用戶端依狀態篩選，依 RuleNo 排序。
- 查詢欄只使用 RuleNo；Core 條件為 `RuleNo LIKE '<search>'`，`%` 和 `_` 為萬用字元。
- 主 Grid 顯示 RuleNo、ComponentCollect（0=No、1=Yes）、Creator、CreateDate、Reviser、ReviseDate。IssueState 不顯示；主表沒有 DataStamp。
- 選取/啟用主檔列時載入該 RuleNo 的明細 Grid，依 Action、ReasonType 排序。明細欄位為 Action、ReasonType、ReasonLevel、RejectNum、Rate、RuleType；自訂 AQL 開啟時再顯示 ChangeAQL；明細稽核欄位存在於 dataset，Grid layout 預設隱藏。
- 主畫面右側垂直按鈕：Add、Edit、DEL、Copy、Approve；底部 Close。沒有 Import/Download/Print。
- RuleNo 主鍵最多 20 字元，離開欄位轉大寫。新增/複製需使用不同 RuleNo；修改時唯讀。

## 新增/修改/複製視窗

- 定義視窗分成主檔、明細與明細編輯三區。主檔欄位為 RuleNo、ComponentCollect 是/否；明細 Grid 可選多列刪除，並透過編輯區新增或修改目前規則。
- 一筆明細的唯一鍵為 `(RuleNo, Action, ReasonType, ReasonLevel)`。編輯明細時 Action、ReasonType、ReasonLevel 三個鍵欄位唯讀。新增若已存在相同三鍵，WinForms 會覆寫該列的 RejectNum、Rate、RuleType、ChangeAQL，不新增重複列。
- Action 選項依 `TBLQCATTRULEDETAIL.ACTION` ValueList；來源舊轉換註解列出 0 Warning、1 Wait、2 Hold、3 Alert。正式值與翻譯應由 YMES options API 供應。
- ReasonType 選項取 `GetValueList("TBLQCATTRULEBASIS","REASONTYPE",True)`；舊 VB 註解僅列出 0 Scrap、1 Defect，不是可信的完整正式選項。
- ReasonLevel 為 -1 到 9 的整數，-1 為舊系統 sentinel。
- 規則類型 RuleType：0 Number（RejectNum 必填、數值至少 1 且為整數）；1 Rate（Rate 必填、數值大於 0，資料欄位為 varchar(10)）；2 AQL Reject Number（RejectNum/Rate 清空，ChangeAQL 下拉可空白；WinForms 沒有對 ChangeAQL 做必填驗證）。RejectNum Oracle 欄位為 NUMBER(14,4)，但 WinForms 額外限制整數且大於等於 1。Rate 只驗數值正數，長度最終受資料庫 varchar(10) 限制。
- ChangeAQL 只有 `wsSYS.LoadParameter(ParameterType=SysInfo,ParameterNo=UserDefineAQL,ParameterValue=1)` 時顯示；候選為 `TBLQCAQL` 中 `AQLType IS NOT NULL` 的 distinct AQL。未開啟時隱藏選項與 Grid 欄位。
- 新增/複製建立 IssueState=0、Creator/Date；修改套用共用 `ExeIssueControl`，RuleNo 唯讀，狀態 1 唯讀，狀態 0 可編輯，其餘狀態僅 Issue Control 的 EditFlag 控制項可編輯，缺設定應 fail closed。
- Confirm 關閉視窗並保存；Apply 保存後視窗保持開啟；Close 時如明細有未保存變更，舊程式會提示是否保存。

## 查詢、資料寫入與狀態行為

- `LoadQCAttRuleBasis` 載入主表，`LoadQCAttRuleDetail(RuleNo)` 載入所選主檔明細。IssueState 篩選在前端；空值 IssueState 不符合四個狀態篩選。
- Add/Copy 呼叫 `AddQCAttRuleData`，整筆主檔和明細一次寫入；Edit 呼叫 `UpdQCAttRuleData`，以 RuleNo 刪除既有主/明細再重建。Web API 應以單一交易實作 aggregate 保存，避免刪除後部分失敗；舊 Oracle 無 FK。
- 舊 WinForms 的 Def 表單會設定 Reviser/ReviseDate，但 SOAP payload 不傳這兩欄；實際 `clsQCBasis.UpdQCAttRuleData` 刪除重建主/明細時只帶回 Creator/CreateDate，沒有寫入 Reviser/ReviseDate，明細 audit 也未傳。規格記錄此舊行為；YMES API 若需維持既有相容性，應先不宣稱舊端有修改 audit。可由後端另行決定是否在 Web 寫入時補 audit，並記錄為 YMES 明確差異。
- 主表 IssueState 是 nullable、DEFAULT 0；無 DataStamp，來源 API/Core 也未使用樂觀鎖。YMES 若新增併發保護屬 YMES 擴充，需另記，不可假稱 Oracle 已有 DataStamp。
- Delete 多選逐筆執行，state 0/-1/2 均實體刪主檔與明細；state 1 不允許。首筆失敗停止，之前成功不回復。API 刪除時應同交易刪 detail 與 basis。
- Approve 只接受 state 0；若目前啟用主檔明細為 0 筆，UI 不呼叫核准。依 Issue Job Map `QCITEM_A RULE DATA`：無 Job/Detail 時 0→2；有簽核 Detail 時建立 Issue，轉 1 並通知第一簽核群組，後續核准 2、退回 0。回傳真實狀態；不可假設一律立即 Active。
- 多選 Approve 逐筆執行，第一筆失敗停止並保留之前已成功項目。舊 UI 只先檢查目前明細 Grid 非空，API 應對每個待核准 RuleNo 再驗明細，拒絕沒有規則的空主檔。

## Vue DEV 頁與 API handoff

DEV 頁以標明 DEMO 的 localStorage 假資料呈現主檔/明細雙 Grid、四個狀態、RuleNo LIKE 查詢、主檔新增/修改/複製/刪除/核准、整筆明細編輯、ComponentCollect、三種 RuleType、AQL 選項開關、Issue Control 與多筆首錯停止。Production 不得讀 localStorage 假資料。

建議登入並以 FunctionKey `QC107` 授權所有 endpoint，SQL 參數化：

- `GET /api/qc/attribute-rule-bases?searchFieldName=RuleNo&searchFieldValue=`：回四個狀態的主檔、audit、IssueState、editableFields。只接受 RuleNo LIKE 條件。
- `GET /api/qc/attribute-rule-bases/{ruleNo}/details`：回 `(Action,ReasonType,ReasonLevel)` 明細與規則值、audit；父子表沒有 FK，API 要驗父檔與欄位型別。
- `GET /api/qc/attribute-rule-bases/options/actions`、`.../reason-types`：依 MES ValueList 等價設定回 `{value,label}`；Action 可沿用共用 ValueList；ReasonType 不使用舊註解寫死。
- `GET /api/qc/attribute-rule-bases/options/aql`：先讀 SysInfo/UserDefineAQL；關閉則回功能停用或空清單，開啟才從 YMES `tblqcaql` 查 distinct AQL 且 AQLType 非空。
- `POST /api/qc/attribute-rule-bases` 與 `PUT /api/qc/attribute-rule-bases/{ruleNo}?issueState=`：Aggregate body `{ ruleNo, componentCollect, issueState?, details:[{ action, reasonType, reasonLevel, rejectNum, rate, ruleType, changeAql }] }`。POST 設 state0 與登入者/伺服器時間；PUT RuleNo 唯讀並檢查 Issue Control。兩者單一交易保存 basis + details，校驗唯一鍵及規則種類的欄位互斥/必填。
- PUT 欄位白名單含 ComponentCollect、ruleDetails；state0 可編輯、state1 唯讀、state2/-1 依 Issue Control EditFlag；缺少設定則唯讀。沒有 Oracle DataStamp；如果 YMES 使用 row version，需明示屬 YMES 擴充。
- `DELETE /api/qc/attribute-rule-bases/{ruleNo}?issueState=`：僅 state 0/-1/2；交易內刪 detail 與 basis。state1 回 409。
- `POST /api/qc/attribute-rule-bases/{ruleNo}/approve?issueState=0`：至少一筆明細；按 Issue Job Map 建 Issue 或直接核准，回實際 IssueState。通知與 Issue 整合使用 YMES 共用流程服務。
- 多選刪除/核准 UI 逐筆 API 呼叫、第一個錯誤停止並回報先前完成筆數。資料稽核差異依本規格上節處理。

### 已實作 API 與併發保護

- 全端點明確 `[Authorize]`；本批依使用者目前方向先提供登入後操作，不因角色／FunctionKey ACL 尚未整合而停工。程式不接受前端指定 Creator/CreateDate/Reviser/ReviseDate 或任意寫入 IssueState，操作帳號取登入 principal；主／明細寫入參數化，Controller 記錄操作、帳號、RuleNo、實際狀態與明細數，資料庫例外只回一般錯誤。
- `GET /api/qc/attribute-rule-bases` 回主檔陣列，包含 `editableFields` 與 `version`。RuleNo 以參數化 `ILIKE` 比對，保留 `%`／`_` wildcard，不額外加前後 `%`；反斜線為一般字元。空查詢回全部狀態（包含 NULL）；UI 僅顯示四種明確狀態。只允許 RuleNo 搜尋，最長 50 字元。
- 新增 `GET /api/qc/attribute-rule-bases/{ruleNo}` 回 `{ basis, details }`，主／明細來自同一 repeatable-read snapshot；既有 `GET /{ruleNo}/details` 仍回明細陣列。Vue 選取主檔後使用 aggregate GET，讓顯示明細與主檔版本一致。只有該 RuleNo 的完整 aggregate 成功載入、版本與目前作用列一致時才啟用修改／複製；查詢開始、切列或載入失敗會清除載入成功標記。不能以清單中的有效版本配上載入失敗後的空明細開啟修改，避免誤刪整組明細。主清單及 aggregate GET 的快照版本均涵蓋所有主／明細與 audit 值，NULL 不等於 0。
- Oracle 沒有 DataStamp。本 API 的 `version` 是伺服器對真實 aggregate snapshot 以 SHA-256 計算的不透明字串，屬 YMES 併發保護擴充，不是偽造 Oracle 欄位或由瀏覽器推算的版本。PUT、DELETE、Approve 都必須傳 `?issueState=&version=`；省略／格式錯誤回 400，版本或狀態不符回 409。來源 NULL 狀態必須明確傳 `issueState=`，不能省略；版本永不可空。
- 所有異動統一先鎖主列 `FOR UPDATE`，再讀取與核對 aggregate snapshot，接著處理明細／核准；新增先插入主檔，再新增明細。沒有獨立明細寫入路由，避免明細更新與核准使用相反鎖順序。主／明細 aggregate 新增、替換或刪除都在同一交易；任何失敗完整回滾本筆。其他子表 API 若引用法則，需在指派時先取得相同主列 `FOR SHARE`，與實體刪除協作。
- POST／PUT body 為 `{ ruleNo, componentCollect, details:[{ action, reasonType, reasonLevel, rejectNum, rate, ruleType, changeAql }] }`。details 必須明確存在，無明細傳 `[]`；單筆 aggregate 上限 1000 筆明細。RuleNo 必填／最多 20 字／大寫；ComponentCollect 僅 0/1；明細複合鍵唯一、ReasonLevel -1..9。真正新增或修改的明細要求 RuleType 0/1/2：Number RejectNum 必填且為 1..9,999,999,999 整數；Rate 最長 10 字且為正的有限數字，保留原文字，不轉成資料庫 numeric。新增／修改明細的非作用欄位正規化為 RejectNum=0、Rate/ChangeAQL=NULL；AQL 模式 ChangeAQL 可空，有值最多 30 字且須存在於正式 AQL 選項。此正規化不套用到原樣保留的舊列。
- POST 固定狀態 0。PUT 目前只有狀態 0 的 `componentCollect`、`ruleDetails` 可編輯；1、2、-1、NULL 皆唯讀，直到取得原生 Issue Control EditFlag 設定。取得主列鎖並確認狀態／版本後，先用 raw request DTO 與伺服器舊明細逐欄精確辨識未變更列，再正規化／驗證真正新增或修改的列。未變更列的 RejectNum=NULL、RuleType=NULL、Rate/ChangeAQL 及建立／修訂 audit 原樣保留，不會先把 NULL 改成 0 或 Number 而誤判成變更，也不會因此要求尚未交付的 ValueList。整組明細不變時不刪除重寫；若其他列確實變更而需替換整組，保留列仍依原 NULL/audit 值寫回。既有明細完全不變時可修改 ComponentCollect；新增或變更明細仍須正式 ValueList 驗證。明細刪除不需要猜測被刪列的選項名稱。
- PUT 採更新主列、同交易替換明細，保留主表 Creator/CreateDate，補上目前登入者與伺服器時間的 Reviser/ReviseDate。明細保留既有複合鍵列的建立 audit，修改列補修訂 audit；未變更列維持原 audit，新增列由服務建立 audit。此 audit 補寫是 YMES 明確改善，並非宣稱舊 SOAP/Core 已傳入或維護修訂資料。
- DELETE 對 0／2／-1 均實體刪除明細和主檔，1／NULL 拒絕，沒有套用其他模組的 2→-1。刪除前在取得主列鎖後檢查已部署的 QC201 `tblqcitemforattributes.ruleno` 及 QC203 `tblspcqattrulemapdetail.lotruleno/comruleno`；被引用回 409。此檢查是 YMES 避免懸空引用的改善，沒有增加來源不存在的 FK。
- Approve 僅 0 且每個 RuleNo 至少一筆真實明細。缺少 Issue/Job 表時直接 0→2，寫修訂 audit 並回實際版本；發現 Issue/Job 表存在時回 503、保持資料不變，等待 `QCITEM_A RULE DATA` 共用簽核，不假造 Issue、通知或退回成功。
- 主明細、Issue/Job 與引用表的存在性以 `pg_catalog.pg_namespace/pg_class` 判定，不用會按登入角色權限過濾的 `information_schema.tables`。表存在但應用無權讀取時仍拒絕／回 503，不誤當沒有簽核設定而直接核准，也不誤當沒有引用而刪除。
- Create／Update／Approve／Delete 成功都回 `{ basis, details }`；Delete 回刪除前快照。Vue 保存後立即保留真實回應與版本再重載清單；新增／複製按套用後轉修改模式，防止重複 POST。表單採 JSON DTO 複製，避免 structuredClone Vue proxy 失敗；使用共用確認對話框，多筆操作第一錯停止並重載，保留先前完成筆數。明細編輯的三個鍵欄位全部固定，唯讀狀態不開放修改。

### 正式 ValueList／SysInfo 待公司端交付的精確項目

公司端後續交付應包含以下 metadata，不能只交舊程式註解或 DEV 假選項：

1. `TBLQCATTRULEDETAIL.ACTION` 的實際 ValueList 儲存值、原始標籤／語系顯示字串、排序及有效性規則；指出這些設定實際來自哪張表／欄位／查詢或 XML resource，附可核對的來源碼／結構。
2. `GetValueList("TBLQCATTRULEBASIS","REASONTYPE",True)` 的完整有效儲存值與標籤，包含第三參數 True 的過濾語意與排序，及其實際 metadata 來源／schema。不要假設只有 0 Scrap、1 Defect，也不要直接重用 QC201 ReasonType，除非來源證明相同。
3. `wsSYS.LoadParameter(ParameterType=SysInfo,ParameterNo=UserDefineAQL,ParameterValue=1)` 的實際參數儲存 schema、唯一鍵、NULL／缺值語意，以及 YMES 要使用的已核實設定值；只能查授權的系統設定／metadata，不匯入 TBLQCAQL 業務資料列。
4. 若要開放 2／-1 的修改，交付 `QCITEM_A RULE DATA` 的 Issue Control EditFlag 正式欄位白名單及來源 schema；否則這些狀態維持唯讀。簽核 Job／Detail 仍由共用服務整合。

在正式 metadata 表與共用 provider 尚未交付前，本 API 提供等價的部署設定轉接，不寫死業務值：`QC107:ValueLists:Actions`、`QC107:ValueLists:ReasonTypes` 為依來源順序排列的 `{Value,Label}` 設定陣列；儲存值必須可放入來源 numeric(1,0)、不得重複，標籤不可空。`QC107:UserDefineAql` 必須明確為字串 `0` 或 `1`。只有 root 依上述已核實來源才能填入設定；本次沒有提供任何正式值、沒有將 DEMO 升格為正式資料。之後可用真正 provider 取代轉接而維持 endpoint 契約。

- `options/actions`／`options/reason-types` 回 `{value,label}[]`；設定缺少或無效回 503。只阻擋需要驗證新／變更選項的操作；查詢、實體刪除、無 Job 核准及保留既有明細的 ComponentCollect 更新不依賴這些選項名稱。
- `options/aql` 先確認已核實的 UserDefineAql。缺值回 503；0 回 `{enabled:false,items:[]}`，不查 AQL 表；1 才查共用 `tblqcaql` 中 AQLType 非 NULL 的 distinct AQL，回 `{enabled:true,items:[...]}`。AQL 模式新增／修改也以相同開關驗證，未啟用回 422，尚未核實回 503；ChangeAQL 空值在已啟用時合法。
