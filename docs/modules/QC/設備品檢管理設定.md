## WinForms 畫面與操作

- 主頁預設在 IssueState=0「未凍結」。狀態篩選為 0 未凍結、1 簽核中、2 已核准、-1 未使用；查詢條件有 OPNo、EquipmentNo、InspType。
- 主頁為主檔與明細兩個 Grid。主 Grid 顯示 OPNo、EquipmentNo、EQPDataType、InspType、週別、開始時間、PeriodMin、EquipmentState、LotCount、MailGroupNo、CCMailGroupNo、建立/修改人與日期；明細 Grid 顯示 QCItemNo、QCItemName、QCItemType。選列以 OPNo + EquipmentNo + InspType 載入明細；明細設定會在同一排程類型的週別/時間間共用。
- 主頁操作：新增、修改、刪除、複製、核准、關閉。修改僅允許 IssueState=0 且單筆；複製以目前選取列和明細為來源，產生另一筆未凍結設定。核准可批次選取，只有狀態 0 送出。
- 編輯表單的 OPNo 可用 `*` 表示全部作業站，否則必須存在。設備範圍必須擇一：單一 EquipmentNo（EQPDataType=0）或 EquipmentType（EQPDataType=1）；單一設備必須存在。編輯時 OP、設備範圍及檢查類型鎖定。
- 檢查類型代碼：0 首件檢查、1 人員檢查、2 班次檢查、3 配件檢查、4 每日檢查、5 定期檢查、6 設備狀態檢查、7 連續批量、8 每週檢查。以 MES ValueList 顯示名稱為正式選項來源；API options 應回傳 ValueList/代碼，不要以 DEV 標籤覆蓋 MES 翻譯。
- 排程欄位依類型顯示：4 每日時間；5 正整數分鐘；6 設備狀態；7 非負整數批量；8 週別及時間。每日/每週可選時間為 00:00–23:30、每 30 分鐘一格，初始 08:00；非週檢查的 InspWeek 存 -1，非日/週檢查的 InspStartTime 存 `N/A`。
- 明細項目類型 `QCItemType`：0 計數品管項目、1 計量品管項目、2 一般計量品管項目群組、3 計數順序群組。表單按類型提供可選/已選項目移動；至少一筆，且所有已選項目的 LotIsValid 必須非 0。
- CC Mail Group 有值時，Mail Group 必填。建立/修改人與日期由表單稽核欄位顯示，Web/API 必須由登入身份和伺服器時間產生，不採信前端送入的稽核值。

## 儲存、狀態與舊程式行為

- `AddQCInspection` 以主檔和全部品管明細一次交易寫入；明細為空即拒絕。新增狀態為 0。`EditQCInspection` 同樣要求至少一筆明細，更新主檔並以 `(OPNO,EQUIPMENTNO,INSPTYPE)` 刪除後重建全組明細。
- 核准使用 Issue Job `QC INSPECTION`。無 Job 時直接把狀態改 2；有 Job 時建立簽核流程、狀態先改 1，簽核通過為 2、退回為 0。核准需保存 Reviser/ReviseDate，並以 DataStamp 防止舊資料覆寫。
- 刪除狀態 0/-1 為硬刪，狀態 2 改為 -1，狀態 1 拒絕。主檔 PK 為 `(OPNO,EQUIPMENTNO,INSPTYPE,INSPWEEK,INSPSTARTTIME)`；硬刪同交易刪主檔與明細。
- **舊程式的共用明細刪除範圍：** `DelQCInspection` 依 OPNo、EquipmentNo、InspType 刪所有明細，沒有以 InspWeek/StartTime 區分。刪除某一個排程時會同時刪掉其他排程共用的明細；編輯則會替換該組共用明細。API 應忠實採用共用鍵並揭露此行為，不可誤以為明細屬於單一週別。
- **核准 SQL 的舊程式瑕疵：** 有 Issue Job 時產生的通過/退回 SQL 將 `InspWeek` 條件誤寫成 `InspType`。Web API 應以主鍵中的正確 InspWeek 和完整複合鍵更新狀態，避免照搬此錯誤造成誤更新；家用端要在簽核交易與 Issue callback 都確認完整 key。
- `EQPDATATYPE` 在 Oracle 是 `VARCHAR2(255)`，程式以 0/1 表示 EquipmentNo/EquipmentType。DataStamp 在 Oracle nullable 且 default 0；API 對 update/delete/approve 使用伺服器端 CAS，避免把空值當成通用通行條件。

## Oracle 資料表與 CREATE SQL

本次使用 Windows PowerShell 5.1 + Oracle.ManagedDataAccess，透過本機受保護連線直接唯讀查 MESTEST `DBMS_METADATA` 與資料字典；未讀業務資料列、未在 Oracle 執行 DDL，也未把連線秘密寫入文件。

| MESTEST Oracle 表 | Oracle 原始 DDL | PostgreSQL CREATE-only 參考 | 主鍵 |
| --- | --- | --- | --- |
| `TBLQCINSPECTIONBASIS` | `database/reference/mestest_qc217_tblqcinspectionbasis_source_ddl.sql` | `database/reference/mestest_qc217_inspection_create.sql` | OPNO, EQUIPMENTNO, INSPTYPE, INSPWEEK, INSPSTARTTIME |
| `TBLQCINSPECTIONDETAIL` | `database/reference/mestest_qc217_tblqcinspectiondetail_source_ddl.sql` | 同上 | OPNO, EQUIPMENTNO, INSPTYPE, QCITEMNO |

兩表均無 FK、無 PK 以外索引。主表 `INSPSTARTTIME` 為 `VARCHAR2(20) DEFAULT 'N/A' NOT NULL`，`INSPWEEK` 為 `NUMBER(2,0) DEFAULT -1 NOT NULL`；`ISSUESTATE` 為 `NUMBER(1,0) DEFAULT 0 NOT NULL`。明細主鍵不含週別/開始時間，是上述共用明細行為的結構依據。

PostgreSQL 檔案是空結構參考，不是 migration，也不可在 MESTEST Oracle 執行。家用端先比對 YMES live schema、migrations 和共用 ValueList/Equipment/OP/QC API；只為實際缺欄位新增 forward migration，不能以 CREATE 參考覆蓋既有表。

## API 契約（家用端待建）

所有端點需登入保護並要求 FunctionKey `QC217`。建議介面如下；新增/修改 payload 含主檔排程值與 `details: [{ qcItemNo, qcItemType }]`，稽核欄位由 API 產生。

| 方法 | 路徑 | 用途 |
| --- | --- | --- |
| GET | `/api/qc/inspections?issueState=&opNo=&equipmentNo=&inspType=` | 主檔清單；查詢值採參數化條件 |
| GET | `/api/qc/inspections/options` | 已核准 OP、設備、設備類型、EQP 狀態、週別/檢查型別 ValueList、Mail Group、可用 QC Items（含 LotIsValid） |
| GET | `/api/qc/inspections/{opNo}/{equipmentNo}/{inspType}/details` | 共用主鍵下的明細清單 |
| POST | `/api/qc/inspections` | 新增主檔與明細的原子交易；強制狀態 0 |
| PUT | `/api/qc/inspections/{opNo}/{equipmentNo}/{inspType}/{inspWeek}/{inspStartTime}` | 修改未凍結設定與共用明細；主鍵不變欄位由路徑指定，DataStamp CAS |
| DELETE | `/api/qc/inspections/{opNo}/{equipmentNo}/{inspType}/{inspWeek}/{inspStartTime}` | 0/-1 硬刪，2 設 -1，1 拒絕；回報因共用鍵而清除的明細範圍 |
| POST | `/api/qc/inspections/{opNo}/{equipmentNo}/{inspType}/{inspWeek}/{inspStartTime}/approval` | 以 Issue Job 送簽/直接核准；DataStamp CAS，callback 使用完整 PK |

API 寫入前需重新驗證 OPNo（允許 `*`）、設備或設備類型、ValueList、週期欄位範圍、Mail Group 關係、至少一筆明細及每一 QC Item 的 LotIsValid。DB query 必須參數化；批次核准/刪除逐筆回傳結果，避免一筆錯誤掩蓋其餘結果。API 尚未建置前，Production 不應回退使用 DEV 假資料。
