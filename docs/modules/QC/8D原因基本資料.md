# QC111 8D 原因基本資料

## 功能識別

- 第一層：品質資料（`QC`，ModuleOrder 5）
- 第二層：基本資料
- 第三層：8D 原因基本資料
- FunctionNo：`8D REASON BASIS`
- FunctionKey：`QC111`
- WinForms：`frmReasonBasis_8D`、`frmReasonSubTypeDef_8D`、`frmReasonBasisDef_8D`
- WinForms 專案：`STD/MESWin/QC/QC_ReasonBasis_8D`
- Service/Core：`wsQC`、`clsQCBasis`
- Vue DEV 路徑：`/YMES/QC/8DReasonBasis`
- 頁面為雙層 Grid：上方原因子類別，下方依選取子類別載入原因明細。公司端以明確標示的 localStorage 假資料作互動；正式 API 尚待家用端實作。

## WinForms 畫面與操作

主表單 ClientSize 為 1008×591，沿用 `frmBasisTemplat` 的查詢條件與 IssueState 篩選。上方 GroupBox「8D ReasonSubType」約在 `(12,53)`、尺寸 `984×233`；下方「8D ReasonBasis」約在 `(12,292)`、尺寸 `984×287`。兩組 Grid 右側各有縱向動作按鈕，底部包含 Close。上方提供新增、修改、刪除、複製、核准；下方提供新增、修改、刪除、複製。

主畫面啟動先查全部原因子類別，預設顯示未簽核，查詢欄位為 `ReasonSubType`。四種狀態由 WinForms 在已載入資料上篩選：0 未簽核、1 簽核中、2 已簽核、-1 不使用。原因子類別依 `ReasonSubType` 排序。切換狀態時清除下方原因明細，選取上方列後才以該 `ReasonSubType` 精確載入原因明細。

### 原因子類別 Grid 與表單

Grid 欄位依序包括 ReasonType、ReasonSubType、ReasonSubTypeName、Description、Creator/CreateDate、Reviser/ReviseDate 及 IssueState；DataStamp 供操作使用但不作可見欄。表單有新增、修改、複製模式；修改時 `ReasonSubType` 唯讀，新增狀態固定為 0。ReasonSubType 與 ReasonSubTypeName 離開欄位時轉大寫，二者為必填；ReasonType 必填。欄位長度依 Oracle DDL 為 ReasonSubType 50、ReasonSubTypeName 100、Description 255。修改只可對 IssueState=0 的列進行。

WinForms 透過 `ValueListProvider.GetValueList("TBLQCREASONBASIS_8D", "REASONTYPE", True)` 讀取 ReasonType；公司端直接唯讀查 MESTEST.TBLSYSVALUELIST 並核對繁中資源，確認 1=Men（人員）、2=Machine_8D（設備）、3=Material（物料）、4=Method（方法）、5=Environment（環境）。Vue DEV 選項使用相同代碼/中文標籤；正式 API 仍須從 YMES 受控字典回傳，不以這份假資料作正式資料來源。

### 原因明細 Grid 與表單

下方欄位包括 ReasonNo、ReasonName、ReasonLevel、ReasonType、Description、Creator/CreateDate、Reviser/ReviseDate；ReasonSubType 作為父關聯欄位使用，不在一般 Grid 顯示，DataStamp 隱藏。只有選取的父子類別 IssueState=0 時，才允許新增、修改、複製或刪除明細。表單的 ReasonType 與 ReasonSubType 由父列帶入且唯讀；修改時 ReasonNo 唯讀。ReasonNo 離開欄位轉大寫。ReasonNo、ReasonName、ReasonType 必填，ReasonLevel 必須為 0–9 整數，Description 最長 255。ReasonNo/ReasonName 最長 55/100。

新增與複製建立新 key；修改以 ReasonNo 定位。明細沒有 IssueState；明細刪除為實體刪除。多選刪除逐筆執行，遇到第一筆失敗即停止，之前已完成的刪除不回復。

### 狀態、核准與刪除

| IssueState | 顯示 | 子類別修改 | 子類別刪除 | 明細維護 |
| ---: | --- | --- | --- | --- |
| 0 | 未簽核 | 允許 | 實體刪除 | 允許 |
| 1 | 簽核中 | 不允許 | 不允許 | 不允許 |
| 2 | 已簽核 | 不允許 | 改為 -1 不使用 | 不允許 |
| -1 | 不使用 | 不允許 | 實體刪除 | 不允許 |

核准只接受 IssueState=0。Service 查詢 Issue Job Map 的 `ReasonSubType BASIS`：沒有 Job 或 Job 沒有 Detail 時直接轉為 2；有簽核明細時建立 Issue 流程、狀態改為 1，並通知第一簽核群組。Issue 核准後轉 2，退回回復 0。此簽核流程需要家用 API 後端串接 Issue/Job；DEV 假資料只模擬沒有簽核 Job 的直接核准分支。

子類別多選刪除逐筆處理：0/-1 由 Core 實體刪除；2 呼叫狀態更新改為 -1；1 拒絕。Reason SubType 表單的 Apply 保持視窗開啟，Confirm 儲存後關閉。新增後的 key 及修改後的 row 會回到主畫面重新查詢並定位。

## Oracle 資料結構

來源為 `MESTEST.TBLQCREASONSUBTYPE_8D` 與 `MESTEST.TBLQCREASONBASIS_8D`。DDL 是公司端使用既有受保護連線，以 Windows PowerShell 5.1、Oracle.ManagedDataAccess 執行 `DBMS_METADATA.GET_DDL` 和 `ALL_TAB_COLUMNS/ALL_CONSTRAINTS/ALL_INDEXES` 唯讀查得；沒有讀 MES 業務列，也沒有在 Oracle 執行 DDL。

| `TBLQCREASONSUBTYPE_8D` | ReasonType | NUMBER(1,0) | NOT NULL |  |

|  | ReasonSubTypeName | VARCHAR2(100) | NULL |  |
|  | Description | VARCHAR2(255) | NULL |  |
|  | IssueState | NUMBER(1,0) | NOT NULL DEFAULT 0 |  |

|  | DataStamp | NUMBER(11,0) | NULL DEFAULT 0 |  |
|  | Reviser / ReviseDate | VARCHAR2(10) / DATE | NULL |  |

|  | ReasonType | VARCHAR2(50) | NOT NULL |  |
|  | ReasonSubType | VARCHAR2(50) | NOT NULL |  |

兩表各只有一個 PK unique index，沒有其他索引、FK 或 Oracle cascade。明細沒有 FK 約束，因此子類別被實體刪除時，舊 Core 不會連帶刪除原因明細；舊 WinForms 的子類別刪除流程也在組合刪除 request 前呼叫了一次明細刪除 service，該次使用舊 InXml。Vue 依可確認的 Core 行為保留子類別與明細分開刪除，API 不得自行假定 cascade。若要修正歷史 orphan 行為，須由家用端與使用者另行確認。

## YMES 前端與 API 契約

Vue 元件：`web/src/components/Qc8DReasonBasisMaster.vue`；Fallback 選單 QC → 基本資料 → 8D 原因基本資料。DEV localStorage key 為 `ymes-dev-mock:qc-8d-reason-basis:v1`。正式環境不使用 localStorage；API 未建立或未設定 Base URL 時顯示錯誤，不回報假成功。

建議端點（供家用端落實，命名可依既有 controller 慣例調整，但需同步 DTO）：

- `GET /api/qc/8d-reason-subtypes?search=`：依 ReasonSubType 查詢；回完整欄位，IssueState 由 UI 對載入結果篩選，或回傳指定 state 的等價結果。
- `POST /api/qc/8d-reason-subtypes`：新增，伺服器設定 Creator/CreateDate、IssueState=0、DataStamp=0；ReasonSubType 唯一衝突回 409。
- `PUT /api/qc/8d-reason-subtypes/{reasonSubType}?dataStamp=`：只允許 IssueState=0；更新 ReasonType/ReasonSubTypeName/Description、Reviser/ReviseDate/DataStamp，使用 DataStamp compare-and-swap。來源 DataStamp nullable，需支援 NULL 與 0 的明確 CAS。
- `DELETE /api/qc/8d-reason-subtypes/{reasonSubType}?issueState=&dataStamp=`：按來源狀態執行：0/-1 實體刪除子類別、2 設 -1、1 拒絕；逐筆操作及部分成功回報要清楚，不應默默 cascade 明細。
- `POST /api/qc/8d-reason-subtypes/{reasonSubType}/approve`：驗證傳入 IssueState=0/DataStamp；依 Issue Job Map `ReasonSubType BASIS` 建立簽核流程或直接轉 2；回傳實際 IssueState/DataStamp，通知第一簽核群組，支援退回轉回 0。
- `GET /api/qc/8d-reasons?reasonSubType=`：以 ReasonSubType 精確查明細。
- `POST /api/qc/8d-reasons`：建立明細；API 檢查父子類別存在且 IssueState=0，ReasonType 由父類別取得，不接受不一致的前端值。
- `PUT /api/qc/8d-reasons/{reasonNo}?dataStamp=`、`DELETE /api/qc/8d-reasons/{reasonNo}`：以 ReasonNo 操作；變更前檢查所屬子類別仍為 IssueState=0。更新 Reviser/ReviseDate/DataStamp；刪除實體列。明細 ReasonType 在來源為 VARCHAR2(50)，UI 舊程式以 numeric code 寫入，PG 欄位需保留 varchar 語意。

所有端點須驗證登入與 FunctionKey `QC111` 權限，使用參數化 SQL。多筆操作遵照舊 WinForms 逐筆處理、遇錯停止；不要加入來源不存在的 FK/cascade。來源沒有審核版號欄位，API 仍需用 nullable DataStamp CAS 防止過期更新。

## 待核對差異

- ReasonType 代碼與繁中翻譯已由 Oracle TBLSYSVALUELIST 和 mesresource.zh-cht.resources 核實；正式環境仍由 YMES options/API 提供字典。
- ReasonType 在子類別表是 numeric，在明細表卻是 varchar(50)；保持兩表來源型別，明細寫入來源代碼的字串形式。
- 明細的 ReasonType/ReasonSubType 在新增時帶入父列；修改父列 ReasonType 時舊 Core 不同步更新既有明細。
- 子類別刪除不 cascade，可能留下不再能從此畫面查到的明細記錄；資料結構未定義 FK。
- 未執行 build、test 或瀏覽器驗收。Production API/schema 未部署前，本頁只有 DEV 模擬互動。
