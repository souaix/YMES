# QC407 最後處理群組

## 功能識別

- 第一層：品質資料（`QC`）
- 第二層：異常設定
- 第三層：最後處理群組
- FunctionNo：`FINAL GROUP`
- FunctionKey：`QC407`
- WinForms：`frmFinalGroup`、`frmFinalGroupDef`
- WinForms 專案：`STD/MESWin/QC/QC_FinalGroup`
- Service/Core：`wsQC.LoadFinalGroup*`、`wsQC.*FinalGroup`、`clsQCBasis`、`clsBasis_UPD`
- 主表：`MESTEST.TBLQCFINALGROUP`
- Vue DEV 路徑：`/YMES/QC/FinalGroup`

## WinForms 主畫面

`frmFinalGroup` ClientSize 為 `1008×591`，Grid 在 `(12,53)`、尺寸 `890×532`；右側有新增、修改、刪除、複製、核准，右下角關閉。查詢狀態是未簽核 0、簽核中 1、已簽核 2、不使用 -1，預設未簽核。查詢欄位是 `MClassNo`、`OPNo`。Service 載入全部狀態，再由 WinForms 本機按 IssueState 篩選。

Grid 顯示 `MClassNo`、`OPNo`、`GroupNo`、`Description`、建立/修改人與日期；`IssueState`、`DataStamp` 隱藏。說明可多行，日期格式 `yyyy/MM/dd HH:mm:ss`。刪除與核准可多選逐筆呼叫，遇到第一筆失敗即停止，最後重載資料。新增/修改/複製以 `(MClassNo, OPNo)` 定位活動列。

## 定義視窗與欄位邏輯

`frmFinalGroupDef` ClientSize 為 `632×454`。上方選主分類；中間區塊是作業站清單及異常處理群組選取器，並有說明欄；下方顯示建立/修改資訊，按鈕為確定、關閉、套用。主分類與群組編號是唯讀欄位，透過 `...` 查找。

- `LoadFinalGroupDefine` 回傳已核准的主分類 `TBLQCMCLASSBASIS`、作業站 `TBLOPBASIS`、異常處理群組 `TBLQCHOLDDISPGROUPBASIS`（皆 `IssueState=2`）。群組選擇器顯示 GroupNo、GroupName、Description。
- 新增可多選作業站；WinForms 額外加入 `OPNo='*'` 通用列。每個勾選 OP 新增一筆資料。
- 修改時主分類不可改，作業站 Grid 只顯示原 OP；可選群組並修改說明。`ExeIssueControl` 會依狀態及系統設定控制欄位；Service/Core 的更新只接受狀態 0 或 2。
- 複製帶入原主分類、群組、說明；作業站候選只限原 OP 與 `*`，預設都未勾選。保存產生新的複合鍵資料。
- 主分類長度 30、作業站 20、群組 20、說明 255；主分類、群組、至少一個 OP 必填。建立者/時間與修改者/時間由表單及 Service 設定。
- Add/Copy 由 `UpdFinalGroup` 對選取 OP 逐列產生 INSERT collection；YMES API 應在單一交易完成批次新增，並驗證複合鍵唯一。

## 狀態、刪除與核准

| IssueState | 畫面 | 修改 | 刪除 | 核准 |
| ---: | --- | --- | --- | --- |
| 0 | 未簽核 | 可改群組/說明 | 實體刪除 | 可送核准 |
| 1 | 簽核中 | 不可修改 | 拒絕 | 不可重複送出 |
| 2 | 已簽核 | Service 接受修改；欄位另受 Issue Control 控制 | 設為 -1 | 不可送出 |
| -1 | 不使用 | 不可修改 | 實體刪除 | 不可送出 |

刪除按主 Grid 選取狀態逐筆處理：0/-1 實體刪除；2 以 `SetFinalGroupIssueState` 軟停用；1 拒絕。WinForms 會傳 DataStamp；舊 Core 實體刪除未比對 DataStamp，狀態更新及一般編輯會 CAS 並遞增。新 API 的實體刪除也要採 CAS，並支援來源 nullable DataStamp。

核准呼叫 Issue Job Map 的來源字串 **`Final GROUP`**（原始碼大小寫及空格如此，與 FunctionNo `FINAL GROUP` 不同）。找不到 Job 或沒有 Job Detail 時直接設為 2；有簽核明細則建立 Issue，資料先設為 1，核准 SQL 設為 2、退回 SQL 設回 0，處理附件並通知第一簽核群組。Production API 必須依登入者與實際 Issue/Job 設定執行；DEV 假資料只模擬直接核准分支。

## YMES 前端/API handoff

Vue 元件 `web/src/components/QcFinalGroupMaster.vue`；三層選單 QC → 異常設定 → 最後處理群組。DEV localStorage key 為 `ymes-dev-mock:qc-final-group:v1`。建議 API 契約：

- `GET /api/qc/final-groups?searchFieldName=&searchFieldValue=` 回傳全部狀態與 audit/DataStamp；搜尋欄白名單為 MClassNo、OPNo，狀態由 UI 篩選。
- Options 僅回傳 `IssueState=2` 的主分類、作業站、異常處理群組；可沿用 QC406 的共用查找實作，保持 QC407 權限檢查與欄位格式。
- `POST /api/qc/final-groups` body `{mClassNo, operationNos, groupNo, description}`；每個選取 OP（含明確允許的 `*`）新增一列，驗證長度、候選狀態及複合鍵，批次使用交易，Audit/DataStamp 由伺服器設定。
- `PUT /api/qc/final-groups/{mClassNo}/{opNo}?dataStamp=` 只改 GroupNo/Description；依舊 Service 限狀態 0/2，更新 Reviser/ReviseDate/DataStamp。nullable DataStamp 用 `IS NULL` CAS。
- `DELETE /api/qc/final-groups/{mClassNo}/{opNo}?issueState=&dataStamp=`：0/-1 實體刪除，2 改 -1，1 回 409；多筆仍逐筆，失敗停止並回報部分成功。
- `POST /api/qc/final-groups/{mClassNo}/{opNo}/approve`：驗證狀態、DataStamp，依 Issue Job Map key **`Final GROUP`** 執行直接啟用或建立 Issue 簽核；回傳狀態與 DataStamp。

所有端點驗證登入及 FunctionKey `QC407` 權限、使用 SQL 參數；來源無 FK，不得 cascade 刪除 lookup 資料。Production API/schema 未部署前只使用 DEV 假資料。
