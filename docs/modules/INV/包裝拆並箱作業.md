# IV310 包裝拆並箱作業

更新：2026-11-24。範圍為在製品包裝拆箱、並箱與拆並箱歷程；公司端 Vue 只使用 DEV 假資料。

## 原始程式

- Form／Designer：公司 MES checkout 的 STD/MESWin/INV/IV_MOPackingCombineDismantle/frmINVMOPackingCombineDismantle.vb。Form 與 Designer 同檔；主 Tab 為 Split Package、Merge Package，包含 Unboxing Method、拆箱包裝階層 Grid、Combine To／From Grid、Full Boxe Auto Closed、Confirm、Delete、Pack Close。
- 查詢 Service：STD/MESws_STD/wsSTD/wsWIP/wsWIP.cs 的 LoadMOLinePackRelation、LoadLotState、LoadInvPackState；STD/MESws_STD/wsSTD/wsINV/wsINV.cs 的 LoadMOPackingData。
- 寫入 Service：wsWIP.ExePackingDismantle、wsWIP.ExePackingCombine。
- Core：STD/MESkc/kcINV/clsInventory.cs::LoadMOPackingData；STD/MESkc/kcWIP/clsLot.cs::ExePackingDismantle、ExePackingCombine。

## Form 操作與規則

### 拆箱

1. 掃描包裝編號時，先拒絕已建立未確認成品入庫單的包裝／Lot；查包裝關係，拒絕已被更高階包裝包含的項目；須存在且在同一批作業內保持相同 MO 與 PackingLevel。
2. 載入時要求來源包裝未封箱。拆至生產批會展開 L0；另外兩種只展開下一個包裝階層。
3. 拆箱方式為 0「拆解單一包裝階層」、1「零散拆箱」、2「拆解到生產批」。切換方式會清掉已載入的拆箱資料。零散拆箱只傳勾選子項；若沒有勾選項目即不執行。Form 的 Delete 只從目前載入的 DataSet 移除選列，Confirm 才呼叫寫入 Service。
4. 線上包裝會查展開 Lot 的狀態，只接受 0、1、11；線邊倉包裝不做過站檢查，拆箱後仍在原線邊倉位置。
5. 確認後 Core 將拆出內容與當前包裝狀態比對，寫入 Pack Log／Pack Merge Log（Action=0），並更新包裝階層主檔、Detail、Relation、Pack State。拆至 L0 會依 strBatchLots 接續自動 BR／Lot transfer 流程。

### 並箱

1. 先掃 Combine To。須為存在、最高層、未封箱、未滿箱、未開立成品入庫單的包裝；Form 再讀 MO、產品包裝規則及標籤列印規則。
2. 每個 Combine From 必須先有目標，且與目標同 MO、PackingLevel 剛好低一層；不可重複。若目標為 L1，來源直接當 Lot 查詢；否則查來源包裝及其 Lot。線上來源的 OP 必須符合目標 PackPosition；線邊倉來源的 Semi InventoryNo 必須符合目標位置。
3. Form 依 FullBoxBoxQty 與 FullBoxNumberQty 限制箱數、LotQty。超量拒絕新來源。達到容量時舊 Form 會視兩條容量是否同時滿箱、Auto Closed 勾選狀態分別詢問是否繼續／自動封箱。
4. Pack Close 需要至少一個來源，呼叫 wsWIP.ExePackingCombine；成功後讀標籤資料、使用本機標籤軟體及已安裝印表機列印。IV310 Core 的 ExePackingCombine 本身未看到更新層級表 CloseFlag；按鈕名稱與此方法的實際責任不完全一致，正式端應依 Pack Rule／獨立封箱流程確認，不可把 Action=1 合併等同 CloseFlag=1。
5. Core 寫入 relation、Lx Detail、Pack State、Pack Log（EventAction=4）、Pack Merge Log（Action=1）。達 MO 最後包裝階層時，會將在線 Status=1 的 Lot 設成 Status=4、LinkName=pass，交 Service／Form 接續 Lot transfer；Form 使用 BeginInvokeSrv("wsWIP.TransferLot_Multi", ...)，不等待結果且吞掉呼叫例外。

## Service／Core 差異與風險

- LoadMOPackingData 可由傳入層級、顯示層級、CloseFlag 與 FullFlag 組階層資料，另帶 MO、容量、PackType、PackPosition、NodeId、箱數及 LotQty。FullFlag=1 代表讀取時拒絕已達滿箱容量的目標。
- ExePackingDismantle 對來源檢查仍為最高層，並比對 Pack State 中實際展開的子包裝數與數量。Core 以 SQL 集合寫多表，再由 row-count 檢查執行；拆箱模式 0／1／2 對應完整下一層、部分勾選下一層、展開至 L0。
- ExePackingCombine 的原始「寫入前再比對目標／來源現況」區塊已被註解。Form 的 MO／層級／位置檢查不能當成伺服器一致性保護。
- Combine Service 會先以 ExePackingDismantle(0, target, targetChildren, ..., blnDeletePackL:false) 展開目標內容，再呼叫 Core ExePackingCombine。這是兩段 Core 寫入；第二段失敗時不能假設第一段已回滾。Form 後續 Lot transfer 又是另一個非同步呼叫。家用 API 必須將目標展開、來源併入、pack state／relation／log、CloseFlag 裁決及必要的 Lot transfer/job 協調為可恢復交易，禁止只回傳成功。
- 舊 Service 接收完整 DataTable XML；正式 API 不應信任瀏覽器回傳的 MO、階層、PackType、數量、Lot 清單或 NodeId。只接收包裝識別與預期版本，伺服器重查關係、狀態、FGD、容量、MO/層級/位置與 DataStamp，再原子寫入。
- L0、L1–L6 共用包裝識別無統一新主鍵；TBLWIPMOLINEPACKRELATION 只有兩個非唯一索引而無 PK，TBLINVPACKMERGELOG 無 PK／索引。正式端須設計伺服器交易識別與冪等鍵，保留原有歷程，不可假設舊 MergeLog 可直接去重。
- 標籤產生依 MO／產品包裝規則、Label Rule、客戶端印表機與 CodeSoft／BarTender COM。本頁只顯示 DEV 標籤工作預覽；browser 不直接選伺服器路徑或啟動舊 WinForms COM。正式列印使用授權的 label job／代理。

## 資料表與 DDL

此功能沿用已查證的 WP601 共用包裝結構，沒有新專屬資料表或 CREATE SQL：

- 包裝主檔與 Detail：TBLWIPMOLINEPACKL1–L6、TBLWIPMOLINEPACKL1DETAIL–L6DETAIL。
- 目前階層：TBLWIPMOLINEPACKRELATION、TBLINVPACKSTATE。
- 包裝歷程：TBLINVPACKLOG、TBLINVPACKMERGELOG。
- 包裝設定與列印：TBLWIPMOLINEPACKCONFIG、TBLWIPMOLINEPACKLABELPRINTER；讀 MO、Lot、產品包裝規則及標籤規則共用表。

WP601 Oracle source DDL／metadata 與 PostgreSQL CREATE-only 參考已在 database/reference/mestest_wip_wp601_source_ddl.sql、mestest_wip_wp601_metadata.txt、mestest_wip_wp601_create.sql；完整補充 metadata 在 mestest_wip_wp601_supplemental_metadata.txt。此輪沒有桌機受保護 Oracle profile，沒有連 MESTEST 查業務列；IV310 所需包裝表直接沿用既有 WP601 metadata，家用端仍須先核對 YMES live schema／migration。

## YMES API／schema handoff

- 不建立另一套包裝表，也不從 Legacy SQL 推測欄位。先比對 WP601 的 CREATE-only 與 live PG schema；缺少物件時逐表核對原始 DDL／migration provenance，再決定 forward migration。
- 提供登入與 IV310 ACL 保護的唯讀包裝階層／Pack Rule lookup，以及兩個明確命令：拆箱（mode 0／1／2、來源包裝識別、零散選取識別、預期版本）與並箱（目標識別、來源識別集合、Auto Closed 選項、預期版本）。
- 每次命令在單一 PostgreSQL transaction 鎖定／重查相關 hierarchy；驗證 FGD 未確認單、封箱／滿箱、同 MO、頂層、層級相鄰、線上 OP 或線邊 Inventory、Lot Status、實際 Pack State 內容與容量。提交前檢查競態版本；失敗須整筆回滾並回傳可追蹤錯誤。
- 同交易維護 Lx／Detail、Relation、Pack State／Log、MergeLog；嚴格作用於指定 package keys。記錄 server-generated operation ID、actor、event time、來源／目的與冪等結果。對 Lot BR／Transfer 及標籤列印使用 outbox／job，回傳 Pending/Failed/Complete，不在 DB commit 之外靜默吞錯。
- 單獨裁決 Pack Close 與 Core ExePackingCombine 的 CloseFlag 差異；只有產品規則要求且交易條件完整時才設定封箱，不得用客戶端 checkbox 宣告封箱成功。
