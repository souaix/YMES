# IV201 原物料倉庫房資料

## 範圍與來源

- FunctionKey：`IV201`；FunctionNo：`RAW INVENTORY`；路由：`/YMES/INV/RawInventory`（左側分類為「原物料倉」）。
- WinForms：`D:\iMES\CSiMES\STD\MESWin\INV\IV_RawInventory\frmINVRawInventory.vb`，Form 與 inline Designer 在同一檔；六個確認視窗也在 `IV_RawInventory` 目錄。
- Service：`STD/MESws_STD/wsSTD/wsINV/wsINV.cs` 的 `LoadRawInventory`、`LoadRawInventoryLoc`、`AddINVTransactionState`、`ExeINVTransactionState`。
- Core：`STD/MESkc/kcINV/clsInventory.cs` 的 `LoadRawInventory`、`LoadRawInventoryLoc` 及六種交易執行方法。
- 本規格依 Form／Designer、Service、Core 原碼整理；畫面沒有直接新增、修改或刪除庫存主檔的功能。

## 畫面與操作

1. Form 載入時呼叫 `wsSMD.LoadInventoryBasis`，帶 `IssueState=2`、`InventoryType=0`，以 `InventoryNo` 排序填入庫房下拉選單。再查原物料庫存並顯示目前選取庫房；原始碼在未選到庫房時會套用不命中的 `InventoryNo='Null'` 篩選。
2. 上方 Raw Inventory Grid 顯示 `InventoryNo`、`MaterialNo`、`SafeQty`、`CurQty`、`AllocateQty`、`UnitNo`。Core 只取 `InventoryNo IS NOT NULL AND CurQty > 0`。選取列時以該列 `InventoryNo + MaterialNo` 載入下方 Locator Grid。
3. Locator Core 查 `TBLINVRAWINVENTORYLOC`，並以 `IssueState=2` 左連 `TBLMTLMATERIALBASIS`。來源回傳 `InventoryNo`、`LocatorNo`、`MaterialNo`、`MaterialName`、`MaterialLotNo`、`LocQty`、`InputDate`、`VendorNo`、`ExpireDate`、`ManufactureDate`、`GraceDate`；Form 實際顯示 LocatorNo、MaterialNo、MaterialLotNo、LocQty、ExpireDate、ManufactureDate、GraceDate。
4. `Refresh` 重載庫存及目前選取列的 Locator；`Close` 關閉 Form。
5. 六個按鈕開各自的單據選取／確認視窗，讀取 State=0 的待確認單據，顯示單頭和明細；按 Confirm 後呼叫 `AddINVTransactionState`，成功回到主畫面重載庫存與 Locator。

| 按鈕 | 確認視窗 | Source | 單據／Core 行為 |
| --- | --- | ---: | --- |
| Material In | `frmINVMaterialInConfirm` | 0 | 進料單；`ExeMaterialIn` 將單據明細換算成庫房單位並增加 `CurQty`／儲位數量。 |
| Material Out | `frmINVMaterialOutConfirm` | 1 | 領料單；先檢查可領數量，再扣 `CurQty`／儲位量、調整預訂量，並可能更新投入點物料狀態。 |
| Material Adjust | `frmINVMaterialAdjustConfirm` | 3 | 調整單；Core `AdjustType=0` 按 `DiffQty` 更新庫存及 Locator；其他類型走儲位異動路徑，並檢查未確認領料單。 |
| Pre Order | `frmINVPreOrderConfirm` | 4 | 預訂單；增加 `AllocateQty`，不增加 `CurQty`。 |
| Material Return | `frmINVMaterialReturnConfirm` | 2 | 原物料退回供應商單；`ExeMaterialReturn` 依明細檢查 Locator 批號數量，扣減 `LocQty`、`CurQty`，刪除歸零列，並清理相關元件庫存資料。 |
| WIP Return | `frmINVMaterialWIPReturnConfirm` | 10 | 在製退料單；由 `ExeMaterialWIPReturn_ForMaterialWIPMOReturn` 處理回庫與來源地點資料。 |

`AddINVTransactionState` 要求 Source 與 TicketNo，呼叫 `ChkDetailQty` 後建立交易狀態並將來源單據設為處理中；領料另檢查庫存並記錄確認人。Service 接著同步呼叫 `ExeINVTransactionState`，依 Source 執行對應 Core。需注意舊 Service 先將 Add response 設為 success，再呼叫執行 Service；該內層例外被空 catch 吞掉，因此 Confirm 回應可能未反映實際執行失敗，Core 另可能將單據設為 State=3。家用端不可照搬此假成功回應，需回傳可核對的最終狀態與交易結果。這是跨單據與庫存的交易流程，不能以單純更新庫存數字取代。

## Vue DEV 交付

- 由 `web/src/components/InvRawInventory.vue` 與 `InvRawInventoryDevPreview.vue` 提供；僅 Vite DEV 載入互動預覽，正式環境顯示尚未開放提示。
- 以 DEV 假資料呈現庫房下拉、庫存主 Grid、選取品項連動的 Locator/Lot Grid、摘要、Refresh、Close 及六種待確認單據入口。
- 單據視窗可選 DEV State=0 單據並查看主要欄位；Confirm 在 localStorage 將單據改為 State=2、記下 DEV 交易紀錄，模擬進料／WIP 退料增加數量、領料／Material Return 扣庫存、調帳或儲位調整、預訂增加 AllocateQty。領料、Material Return 及調整會檢查 DEV 可用數量。
- 瀏覽器保存鍵為 `ymes.dev.inv.raw-inventory.v1`。所有 DEV fixture、單位轉換、Vendor、批號日期與交易流水號均為展示資料；未連 MES Service、Oracle、YMES PostgreSQL 或正式 API。
- DEV 只呈現單明細的示例，不包含完整多明細單據、物料單位換算、領料投入點／元件／WIP 狀態、預訂單關聯消耗、外包與產業包分支、單據退貨政策及失敗交易回復。

## 資料表、DDL 與限制

- 查詢直接依賴 `TBLINVRAWINVENTORY`、`TBLINVRAWINVENTORYLOC`，另讀 `TBLMTLMATERIALBASIS`；交易還讀寫各類單據主檔／明細、INV transaction state/log、物料／投入點／WIP 相關資料，完整表清單須按各 Core 分支由家用端確認。
- Repo 目前只有 WIP 盤點規格提到這兩張庫存表，沒有可追溯至此版本 MESTEST 的兩張表 Oracle DDL／metadata，也沒有可信 PostgreSQL CREATE-only。桌機的受保護 Oracle profile 不存在，因此本輪未連 Oracle；沒有猜測或新增 schema SQL。
- Core 以字串串接 SQL；正式 API 必須參數化、驗證登入者和 `IV201` Function ACL，不接受任意 AdditionalXml 條件。分頁／最大列數需由家用端設計，避免無界查詢。

## 家用端 API／schema handoff

- 2026-11-24 以 PPK SSH 對 YMES PostgreSQL `ymes`／quoted schema `YMES` 做唯讀 catalog audit：`tblinvrawinventory`、`tblinvrawinventoryloc`、`tblinvtransactionstate`、`tblinvtransactionlog` 均不存在；`tblmtlmaterialbasis` 存在 110 欄，`tblinvinventorybasis` 存在 14 欄，`tblinvlocatorbasis` 存在 12 欄。`YMES` 內目前只有四張 `tblinv*` 表：Inventory Basis、Locator Basis、Stocker Basis、Engineer Group Basis；沒有 Raw Inventory／Locator 或共用交易 State／Log。資料庫只找到 `ym_migration_0012_navigation_backup` 這個特定用途備份表，沒有通用 migration ledger；repo migrations 也沒有建立上述四表的 migration。
- `TBLINVTRANSACTIONSTATE/LOG` 已有 WP605 Oracle source DDL 與 PostgreSQL CREATE-only reference，可在核對共用交易所需欄位／權限後另做 forward migration；`TBLINVRAWINVENTORY/LOC` 在 repo 沒有可追溯 Oracle DDL／metadata／PostgreSQL CREATE-only。已把精確 Oracle 結構資料需求交公司端 `todolist_officepc.md`。在收到可信原始 DDL 之前，不新增這兩張表、不依 DEV fixture 猜欄位，也不開始依賴其結構的查詢 API。
- 六種交易所需的單據主檔／明細、INV transaction、投入點與 WIP 相依仍需逐一沿 Core 分支建立表清單，再和 live schema／既有 source references 比對；沒有經查證的表結構不建立 migration。
- 提供受登入與 `RAW INVENTORY` Function ACL 保護的 RAW `InventoryType=0`／有效庫房 lookup、有限筆數庫存查詢，以及依 `InventoryNo + MaterialNo` 載入 Locator/Lot 明細的唯讀 API。伺服器固定 `CurQty > 0` 等舊畫面條件，使用參數化條件與明確排序。
- 六個確認入口應呼叫各自已授權單據 API 或共用伺服器交易 command；重新驗證來源單據 State=0、庫房／物料／單位、可用量、預訂量、批號／Locator、使用者權限及版本。以單一資料庫交易或可靠的可恢復工作流程處理來源單據、transaction state/log、庫存總量／儲位與投入點副作用；冪等鍵與併發鎖防止重複 Confirm。領料與儲位異動需保留來源檢查，失敗時不可回報交易成功或留下部分更新。
- Unit conversion、各單據多明細、`FromInventoryNo`、領料的 Material Component／OE／WIP、PreOrder 使用／扣抵、Material Return 元件清理、AdjustType 分支、WIP Return 來源 Place 與特定產業包資料，均需逐條對照 WinForms／Service／Core 後實作，不沿用 DEV 單筆示例。
- 公司端未連 YMES PostgreSQL，未實作或驗收正式 API／schema／migration，未部署。
