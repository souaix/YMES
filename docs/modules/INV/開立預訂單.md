## 原程式畫面與操作

Form 載入時以 State=0 查詢所有未確認預訂單，Query 搜尋欄只有精確 PreOrderNo，主 Grid 依 PreOrderNo 升冪排列；載入後自動選取第一張並載入明細。查無單頭時 Form 直接清空 Detail Grid。主畫面是 PreOrder Basis 與 PreOrder Detail 兩個 Grid；沒有確認、列印或日期範圍功能。

Basis Grid 顯示 `PreOrderNo`、`InventoryNo`、`State`、`Description`、`Creator`、`CreateDate`、`Reviser`、`ReviseDate`。按鈕為 ADD、EDIT、DEL、COPY、Query、Close。ADD／COPY 建立 State=0 單頭；新增需要 PreOrderNo 與 InventoryNo。COPY 帶入來源單的 InventoryNo／Description，使用新 PreOrderNo，**不複製明細**。EDIT 只改 Description，PreOrderNo 和 InventoryNo 鎖定；單頭編輯送 DataStamp，Core 同時更新 Reviser／ReviseDate 並將 DataStamp 遞增。DEL 只允許 State=0；Core 以一組 SQL 刪除明細及 Basis，主畫面對多選單頭逐筆呼叫 Service，若中途失敗先前項目不會回復。

單號依 `PREORDERNO` Serial Rule。Rule 啟用時 PreOrderNo 欄位鎖定、顯示取號按鈕；Form 先以 `ReserveSerialNo=False` 預覽號碼，儲存時再次比對候選號並以 `ReserveSerialNo=True` 保留。Rule 停用時允許人工輸入，離開欄位時轉大寫。正式端應由伺服器執行序號產生／保留及防重，不能信任瀏覽器產生的號碼。

Detail Grid 顯示 `MaterialNo`、`UnitNo`、`Qty`、`Creator`、`CreateDate`、`Reviser`、`ReviseDate`；Qty 顯示最多六位小數。只有目前單頭 State=0 可 ADD／EDIT／DEL／COPY。新增與複製時由單頭 InventoryNo 呼叫 `LoadRawInventory`；Core 限 `CurQty > 0`，搜尋視窗選取物料後帶入 MaterialNo／UnitNo。MaterialNo 和 UnitNo 在表單唯讀；EDIT 鎖 MaterialNo，只能改數量。Qty 必填、需為數字且大於 0。明細 COPY 帶入原物料／單位／數量後使用者可重新挑選物料。明細新增由 Core 寫入 Creator／CreateDate；編輯透過 DataStamp 比對更新並改寫 Reviser／ReviseDate。刪除以 PreOrderNo／MaterialNo 為條件。

## 狀態與 IV201 邊界

- IV205 主畫面只讀寫 State=0。Service 的單頭 Edit／Delete 檢查呼叫端傳入 State=0；舊明細寫入 Service 沒有同等完整的單頭狀態守門，Web API 必須自行在每次異動時重讀父單並確認仍為 State=0。
- 新增預訂單或明細不扣 `CurQty`，也不增加 `AllocateQty`。使用者需到 IV201 Material PreOrder 確認流程才會執行預訂確認／庫存預約；不要在 IV205 回報「已保留」或「已預約」。IV201 之後的出庫可在 IV203 指定同庫房且 State=2 的 PreOrder。
- Service/Core 的既有 SQL 使用字串串接；Formal API 必須參數化，並在單一交易內守住 State、DataStamp、序號及主從一致性。

## 資料表、DDL 與 Oracle 查證

Core 使用 `TBLINVPREORDERBASIS`、`TBLINVPREORDERDETAIL`，物料 lookup 讀 `TBLINVRAWINVENTORY`；IV201 確認會另寫庫存預約及共用交易歷程。Repo 未找到本版本 PreOrder Basis／Detail 的 Oracle source DDL／metadata 或可信 PostgreSQL CREATE-only。`TBLINVTRANSACTIONLOG` 可沿用 WP605 已有 Oracle source DDL 與 PostgreSQL CREATE-only reference。公司桌機受保護 Oracle profile／attachment 不存在；本輪未用 PowerShell 5.1／ODP.NET 查 MESTEST、未查業務資料，也未猜 CREATE SQL。

## 家用端 API／schema handoff

- 先 pull 最新 `main`，核 PostgreSQL live schema／migrations；若 Basis／Detail 或其唯一鍵、DataStamp 結構缺失，先取得可信 Oracle DDL／metadata，不從 Core SQL 推欄位型別、nullable、default、PK/FK/index。
- 提供登入與 IV205 Function ACL 保護的 State=0 主檔查詢／建立／修改／刪除及明細查詢／維護 API。主查詢依 PreOrderNo 搜尋，穩定排序與分頁／上限；明細 endpoint 必須帶 PreOrderNo，舊 Core 空單號會回傳全表明細，正式 API 不可接受此行為。
- Add 單頭由伺服器建立 State=0、限制有效 InventoryType=0 庫房、產生及保留 PREORDERNO serial。Copy 複製 InventoryNo／Description，不複製明細。Edit 限 Description，PreOrderNo／InventoryNo 不可改，以 DataStamp compare-and-swap；Delete 僅限 State=0，於同一交易刪明細及 Basis。Batch 操作回報逐筆結果，明確保留或改善舊 WinForms 逐筆部分成功語意。
- Detail Add／Copy 重新驗證父單 State=0、物料屬於同一原料庫房且 RawInventory `CurQty > 0`，UnitNo 從有效物料資料取得、Qty 必須大於 0；不要因草稿建立而更動庫存／AllocateQty。Edit 保持 MaterialNo 鎖定並只改 Qty，以 DataStamp CAS；Detail Delete 限同父單 State=0。唯一性與複合鍵需由 live schema 核實，不可只依 DEV guard。
- 真正預約／確認放在 IV201：需依來源 Core 重驗單據與庫存，於交易更新預訂單狀態、AllocateQty 與 Transaction State／Log，支援冪等及失敗回復；IV205 API 不回報已預約。參數化所有 SQL，不接任意 AdditionalXml。
