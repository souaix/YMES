## 原程式畫面與單頭操作

Form 載入會呼叫 `funInitialize()`，將 `MaterialReturnNo` 設為唯一搜尋欄，固定送 `State=0` 查詢，按 `MaterialReturnNo` 排序；表單沒有確認、列印或簽核按鈕。原始 State ValueList 讀 `TBLINVMATERIALOUTBASIS.STATE`，雖是 MaterialOut 表名，IV206 本身仍以 State=0 查詢。

Basis Grid 欄位為 `MaterialReturnNo`、`InventoryNo`、`VendorNo`、`State`、`Description`、`Creator`、`CreateDate`、`Reviser`、`ReviseDate`。操作是 Query、ADD、EDIT、DEL、COPY、Close。ADD／COPY 建立 State=0；必填單號、原料庫房與 Vendor，Description 可空。庫房 picker 使用 `InventoryType=0`，Vendor picker 來自供應商查詢。

`MATERIALRETURNNO` Serial Rule 啟用時單號唯讀並透過 `wsSYS.GetMaterialReturnNo` 先試取、儲存時再比對及保留；Rule 未啟用時可手動輸入。DEV 預覽自動取號路徑，沒有模擬手動序號規則或多使用者序號競爭。COPY 帶來源 InventoryNo、VendorNo、Description 並取新號，**不複製明細**。EDIT 僅能修改 Description，單號／庫房／Vendor 鎖定，傳 DataStamp；Core 更新 Reviser／ReviseDate 並遞增 DataStamp。

Basis DELETE 只允許 State=0；主畫面可多選並逐筆呼叫 Service，中途失敗會留下先前已刪項目。Core 刪除 Detail、Basis、MaterialReturnComponent，並釋放對應 RawInventoryComponent 的 `BookingFlag`；Core 以 SQL Collection 執行，但未確認整個刪除生命週期的交易／回復保證。正式 API 必須在一筆交易內處理父單、明細、退料元件及 BookingFlag，並回報多選結果。

## 明細與元件操作

Detail Grid 顯示 `MaterialNo`、`MaterialLotNo`、`LocatorNo`、`UnitNo`、`Qty`、`Creator`、`CreateDate`、`Reviser`、`ReviseDate`；依 `MaterialReturnNo, MaterialNo, MaterialLotNo, LocatorNo` 排序。只有所屬 Basis State=0 時可 ADD／EDIT／DEL／COPY。主畫面先選單頭，再以該 `MaterialReturnNo` 載入明細及元件子列；正式 API 的 Detail／Component 查詢必須要求有效單號，不能將空單號傳給舊 Core。

Detail 視窗的 `MaterialReturnNo`、`InventoryNo`、`VendorNo` 為唯讀上下文。物料 lookup 使用該 Vendor 的 `LoadMaterialBasis`，MaterialNo／UnitNo 由料件主檔帶入；批號與 Locator 從同一 InventoryNo＋MaterialNo 的 `LoadRawInventoryLoc` 選取，初始 Qty 帶 LocQty。來源沒有在草稿儲存前限制 Qty 不得大於 LocQty；IV201 確認時才應重新驗庫存。MaterialNo、Lot、Locator、UnitNo 為編輯中的識別欄位，Detail Edit 更新 Qty 並帶 DataStamp。

Qty 必填、數字且大於 0。若該原料批號有 Component，視窗載入 Component、顯示 BookingFlag=0 的候選項並提供 Select All／UnSelect All／MultiSelect；至少要選一個，且 `CInt(Qty)` 必須等於選取元件數。Core 的 Raw Component lookup 呼叫只傳 MaterialNo／MaterialLotNo，沒有 InventoryNo；Core 查詢可跨庫房混入相同批號元件。DEV fixture 以父單 InventoryNo 限定候選，正式 API 必須明確補上此範圍及鎖定／重驗 BookingFlag。

Detail Add／Edit／Delete 的 Service 先呼叫 Basis Core，再分開呼叫 Component Core 與更新 Raw Component `BookingFlag`，各步驟不是一個 Service 層交易；失敗可能只完成部分寫入。另 `EditINVMaterialReturnComponent` Core 先刪除同一 `MaterialReturnNo` 的所有退料元件，再寫入本次 payload，可能覆蓋其他明細所選元件。正式 API 應以完整 Detail 識別欄位定位元件，限制修改範圍並以單一交易完成明細與 BookingFlag 更新。明細實際唯一鍵／PK 尚未由可信 metadata 確認，不可將 Core 條件當成已驗證資料庫唯一鍵。

## IV201 確認邊界

IV206 只建立／維護未確認草稿，不扣減 `TBLINVRAWINVENTORYLOC` 的 `LocQty`，也不增加退料庫存。退料確認由 IV201 Source=3 執行：來源 Core 會依單據明細扣減 Locator／Raw Inventory 數量並處理退料元件 Booking 狀態。`ExeMaterialReturn` 的狀態檢查部分在舊 Core 中有註解，不應只依傳入 State 放行；正式 IV201 command 必須重新讀單據、檢查現況與庫存、以交易及冪等鍵防止重複扣帳。IV206 草稿 API 不得冒稱已退料。

## Vue DEV 頁

- `web/src/components/InvMaterialReturn.vue` 是 DEV fallback 入口；僅 Vite DEV 且 `developmentPreview=true` 時載入 `InvMaterialReturnDevPreview.vue`。
- localStorage key：`ymes.dev.iv206-material-return.v1`。頁面提供 MaterialReturnNo Query、State=0 Basis／Detail ADD／EDIT／DEL／COPY、雙 Grid、確認刪除、Component 子列展開、`MATERIALRETURNNO` 假取號、Vendor／Inventory／Lot／Locator 假 lookup、Qty 驗證和本機 DataStamp／BookingFlag 更新。
- Basis COPY 不複製 Detail；Basis Edit 限 Description。Detail COPY 複製原料／批號／Locator 作為起點，但不沿用被預約的元件。元件明細以 fixture 選擇並同步本機 booked id。DEV 的選取刪除以 row key 精確清除，不模擬舊畫面多筆逐筆部分成功；不模擬真實 DataStamp 競爭、序號保留競態、DB transaction、庫存確認或 Oracle／MES Service 呼叫。
- 元件選取時 DEV 要求正整數 Qty 等於選取筆數；這比舊 WinForms `CInt(Qty)` 的四捨五入轉型更嚴格。DEV 會按父單 InventoryNo 篩選元件；來源 Core lookup 沒有庫房條件。
- 本頁無 Print／Confirm action。資料只留在本機 DEV localStorage，未連 YMES PostgreSQL，也未呼叫正式 API。

## 資料表、DDL 與 Oracle 查證

Core 直接讀寫 `TBLINVMATERIALRETURNBASIS`、`TBLINVMATERIALRETURNDETAIL`、`TBLINVMATERIALRETURNCOMPONENT`、`TBLINVRAWINVENTORYCOMPONENT`；明細批號／儲位 lookup 讀 `TBLINVRAWINVENTORYLOC`，另透過 MTL Vendor／Material lookup 讀相應主檔。Repo 目前沒有 Return Basis／Detail／Component 的可核實 Oracle source DDL／metadata 或 PostgreSQL CREATE-only；Raw Component／Raw Inventory Locator 同版 metadata 也未找到。公司桌機指定受保護 Oracle profile 路徑不存在，這輪未連 MESTEST、未用 PowerShell 5.1／ODP.NET 查 metadata、未讀業務資料，亦未推測 CREATE SQL。MTL vendor/material references 可供家用端沿用已存在的 source files；Return 專用表仍待可信結構。

## 家用端 API／schema handoff

- 先 pull 此 commit 並核對 YMES PostgreSQL live schema／migrations。以可信 Oracle metadata 補足 Return Basis／Detail／Component、Raw Component／Raw Inventory Locator 的欄位型別、nullable、default、PK／unique／index／FK／trigger，再決定 CREATE-only／migration；不可從 DEV fixture 或舊 SQL 推完整結構。
- 提供登入及 `MATERIAL RETURN` Function ACL 保護的 State=0 查詢／單頭建立、說明修改、刪除及 Detail 維護 API；參數化 MaterialReturnNo，穩定排序／分頁及上限。Detail 與元件 endpoints 必須要求有效父單號，無父單回傳空結果而非全表。
- 伺服器建立 State=0，檢查有效 InventoryType=0 與 Vendor，負責 `MATERIALRETURNNO` serial；Copy 僅複製 InventoryNo／VendorNo／Description、不複製 Detail。Edit 限 Description 並以 DataStamp CAS。每次 Detail command 重新確認父單仍是 State=0，從受控 lookup 取得 UnitNo，檢查 Qty>0；有 Component 時在同一庫房與 Lot 內鎖定可用元件、驗證 BookingFlag 及 Qty，再將 Detail、Return Component、Raw Component BookingFlag 以單一資料庫交易寫入。
- 核實退料明細真實唯一鍵，勿沿用疑似不完整的 Service/Core WHERE。多筆 Delete 應有明確全有或全無契約，並在同一交易刪主／明細／元件與釋放預約。防止同一元件被不同退料草稿重複預約。
- 實際庫存扣帳仍只由 IV201 Source=3 負責；在正式確認 command 內重新讀 State、Locator／RawInventory 數量及元件占用，使用 row version/lock、transaction log、冪等鍵保證重試不會重複扣帳。尚未確認的資料不得出現在正式「已退料」結果。

## 本輪限制

本輪更新後未執行 Vue build、測試或瀏覽器操作。桌機 Oracle profile 缺失，因此 Return tables DDL／metadata 是明確待查項；不阻止 DEV 與家用端 handoff 繼續。
