# IV305 在製貨架上下架作業

更新日期：2026-11-25。公司端完成 WinForms／Service／Core 核對、Vue 3 DEV 假操作與家用端交易 handoff；未連 YMES PostgreSQL，未實作正式 API。

## 功能與入口

- 選單 FunctionNo／功能代碼：`STOCKER MANAGER`／IV305；Form `frmStockManagement`，執行檔 `IV_StockerManager.dll`。
- Vue DEV fallback FunctionKey `function:INV:STOCKER MANAGER`，路由 `/YMES/INV/StockerManager`，位於庫存管理／在製品庫。
- 功能將生產批 Lot 或已核准 Carrier 放入／取出 Stocker Locator，資料寫入 Stocker 現況與 Detail Log；不改 WIP Lot 本身的 CurQty。

## 舊畫面流程與規則

### 初始化與貨架選取

- Form Load 載入 `IssueState=2` 的 Stocker Basis；不會自動選貨架。
- 選 StockerNo 或用 `frmCOMSearch` Lookup 後，先讀該貨架 Detail，再讀 Stocker State，建立 `clsStockerInfo` 格位座標與每格的 ContentNo 清單。
- 格位由 HNumber／VNumber 建立；只納入 Detail 中 `VerticalPosition` + `HorizontalPosition` 恰好唯一的一格。動態 Panel 按钮用顏色區分空／有內容／容量已滿，但 `AddHandler` click handler 已註解；上下架仍以 LocatorNo 欄位／Lookup 輸入為準。
- Grid 主要顯示 LocatorNo、ContentNo、狀態字串 `StockOnFinished`；格位中的多個 ContentNo 由逗號串接，用於畫面容量判斷。

### StockOn

- 操作者選 StockOn、指定 StockerNo、LocatorNo、掃入 ContentNo，再按 Enter。Client 先要求三欄非空、貨架及 Locator 存在，並以本機格位內容檢查 `CapacityCtrl`／`QtyLimit`；滿格會阻擋呼叫 Service。
- Core 全庫檢查 ContentNo 是否已在任一 Stocker 上架；接著讀該 Locator 已有內容的 LotNo 欄位判斷格位類型，Lot 與 Carrier 不可混放。
- 若 ContentNo 是 `TBLWIPLOTSTATE` Lot，Core 拒絕 Status `1`、`11`、`12`、`99`，其餘找到的狀態可進入上架路徑。否則查 Carrier State + Carrier Basis；Carrier 必須存在且 Basis `IssueState=2`，同時不能進入目前放 Lot 的格位。兩類來源皆未找到時拒絕。
- Core 建立 `TBLINVSTOCKERSTATE` 現況並增加一筆 `TBLINVSTOCKERDETAILLOG` `Status=IN`；Service Core 成功後另呼叫 `AddEventLog`。現況寫入與 Event Log 不在同一資料庫交易邊界。

### StockOff

- 操作者選 StockOff、指定原 StockerNo／LocatorNo，再掃入該格 ContentNo。
- Core 先要求該 ContentNo 的現況位於指定貨架與 Locator；未曾上架或位於別格即拒絕。若為 Lot，同樣拒絕 Status `1`、`11`、`12`、`99`；若不是 Lot 則需能在 Carrier State 找到 Carrier。StockOff 分支沒有重查 Carrier Basis 的 `IssueState`。
- 成功後刪除該筆 `TBLINVSTOCKERSTATE`，寫 `TBLINVSTOCKERDETAILLOG` `Status=OUT`，Service 再記錄 Event Log。

### 舊 Core 缺口

- `QtyLimit` 只在舊 Form 的格位顯示／輸入前檢查；Core `StockOn` 沒有重新讀取 CapacityCtrl／QtyLimit 或在寫入前鎖格位，多個掃描器併發時可能超容量。Web API 不能只仿 Form 前端驗證。
- StockOn 依 Locator 查現況時只讀第一筆以判斷 Lot／Carrier；若同格已有多列或狀態不一致，類型判斷受資料庫回傳順序影響。
- Core 會計算 Lot CurQty／Carrier 內 Lot CurQty，但實際寫入 Log 的 `ContentQty` 使用貨架現有列數 `Count(*) ± 1`，不是 Lot 數量。DEV 保留名稱與數量語意並明示為格位內容筆數。
- StockOff 的 Carrier 分支只確認 Carrier State 存在，沒有與 StockOn 對稱地確認 Carrier Basis IssueState。
- SQL 以字串串接 ContentNo／StockerNo／LocatorNo；Service 的 EventLog 在 Core 現況／Detail Log 操作後呼叫，可能出現資料已變更但稽核事件失敗的分離狀態。

## Vue DEV 復刻

- 選單加入 `function:INV:STOCKER MANAGER` fallback；頁面提供 StockerNo 假 Lookup、貨架格位圖、Locator 選取、ContentNo 輸入與 StockOn／StockOff radio。
- 上架模擬 ContentNo 唯一性、Lot 狀態黑名單、Carrier `IssueState=2`、同格 Lot／Carrier 不混放與 CapacityCtrl／QtyLimit；下架模擬指定貨架／格位配對與 Lot 狀態驗證。
- 現況 Grid 顯示 Locator／Content／種類／完成狀態；本頁操作回饋另列模擬 IN／OUT Log，方便確認 DEV 假操作。初始 fixture 含滿格、空格、Lot、Carrier 及禁止上／下架分支。
- DEV 的現況與操作回饋只存在頁面記憶體，不連正式 API，不寫 localStorage，不變更 Lot Qty／Carrier 資料；`ContentQty` 展示格位中的內容筆數。頁面用格位按鈕可點選方便操作，屬於 Web 模擬互動；舊 Form 原格位按鈕 click handler 為註解狀態。DEV 未 build、test 或 browser 驗收。

## 資料表與 Oracle references

| 表 | 用途 | DDL／metadata 狀態 |
|---|---|---|
| `TBLINVSTOCKERBASIS` | Stocker 尺寸、Area、CapacityCtrl／QtyLimit、IssueState | IV103 規格確認 repo 未有可信 Oracle DDL；first-phase CREATE 已標為推測，不可當原生來源 |
| `TBLINVSTOCKERDETAIL` | LocatorNo 與貨架格位座標 | repo 未找到可核實 DDL／metadata；不可依 Form 反推 CREATE |
| `TBLINVSTOCKERSTATE` | 目前 Stocker／Locator／Content、Lot 或 Carrier | WP302 `mestest_wip_wp302_source_ddl.sql`／`mestest_wip_wp302_create.sql`；Oracle PK 為 `(STOCKERNO, LOCATORNO, CONTENTNO)` |
| `TBLINVSTOCKERDETAILLOG` | 上架／下架事件列 | WP902 `mestest_wip_wp902_metadata.txt`／`mestest_wip_wp902_create.sql` |
| `TBLWIPLOTSTATE` | Lot 狀態及 CurQty 查核 | WP101 source DDL／CREATE |
| `TBLWIPCARRIERSTATE`、`TBLWIPCARRIERSTATEDETAIL`、`TBLEQPCARRIERBASIS` | Carrier 是否存在、是否已核准及其 Lot Qty 計算 | Carrier Basis dependency／WP302／Carrier Basis source DDL／CREATE |

桌機受保護 Oracle profile 在本接手環境不存在；本輪沒有連 MESTEST。Stocker Basis／Detail 缺可信 DDL／metadata，不產生或猜 PostgreSQL CREATE SQL；家用端先查 live PostgreSQL schema／migration，再決定缺表遷移。

## 家用端 API／transaction handoff

- 提供登入及 Function ACL 保護的 Stocker Basis／Locator／Current State 查詢；只回 IssueState=2 貨架，且每次操作都以 server 驗證使用者對 Area／Stocker 的權限。
- 提供單一 StockOn／StockOff command，使用參數化欄位及 operation/idempotency key。每次都在資料庫交易內重讀 Stocker IssueState、Locator 關係、當前現況、Lot Status 或 Carrier State／Basis、ContentNo 全域唯一性。
- StockOn 交易中鎖定 Stocker／Locator 的容量判斷，重新計算目前內容筆數並檢查 CapacityCtrl／QtyLimit；同格 Lot／Carrier 類型需依全部現況列判定。防止兩個掃描命令都先通過容量檢查再同時寫入。
- StockOff 必須使用 server 目前讀到的 StockerNo + LocatorNo + ContentNo 複合鍵與版本／現況檢查，避免舊讀碼結果誤刪已移格資料；Carrier Basis 核准規則需與產品決策一致，並修正 StockOn／StockOff 規則不對稱。
- 一個資料庫交易同時維護 `TBLINVSTOCKERSTATE` 與 `TBLINVSTOCKERDETAILLOG`，寫入不可重複的事件鍵與實際 ContentQty 語意。若外部 MES Event Log 另需保留，使用 transactional outbox 或可重送機制，避免現況與稽核事件分離。
- 家用端不得把 IV103 未核實的 `TBLINVSTOCKERBASIS`／Detail 推測 CREATE 套進資料庫；先查 YMES live PostgreSQL schema、migration history 及 Oracle reference 狀態，再補正式欄位／PK／FK／index。
