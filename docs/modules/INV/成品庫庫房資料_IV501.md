# IV501 成品庫庫房資料

## 範圍與來源

- MES FunctionKey：`IV501`；Function name：`FGD INVENTORY`；Form：`STD/MESWin/INV/IV_FGDInventory/frmINVFGDInventory.vb`；確認視窗：`frmINVFGDInConfirm.vb`。
- 本規格只涵蓋 IV501 的成品庫存查詢、Component／Bin 明細與 FGD In 確認。WP605 `frmInventory_FGD` 是另一支有人工調整、刪除及轉庫的帳務維護功能，不可把其按鈕或 API 混進 IV501。
- 已直接核對 Form／inline Designer、`wsSMD.LoadInventoryBasis`、`wsINV.LoadFGDInventory/LoadFGDInventoryComponent/LoadINVFGDInBasis/LoadINVFGDInDetailAndComponent/AddINVTransactionState/ExeINVTransactionState`、`wsWIP.LoadGoodBinState`、`wsSYS.LoadBin`，以及 `clsInventory.LoadFGDInventory/LoadFGDInventoryComponent/LoadINVFGDInBasis/LoadINVFGDInDetailAndComponent/ExeFGDIn/SetINVFGDInBasisState`。

## WinForms 行為

### 成品庫存查詢

1. Form 啟動時呼叫 `wsSMD.LoadInventoryBasis(InventoryType=1)`，準備成品庫 lookup；不預先載入主庫存列。
2. 使用者輸入 InventoryNo 後按 Enter 查詢，或按 `...` 從庫房清單選取。主查詢呼叫 `wsINV.LoadFGDInventory(InventoryNo)`。
3. Core 讀 `TBLINVFGDINVENTORY`，條件是 InventoryNo 非空且 `LocQty > 0`；Form 再套同一個 `LocQty > 0` 列篩選。
4. 主 Grid 顯示 InventoryNo、ProductNo、LocatorNo、LotNo、LocQty、UnitNo、BelongToType、BelongToNo、InputDate、FGDInNo。`BelongToType=0` 顯示 MO；數量最多 4 位小數，InputDate 顯示年月日時分秒。
5. 點選主列先清空下方明細，再呼叫 `wsINV.LoadFGDInventoryComponent(InventoryNo, LotNo, LocatorNo)`。有 Component 時只顯示 ComponentNo、GoodQty、ScrapQty、UnitNo；沒有 Component 才以 LotNo 呼叫 `wsWIP.LoadGoodBinState`，並依 `wsSYS.LoadBin` 的 BinOrder 動態建立 Bin 欄位。
6. 本 Form 可見操作是成品庫查詢、`FGD In`、`Close`；Designer 的 Find 預設隱藏。這裡沒有 IV501 的人工 Add/Edit/Del/Turn INV 操作。

### 成品入庫確認

1. `FGD In` 開啟 `frmINVFGDInConfirm`。使用者按 lookup 後呼叫 `wsINV.LoadINVFGDInBasis(State=0)`；Form 在前端排除 `ToERP=1`，按 FGDInNo 排序，lookup 顯示 FGDInNo／InventoryNo。
2. 選取單據後顯示 FGDInNo、InventoryNo、Description、Creator、CreateDate，並以 `wsINV.LoadINVFGDInDetailAndComponent(FGDInNo)` 載入 Lot 明細及 Component 子表；Detail 帶 ProductName，Component 帶 MinLifeGrade。
3. 按 Confirm 必須有 FGDInNo。Form 呼叫 `wsINV.AddINVTransactionState(Source=30, TicketNo=FGDInNo, Creator=登入者)`。Service 建立 TransactionID、寫交易 State、將 Basis 設為 State=1，接著同步呼叫 `ExeINVTransactionState`。
4. Source=30 的 Exe 分支由 Core `ExeFGDIn` 過帳，成功後 Basis 設為 State=2 並將 Transaction State 移至 Log；失敗分支會將 Basis 設為 State=3。
5. `ExeFGDIn` 依單據 Source=0／1、Lot 明細、Component、目標庫房與儲位更新成品庫存及相關 WIP／Lot 狀態。Source=1 明確讀取來源 WIP Inventory，檢查來源 Qty，再扣來源庫存、解除 BookingFlag，並更新 Lot Qty／Component／release history。這是正式庫存交易，不可簡化成只把單據狀態改為 Confirm。

## Service/Core 已知風險

- `AddINVTransactionState` 先把外層回應標為 success，再同步呼叫 `ExeINVTransactionState`；該內層呼叫包在空的 `catch` 中。若 Exe 過帳失敗，服務仍可能向 Form 回 success，而 Basis 已被設為 State=3。正式 API 不可沿用這種吞錯回應；必須回傳明確結果與可追蹤錯誤，避免用 UI toast 宣稱成功。
- 舊 Core 的多段 SQL／狀態寫入不是足以供新 API 信任的原子交易契約。家用端需在單一 PostgreSQL transaction 內重驗單據 State、目標／來源可用量、Locator capacity、Component／Lot 現況，使用冪等鍵，完整維護 inventory、來源庫存、Basis State、Transaction State／Log 與 Lot history。
- `LoadINVFGDInventoryBin`／JoinBin Core 方法雖存在，但 IV501 Form 此處實際透過 `LoadGoodBinState` 顯示 Bin。既有 WP605 MESTEST 核對記錄指出 `TBLINVFGDINVENTORYBIN` 不存在；不要因方法存在就把該表列為 IV501 必要表。
- 舊 Core 以字串組 SQL，正式 API 使用參數化查詢；不得接受瀏覽器傳入 Creator、State、TransactionID 或最後過帳數量作為權威值。

家用端以 0074 在核實缺表及完成備份後建立 FGD Inventory／Component、FGD／SEMI 入庫表、WIP Semi／Component、GoodBinState、System Bin、ReverseHistory 與包裝 lookup。來源欄位、鍵、索引與權限已 SSH 回讀；只建立空表。0075 只授予 `ymes_app` 對既有 `tblinvinventorybasis` 的 SELECT，讓成品庫房 lookup 可用。`TBLINVFGDINVENTORYBIN` 在 MESTEST 不存在，沒有建置。Source=30 API 及正式過帳尚未交付。

## YMES 家用端 API／schema handoff

1. 使用已存在的成品庫／FGD In／交易／Bin schema；live schema 已核對，沒有重複建表。0075 是既有庫房主檔的最小 SELECT 權限 migration，無新 CREATE SQL。
2. 提供登入與 IV501 Function ACL 保護的成品庫 lookup（`InventoryType=1`）、主查詢、Component 明細與 Lot Bin 明細 API。查詢限定有效 InventoryNo，保留 `LocQty > 0`；Component 非空時不再合併回傳 Bin，Bin 欄依授權的 system-bin metadata 排序。
3. FGD In 待確認清單取 State=0，並排除 `ToERP=1`、依 FGDInNo 排序。Detail API 必須要求有效 FGDInNo 並回傳對應 Component，空單號不可變成全表查詢。
4. 建立明確的 Source=30 confirm command：伺服器生成 TransactionID／冪等鍵，重驗 State=0、ToERP、來源及目標庫房／Locator 容量、Lot／Component／WIP 來源狀態；同一交易完成整批過帳、Basis State、Transaction State→Log 和錯誤回復。Source=1 須原子扣來源 WIP／SEMI、清除預約並維護 Lot／Component／history。
5. 對舊 Add Service 的「內部 Exe 失敗仍回 success」採明確錯誤結果和可重試／可查詢的交易狀態；不可只因收到舊 Service success 就回報過帳完成。

### 家用端唯讀 API（2026-11-26）

- 已新增登入保護的 `GET /api/inventory/fgd-inventory/lookups/inventories`：只列 `InventoryType=1`，固定排序並分頁，每頁最多 100 筆。
- `GET /api/inventory/fgd-inventory?inventoryNo=...` 必須指定成品庫房；伺服器再驗 `InventoryType=1`，只回傳 `LocQty>0` 庫存，明確排序，每頁最多 100 筆。
- `GET /api/inventory/fgd-inventory/{inventoryNo}/{lotNo}/{locatorNo}/details` 必須指定完整庫存鍵。若有 Component，回 Component 子列；沒有 Component 才回 Good Bin 數量與 `TBLSYSBIN` 定義。Good Bin 的來源欄名目前原樣回傳 `bin1`–`bin8`；尚未確認舊系統如何將 `BinNo` 對應至這八個欄位，因此不得直接把回應當成已完成的動態 Bin 標籤接線。
- `GET /api/inventory/fgd-inventory/confirmations` 只讀取 `State=0` 且 `ToERP<>1` 的 FGD In 待確認清單，按 `FGDInNo` 排序並分頁，每頁最多 100 筆。`GET /confirmations/{fgdInNo}` 必須指定單號，回父單、最多 500 筆 Detail、最多 5,000 筆 Component；不存在的單號回 404。
- 所有端點使用參數化 SQL 和登入保護。唯讀 API 已接 `/YMES/INV/FgdInventory` 正式頁並部署；僅 app-browser 確認正式庫房 lookup 沒有可選資料，待確認入庫 0 筆。FunctionKey 細部授權仍待接入，Source=30 過帳端點尚未建立。

### 正式站驗證（2026-11-26）

- 首次驗證發現 `ymes_app` 缺少 `YMES.tblinvinventorybasis` SELECT，已先做完整備份並以 0075 最小授權；資料表結構與業務列未變更。備份與 SQL checksum 見 [資料庫連線紀錄](../../DATABASE_CONNECTION.md)。
