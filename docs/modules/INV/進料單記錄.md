# IV207 進料單記錄（Material In Log）

- FunctionKey：`IV207`；FunctionNo：`MATERIAL IN LOG`；表單：`frmINVMaterialInLog`；分類：原物料倉。
- DEV 頁：`/YMES/INV/MaterialInLog`，Vue 功能選單鍵 `function:INV:MATERIAL IN LOG`。
- 範圍：只讀查詢進料單主檔和目前單據明細；不新增、修改、刪除、確認或列印。

## 原程式畫面與操作

畫面上方是 Query 條件區，下方依序為 MaterialIn Basis 和 MaterialIn Detail Grid。Form 載入時先取單號查找資料、`InventoryType=0` 原物料庫房和供應商清單，但不自動執行主查詢。使用者按 Query 後才載入主檔；選取主檔列後載入該單明細。畫面操作為 Query、三個 `...` 查找按鈕及 Close，沒有寫入、列印或匯出功能。

查詢條件為精確 `MaterialInNo`、`InventoryNo`、`VendorNo`，可選 State、From/End CreateDate 與 From/End INV Date。State 對應 `0=UnConfirm`、`1=Handling`、`2=Confirm`、`3=Fail`；WinForms 以 ValueList 項目的 SelectedIndex 傳 0–3。未指定的條件不加入查詢。

主 Grid 顯示 `MaterialInNo`、`InventoryNo`、`VendorNo`、`State`、`ConfirmDate`、`Description`、`Creator`、`CreateDate`。明細 Grid 顯示 `MaterialNo`、`MaterialLotNo`、`UnitNo`、`LocatorNo`、`LimitTime`、`Qty`；Core 另外 left join `TBLMTLMATERIALBASIS` 的核准物料名稱，但 Form 將 `MaterialName` 隱藏。來源沒有指定主檔或明細排序，也沒有分頁／筆數限制。

日期條件由 Core 處理：CreateDate 範圍比對主檔 `CreateDate`；只提供起日或迄日時，另一端分別補 `2000/01/01` 或 `3000/01/01`；日期型迄日延長到當天 `23:59:59`。INV Date 範圍不是主檔 ConfirmDate，而是用 `TBLINVTRANSACTIONLOG` 中 `Source=0` 且 `CreateDate` 落在區間的 `TicketNo` 篩選 MaterialInNo。

## Core 行為與家用端注意事項

- `LoadINVMaterialInBasis` 以 `TBLINVMATERIALINBASIS` 為主表，依上述精確條件組查詢；`LoadINVMaterialInDetail` 查 `TBLINVMATERIALINDETAIL`，並 left join `TBLMTLMATERIALBASIS` 且限 `IssueState=2`。詳細欄位由資料表回傳，再由 WinForms 顯示白名單欄位。
- 舊 Core 將條件串成 SQL，並接受 `AdditionalXml`；正式 API 應使用參數化條件，不接受前端任意 SQL／AdditionalXml。主查詢要有明確排序與分頁／上限，避免空條件掃描大量歷史資料。
- 舊 Form 在查詢結果為零筆時會呼叫 `LoadDetail("")`；群組列啟用時也呼叫 `LoadDetail("")`。Core 對空 MaterialInNo 不加單號限制，可能回傳整張明細表。這是舊程式的過度查詢風險；正式 API 和 DEV 預覽均應要求有效 MaterialInNo 才載入明細，查無主檔時回傳空清單。
- 主檔與明細欄位是查詢投影，不代表本功能可改資料。所有正式端資料以登入身分及 `IV207` 功能權限保護；不可把使用者提交的 Creator、State 或額外 SQL 條件當作可信資料。

## Vue DEV 頁

- `web/src/components/InvMaterialInLog.vue` 是路由入口；只有 Vite DEV 且 `developmentPreview=true` 時載入 `InvMaterialInLogDevPreview.vue`，其他環境顯示尚未開放提示。

- DEV 假資料固定在元件內，不使用 localStorage、不呼叫 MES／Oracle／YMES PostgreSQL／正式 API。查詢結果排序僅為 fixture 宣告順序，並非舊 Core 保證的排序。
- 未模擬完整 `frmCOMSearch` 欄位、使用者 Grid layout、遠端查詢錯誤、正式權限、分頁或大量資料；不顯示全表明細，也不提供實際匯出／報表。

## 資料表、DDL 與 Oracle 查證

查詢直接依賴 `TBLINVMATERIALINBASIS`、`TBLINVMATERIALINDETAIL`、`TBLINVTRANSACTIONLOG`，並連結 `TBLMTLMATERIALBASIS`；庫房與 Vendor 查找由現有 Service 提供。Repo 未找到可核對本版本 `TBLINVMATERIALINBASIS`、`TBLINVMATERIALINDETAIL` 的 Oracle source DDL／metadata，也沒有相應 PostgreSQL CREATE-only。`TBLINVTRANSACTIONLOG` 可沿用 WP605 已提交的 `database/reference/mestest_wip_wp605_source_ddl.sql` 及 `database/reference/mestest_wip_wp605_create.sql`。

公司桌機受保護 Oracle profile／attachment 不存在，未使用 ODP.NET 查 MESTEST，也未查業務資料。不可由 Core SELECT 欄位推測主檔／明細的型別、長度、nullable、default、PK/FK/index；缺少兩表可信 DDL 時不產生推測 CREATE SQL。

## 家用端 API／schema handoff

- 先 pull 最新 `main` 並核對 PostgreSQL live schema／migration。確認兩張 MaterialIn 主／明細表的現況；若缺表或欄位，再取得受保護 MESTEST 的原生 DDL／metadata。Transaction Log 優先核對 WP605 的來源 DDL及既有 live schema，不重複猜建表。
- 提供登入與 `IV207` Function ACL 保護的主檔查詢，支援精確單號／庫房／Vendor／State、CreateDate、Source=0 INV TransactionLog 日期範圍。建議以明確的穩定排序、最大頁數和伺服器端上限回傳，並讓日期條件採含起日、含迄日的 date-only 語意。
- 明細 API 必須以路由 MaterialInNo 為必要條件，例如 `GET /api/inventory/material-in/logs/{materialInNo}/details`；無主檔或無明細回傳空陣列。不要提供可略過單號限制的明細全表查詢。主檔與明細都只讀。
- 對 `FromINVDate`／`EndINVDate` 使用 `TBLINVTRANSACTIONLOG` 的 `Source=0`、`TicketNo` 與 `CreateDate` 關聯；避免把 `ConfirmDate` 當成 INV Date。Lookups 重用已存在的庫房（InventoryType 0）和 Vendor API；舊畫面 Vendor lookup 是全清單，不應自行套用 IssueState=2，除非家用端已有明確產品規則。
- 無本模組可提交的 CREATE-only SQL，直到取得兩張 MaterialIn 表可信結構或核對 live schema。公司端未連 YMES PostgreSQL，未新增 schema/migration 或實作正式 API。
