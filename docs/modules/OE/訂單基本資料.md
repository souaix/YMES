# OE101 訂單基本資料

- 選單為「工單管理 → 訂單 → 訂單基本資料」，FunctionNo `RO BASIS`，FunctionKey `OE101`。Vue 入口為 `/YMES/OE/ReceivingOrders`。
- 已讀 `STD/MESWin/OE/OE_ROBasis` 下的 `frmROBasis`、`frmROBasisDef`、`frmRODetail`、`frmRODetailDef`、`frmROPropertyDef`。舊專案的 Designer 區域內嵌在各 VB 表單。服務為 `STD/MESws_STD/wsSTD/wsOE/wsOE.cs`。Core 為 `STD/MESkc/kcOE/clsOEBasis.cs` 及 `kcBasis_UPD.clsBasis_UPD`。

## 原 MES 互動

- 主畫面預設未簽核，四種 IssueState 為 0 未簽核、1 簽核中、2 已簽核、-1 不使用。查詢欄為 RONo。清單顯示 RONo、CustomerNo、ROState、說明及建立／修改資料。ROState 是另一個狀態欄，標準顯示 0 未確認、1 簽核中、2 確認、99 結案，正式顯示由 `TBLSYSVALUELIST` 供應。Designer 有新增、修改、刪除、複製、核准、明細、關閉。
- 主檔定義要求 RONo、CustomerNo。可加減屬性；編輯讀 `LoadROProperty_Recive`。Service Add/Edit 在同一交易更新主檔、接收屬性及 `UpdROProperty_ROCreate` 指定的對應欄位。Edit 傳舊 DataStamp，並經共用 Issue Control。
- 舊 Copy 先新增新 RONo，再呼叫 `CopyROBasis` 複製明細，Core 全量重建目標明細並將未開單量設為訂單量。舊 Service 會吞掉明細複製例外。YMES 交接採整筆原子複製，避免留下半筆訂單。
- 明細由 RONo 載入。同一訂單的 ItemNo 在標準型態為 0–99，現場 Oracle 是 NUMBER(2,0)。主檔 IssueState 非 0 時明細唯讀。明細含產品、客戶、訂單類型、訂單量、訂單單位、優先序、計價資料、訂單日期及說明。產品、客戶與單位來源為 PRD、ENT、SYS，OrderType 用 `ValueListProvider("tblOERODetail", "OrderType", True)`。
- 核准需至少一筆明細。Form 檢查必需屬性 `Controlled=1`、允許經確認略過的屬性 `Controlled=2`。Service `ApproveROBasis` 進 Issue Job，有設定時 IssueState／ROState 置 1，無 Job 或明細時置 2。核准 callback 同設兩欄為 2；可見退回 SQL 只把 IssueState 置 0。
- 刪除依原 IssueState 分支，0／-1 硬刪，2 以 DataStamp 轉 -1，1 拒絕。Core 硬刪前查 `TBLOEMOBASIS.RONO`，已開工單時拒絕，通過後在同一交易刪兩張屬性表、明細和主檔。

## Oracle 結構

MESTEST 以 PowerShell 5.1 + Oracle.ManagedDataAccess 唯讀擷取四張表的 DBMS_METADATA DDL，另核對欄位、鍵與索引。四張表各有主鍵及其唯一索引，字典未顯示其他索引或外鍵。

| 表 | 主鍵 | 備註 |
| --- | --- | --- |
| `TBLOEROBASIS` | RONO | VARCHAR2(25)，ROState 預設 0，DataStamp NUMBER(11,0) 預設 0 且可 NULL |
| `TBLOERODETAIL` | RONO, ITEMNO | 數量 NUMBER(12,4)，單價 NUMBER(8,2)，DataStamp 可 NULL |
| `TBLOEROPROPERTY` | RONO, PROPERTYNO | PropertyValue 可 NULL，另含 LotSerial |
| `TBLOEROPROPERTY_RECIVE` | RONO, PROPERTYNO | 保留 Oracle 來源拼字 |

## 家用端 API 交接

建議路由 `/api/oe/receiving-orders`。GET 集合以 RONo 篩選、IssueState 篩選並穩定排序；GET 單筆附接收屬性，`/{roNo}/lines` 提供明細。POST／PUT 處理主檔與屬性，`/{roNo}/copy` 以新 RONo 原子複製，`/{roNo}/approve` 執行正式簽核。明細以 `/{roNo}/lines/{itemNo}` 定位。DELETE 應依伺服器重查的 IssueState 刪除或停用。

- 寫入前以相同交易鎖主檔並重查狀態。使用 nullable DataStamp 的 CAS，留意舊 NULL 不可等同 0。硬刪的工單引用檢查須與工單建立共用鎖次序。正式轉態以已儲存的訂單狀態為準。
- API 明細應保留顯示用數量、BookingFlag／ShippingFlag、建立／修改欄位，並用十進位驗證精度、範圍與未開單量。整合真實客戶、產品、單位、幣別、OrderType ValueList 和可受控屬性規則後，再開放正式寫入。
- Oracle 的 `AdditionalXml`、企業客製分支、屬性跨欄位對應及正式簽核在家用端整合。正式端需先比對現行 PostgreSQL schema 與 migration history。

## 公司端 DEV 範圍

- 清單查詢、四狀態、訂單和屬性維護、複製、核准、刪除／停用、訂單明細獨立新增／修改／複製／刪除，皆使用 localStorage 的假資料。套用後保持編輯，確認後關窗。使用共用站內確認窗。
- DEV 使用 RONo 不分大小寫的字面包含、單筆選取和固定候選資料。DEV 核准要求至少一筆明細後直接轉 2，並以假資料模擬工單擋刪。正式 Issue Control／Job、批次選取、受控屬性提示、客戶／產品／字典查找及廠別特例待正式整合。
