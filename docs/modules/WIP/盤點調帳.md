# WP608 盤點調帳

## 復刻範圍

公司端以 DEV 假資料復刻 `frmInvCountStateAdjust` 主畫面、`frmInvCountAdjust` 生產批數量視窗、`frmInvCountAdjust_MTL` 物料庫存視窗及 `frmInvCountAdjust_PRD` 產品庫存視窗。對照 Service `LoadInvCountStateWithDetail`、`ExeInvCountAdjust`（含 `_MTL`／`_PRD`）與 `ExeInvCountConfirm`，以及 Core `clsINVCount`。未呼叫正式 Service、資料庫或印表機。

功能未掛入正式 `MenuItem`。Vue DEV fallback 路由：`/YMES/WIP/InvCountStateAdjust`。

## 六種盤點資料

| DataType | 主畫面盤點鍵 | 調帳明細 | Confirm 更新範圍 |
| --- | --- | --- | --- |
| WIP | LotNo、OPNo、MO、ProductNo／Version | 生產批盤點 detail | LotState CurQty／SysQty |
| SEMIWIP | LotNo、OPNo、MO、ProductNo／Version | 生產批盤點 detail | LotState CurQty／SysQty，並更新線邊 `TBLINVWIPINVENTORY_SEMI.Qty` |
| FGD | InventoryNo、LocatorNo、LotNo、ProductNo | 產品庫存盤點 detail | FGD 儲位 LocQty |
| SEMI | InventoryNo、LocatorNo、LotNo、ProductNo | 產品庫存盤點 detail | SEMI 儲位 LocQty |
| RAW | InventoryNo、LocatorNo、MaterialNo、MaterialLotNo | MTL 盤點 detail | RAW 儲位 LocQty 與原物料庫 CurQty |
| MTLWIP | InventoryNo、MaterialNo、MaterialLotNo | MTL 盤點 detail | 線邊 WIP 原物料 Qty |

主 Form 的六個選項分成 WIP／SEMIWIP、生產產品 FGD／SEMI，以及原物料 RAW／MTLWIP。Query 以盤點批次 `State=0` 讀取已關帳資料，再依資料型別排序；生產批視窗以人工輸入 LotNo，原始碼的 Lot lookup 按鈕已註解。產品與物料視窗提供 Inventory／Locator／Lot／Material 查找。

## 調帳與確認

1. 只對 `State=0` 的盤點批次載入明細；主 Grid 顯示盤點時間、對應 Lot／庫存鍵、CurQty／CurUnit、NewCurQty、AdjustQty、調帳人員／時間及 AdjustState。
2. 選一筆明細開啟對應編輯視窗，輸入非負數且不等於 CurQty 的 NewCurQty。`AdjustQty = NewCurQty - CurQty`；Apply 儲存後仍留在視窗，確定則儲存並關閉，兩者都只將明細 `AdjustState=1`。
3. Confirm 以第一筆顯示列的 CountSerial 和 DataType 呼叫 Service。Service 選出該盤點批次所有 `AdjustState=1` 明細，逐筆執行 Core 更新庫存，再將該 detail 標記 `AdjustState=2`。
4. WIP 的 SysQty 依 CurUnit／SysUnit 換算；SEMIWIP 還同步更新線邊庫存。FGD／SEMI／RAW 先比對目前儲位數量是否仍等於盤點時 CurQty，避免直接覆蓋盤點後已變動的庫存。MTLWIP 亦以盤點數量比對目前線邊原物料數量。
5. Print 依資料類型選 General、MTL 或 PRD ActiveReport。DEV 僅顯示預覽並記錄模擬列印，不呼叫本機印表機。

## 靜態檢閱發現

- Service 逐列呼叫 Core；Core 多表更新沒有有效 transaction／rollback 保護。多筆 Confirm 中途失敗可能已更新部分庫存與 detail，家用端需改成單一本地交易，或明確設計可恢復的逐列命令與結果紀錄。
- `ExeInvCountConfirm` 對外只收到第一列 CountSerial；若畫面同一 DataType 混有多個盤點批次，確認範圍可能和使用者在 Grid 暫存的列不一致。正式 API 應要求明確單一 CountSerial，或把明細鍵集合明確送入且伺服器重新驗證。
- 編輯視窗沒有版本條件；Confirm 的庫存比對只覆蓋部分庫存類型。正式 API 應對所有更新的明細和目標庫存列加版本／數量 CAS，並記錄操作者與差異。
- MTL Form 組送 Service 的欄位名稱誤將 `MaterialLotNo` 設成 `LocatorNo`，Service 期待 `MaterialLotNo`；照原字面送出可能無法取得物料批號。DEV 以正確欄位互動，正式端應修正 request contract 並保留來源缺陷紀錄。
- MTL Form 的初始化反選比較也把 `MaterialLotNo` 與 `LocatorNo` 混用，可能讓重新選取列無法正確反映；DEV 不重現此錯誤。
- SEMIWIP 單位換算在 DEV 只用示例資料中的 2:1 比率；正式端必須從 MES 單位換算規則取得係數，不可固定使用此數值。

## 資料表與家用端 handoff

原始碼直接使用四張盤點 state／detail 表：`TBLWIPINVCOUNTSTATE`、`TBLWIPINVCOUNTDETAIL`、`TBLWIPINVCOUNTDETAIL_MTL`、`TBLWIPINVCOUNTDETAIL_PRD`。共用目標庫存至少包括 `TBLWIPLOTSTATE`、`TBLINVWIPINVENTORY_SEMI`、`TBLINVFGDINVENTORY`、`TBLINVSEMIINVENTORY`；RAW／MTLWIP 目標表依 Core 的實際 SQL 建立映射。

在 `database/reference/`、既有模組文件及 SQL references 中沒有找到本功能四張盤點表的 Oracle DDL／metadata；桌機沒有可用受保護 Oracle profile，故未查詢 Oracle，也未猜測或產出 PostgreSQL CREATE-only SQL。已存在的共用庫存 reference 沿用 WP101／WP201；不得為本功能重建。

家用端先查 PostgreSQL live schema 和 migration history，再依實際列名與 PK/index/constraint 補 migration（僅當 live 缺表）；實作登入／ACL 保護的讀取、暫存、批次確認及報表資料 API。確認命令須指定 CountSerial+DataType、在交易內鎖定並重讀盤點 detail 與庫存，驗證 `State=0`、`AdjustState=1`、未改變的 CurQty／版本和非負 NewCurQty，按型別更新所有相依庫存、寫 AdjustState=2 與 audit；任何失敗整批 rollback。不要把桌機假資料頁視為正式 API 或 schema 驗收。
