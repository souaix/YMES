# WP215 元件分片處理（LOT COMP SPLIT）

## 功能與原生來源

- 選單：在製品管理 → 生產報工 → 元件分片處理；FunctionNo `LOT COMP SPLIT`、FunctionKey `WP215`、Form `frmSplitComponent`、DLL `WP_SplitComponent.dll`。公司 Vue DEV 頁：`web/src/components/WipComponentSplit.vue`，路徑 `/YMES/WIP/ComponentSplit`。
- WinForms：`STD/MESWin/WIP/WP_SplitComponent/frmSplitComponent.vb`。Service：`STD/MESws_STD/wsSTD/wsWIP/wsWIP.cs` 的 `InitRunSplitComponentNo`、`EXE_SplitComponent` 及 `LoadLotBasisJoinState`／`LoadComponentState`／`LoadComponentProperty`；載具查找使用 `wsEQP.LoadCarrierState`／`LoadCarrierStateDetail`。Core：`STD/MESkc/kcWIP/clsWIP.cs` 的 `InitRunSplitComponentNo`、`EXE_SplitComponent`，另呼叫 `kcWIP.clsLot` 的客製欄位、TestSummary、LotStamp helper。

## WinForms 版面、查詢與預覽

原視窗標題 `SplitComponent`，ClientSize 669×451。上方 `GroupBox1` 有黃色 Lot No 輸入、`ComponentState` Grid（ComponentNo、GoodQty、ScrapQty）及 `Select`。Lot No 按 Enter 載入元件；原 `btnGET1_Click` 有搜尋程式碼但沒有 `Handles` 綁定，Designer 也未加入對應可見按鈕，因此不能宣稱原畫面有可用的 Lot 查找。載入時 `LoadLotBasisJoinState` 查 Status 0／1／4／5、HaveComponent=1、LotState=1；沒有限 HaveLevel。點選來源元件列會清除下方草稿，`Select` 填入 ComponentNo、原 GoodQTY／ScrapQTY 並預設 Split Comp Count=2；雙擊列會填入但 Count=0。

下方 `SplitComponent` 群組有 ComponentNo、黃色 Split Comp Count、只讀 GoodQTY／ScrapQTY、`SplitWafer` 與新元件 Grid。Grid 可見欄為 ComponentNo（灰底唯讀）、GoodQty、ScrapQty；`CarrierNo` 雖在 DataTable／Service 中，原 Grid layout 設 `.Hidden=True`。`AreaQty` 控制也 `Visible=False`，相關數量計算被註解。底部 Confirm、Close。整體使用黃色輸入底色，沒有桃紅或藍色主檔表頭。

`SplitWafer` 先查 Lot 是否在 CarrierState 或 CarrierStateDetail，若是即拒絕並提示使用載具分批功能；Split Comp Count 必須為 2–26 的數字。Form 以來源 ComponentNo 前綴搭配字母尾碼產生新編號，透過 `InitRunSplitComponentNo` 查 `TBLWIPCOMPONENTSTATE`／`TBLINVWIP_COMPONENTSCRAP` 的既有最大尾碼。原演算法混合 `MAX`、`Asc`、`Chr` 與對 I/O 的特例，跨資料庫排序、尾碼耗盡及併發唯一性不能直接照搬；正式編號由 server 在交易內保留。新 Grid 初始 GoodQty／ScrapQty 為 0，由操作者逐列填寫。

## Confirm 與交易副作用

Form Confirm 要求至少一筆新元件；各列 GoodQty／ScrapQty 不能負數，且不能同時為 0，非空 CarrierNo 不可重複；新列 GoodQty 合計要**等於**來源 GoodQty，新列 ScrapQty 合計要**等於**來源 ScrapQty。`funChkNewComponent` 僅要求新 GoodQty 大於 0、且兩種數量小於等於來源，呼叫處已註解，**不是**實際 Confirm 規則。Form 送 LotNo、LotStamp、來源 ComponentNo 與每列 ComponentNo／GoodQty／ScrapQty／CarrierNo 到 `wsWIP.EXE_SplitComponent`；成功後重新載入 Lot 查詢資料，再清空表單，避免同一來源重複分片。

Service 將 XML 轉 DataTable，加上 UserNo，呼叫 `clsWIP.EXE_SplitComponent`。Service 的每列缺欄判斷使用三個 `Count==0` 的單一位元 `&`，只有**三欄都缺**才拋提示，隨後仍直接取各節點；正式 API 應逐欄驗證。Core 讀 LotState／ComponentState／ComponentProperty／CarrierStateDetail；站中另讀 Temp/Cont ComponentAttrib 與 Cont Component。來源環境若存在 `TBLWIPCOMPONENTBASIS`，亦繼承其欄位。逐新元件插入 ComponentState／Property／Basis，站中複製並改寫 `CGOODQTY`／`CSCRAPQTY` 及 Cont Component。SEMI_WAFER 或 LED_PKG 配置時呼叫 `funSHR_Inherit_TestSummary`。然後 LotState.CurQty 改為舊值 - 1 + 新元件數，刪來源 ComponentState／Property／Basis，站中更新 Temp_LotState 並刪來源 Temp/Cont ComponentAttrib；若來源有 CarrierStateDetail，下載具、寫 DetailLog、將 CarrierState 設空。最後更新 ReverseHistory 的 CommitState／CommitDesc，將 `ChkLotStamp_RowCount` 加入 SQL collection，交 `ExecuteSQLNoneQuery_ChkRowCount` 執行。

**正式 API 要補的守門：** Core 方法本身未重算新列 GoodQty／ScrapQty 合計，也未檢查新編號唯一性或來源元件現況完整性；原 Form 的守門不可作為正式可信邊界。需交易中重讀 LotStamp、來源 GoodQty／ScrapQty、元件歸屬、載具現況與命名空間，對每列非負／非全零、總量完全守恆、精度／欄長及數量 2–26 做 server 驗證。來源有 Carrier 時，Form 的 SplitWafer 拒絕；Core 有卸載具處理，但新元件上載具 SQL 目前是**註解**，Grid CarrierNo 也隱藏。正式先維持無載具操作；若業務需要帶載具分片，需明確設計與驗證，不能把目前 Core 註解當生效功能。`funGetStateCode` 回傳值在 `btnSplit_Click` 取出後未使用，不能當預覽保護。

## Oracle DDL 與 CREATE SQL

兩個 Core 方法字面直接引用 14 張實體表：`TBLINVWIP_COMPONENTSCRAP`、`TBLSYSFUNCTION`、`TBLWIPCARRIERSTATE`、`TBLWIPCARRIERSTATEDETAIL`、`TBLWIPCARRIERSTATEDETAILLOG`、`TBLWIPCOMPONENTBASIS`、`TBLWIPCOMPONENTPROPERTY`、`TBLWIPCOMPONENTSTATE`、`TBLWIPCONT_COMPONENT`、`TBLWIPCONT_COMPONENTATTRIB`、`TBLWIPLOTSTATE`、`TBLWIPREVERSEHISTORY`、`TBLWIPTEMP_COMPONENTATTRIB`、`TBLWIPTEMP_LOTSTATE`。其中 12 張已有 `database/reference/` Oracle source DDL／PostgreSQL CREATE-only，分別沿主檔／WP101／WP201／WP302／WP603 等 refs。`tblCompState`、`tblCarrierStateDetail` 等是 Core DataSet 暫存別名，不是額外 DB 表。

缺參考的兩張已由公司端用 Windows PowerShell 5.1、ODP.NET 與受保護 MESTEST profile **唯讀**取得 `DBMS_METADATA.GET_DDL` 及 `ALL_TAB_COLUMNS`／`ALL_CONSTRAINTS`／`ALL_INDEXES`／`ALL_TRIGGERS`：`TBLWIPCOMPONENTBASIS` 32 欄、PK `COMPONENTNO`、無 FK／trigger／其他 index；`TBLWIPREVERSEHISTORY` 11 欄、複合 PK `(LOTNO,REVERSEID)`、另有非唯一 `LOTSERIAL` index、無 FK／trigger。來源表 DDL、index DDL、metadata 與 PostgreSQL CREATE-only 分別為 `database/reference/mestest_wip_wp215_source_ddl.sql`、`mestest_wip_wp215_source_indexes.sql`、`mestest_wip_wp215_metadata.txt`、`mestest_wip_wp215_create.sql`。CREATE-only 是結構參考，家用端先比對 live PostgreSQL schema/history，確實缺表才做 forward migration；`TBLWIPCOMPONENTBASIS` 在 Core 為存在才繼承的可選分支，不應無條件強制所有部署建立。未讀 Oracle 業務列、未執行 DDL/DML、未連 YMES PostgreSQL、未把憑證放入 repo。

## 公司 DEV 與家用端 API handoff

DEV `DEV-LOT-215` 有兩顆無載具元件，`DEV-LOT-215-CAR` 示範拒絕。頁面讓使用者按 Enter 載 Lot、選元件、以 2–26 產生 A–Z 尾碼、逐列編輯 GoodQty／ScrapQty；Confirm 驗證非負／非全零、四位小數及兩種總量守恆，更新 DEV Lot CurQty／LotStamp 並可再分片。假狀態只寫 `ymes-dev-mock:wip-component-split:state:v1`；正式 non-DEV 禁用 fixture 與 Confirm。DEV 的尾碼生成不查真 Scrap／跨系統元件命名空間，沒有模擬所有客製 TestSummary／Reverse／Carrier 副作用。本輪依既有使用者約束未執行 build/test/browser。

建議正式契約：`GET` 可執行 Lot 與元件現況、來源版本及 Carrier 檢查；`POST` 以 LotNo、來源 ComponentNo、LotStamp、分片列的 GoodQty／ScrapQty 為輸入，server 產生或原子保留新 ComponentNo。若保留前端編號預覽，POST 仍須以唯一鍵與鎖重驗。API 回傳新元件編號、數量、新 LotStamp、CurQty 與可查交易 ID，不信任 browser 送的 UserNo、CarrierNo、源數量、模組或時間。站中 Temp／Cont、可選 ComponentBasis、SEMI／LED TestSummary、ReverseHistory 及 LotState/ComponentState 必須同一交易處理；失敗回滾，重試防重。家用端負責 live schema、migration、正式 API 與驗收。
