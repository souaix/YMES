# WP503 批次立即異常設定（IMMEDIATE HOLD SET_BATCH）

## 來源與範圍

- 選單：WIP → 異常與等待 → 批次立即異常設定；FunctionNo `IMMEDIATE HOLD SET_BATCH`，WinForms `WP_ImmediateHoldSet_Batch.dll`。
- 主視窗 `STD/MESWin/WIP/WP_ImmediateHoldSet_Batch/frmImmediateHoldSet_Batch.vb` 與內嵌 Designer；獨立彈窗為同目錄 `frmBRERFCreate_Batch.vb`，不可直接沿用 WP501 的 `WP_BRERFCreate`。
- Service `STD/MESws_STD/wsSTD/wsWIP/wsWIP.cs` 的 `Exe_ERF_Create_Batch`；Core `STD/MESkc/kcWIP/clsLot.cs` 的 `UpdERF_Create_Batch`。此 Core 也供 Future Hold 使用，必須以 `ERFType` 分支判斷實際表依賴。
- 本交付為公司端 Vue 3 DEV 假資料及 API/schema 規格。正式 API、PostgreSQL migration、上傳與報表由家用端接手。

## 主畫面

主 Form 標題 `Batch Immediate Hold Set`，ClientSize 1008×591。`Lot Query` 有 RO No、MO No、Product No、Area No、OP No、LotNo、Customer No、PS No、Equipment No、Component No，另有 CheckInTime From/To；RO/MO/Product/Area/OP/Customer/Equipment 有查找 `...`。Query 至少輸入一項，僅同時指定時間起訖時要求起點早於終點。ComponentNo 查詢先找對應 Lot，再進 LotBasisJoinState；設備條件會查目前 `TBLWIPTEMP_EQUIPMENT`，指定時間時亦查 `TBLWIPLOTLOG_REPORT` JOIN `TBLWIPCONT_EQUIPMENT`，結果是目前或歷史曾上該機的 Lot。正式 API 不可接收或拼接 WinForms 的任意 SQL Additional。

查詢依系統參數 `ERFMultipleHold` 決定 Status：`1` 可含 `0/1/3/4`；否則 `0/1/4`。另要求 `LotState=1`、`CurQty>0`；排除 `PartialMode=1` 且非 Queue 的列，依 LotNo 排序。Grid 16 欄：勾選、LotNo、HotLot、OPNo、Status、CurQty、CurUnitNo、SysQty、SysUnitNo、HoldTimes、MONo、ProductNo、ProductVersion、ModuleNo、ModuleVersion、ModuleStageNo。HoldTimes 可開未結案異常單；Select All、UnSelect All 只作用於目前結果。底部 Hold Set、Close。外部 IPQC 以 `ERFLotNo` 呼叫時，所選必須包含該批；一般選單入口沒有此參數。

Hold Set 至少選一批，依 LotNo 排序，不能混合 PartialMode。第一批成為 RefLotNo/OPNo，開 `frmBRERFCreate_Batch`，`ERFSource=0`、`ERFType=6`。關彈窗後重查；來源沒有主畫面選取時的包裝預檢，不能把 WP501/WP502 的包裝守門當成 WP503 已有規則。

## Batch ERF 彈窗與交易

彈窗的 Lot State 區顯示 RefLotNo、OPNo、ProductNo、其他被選批號的 Lot Detail；元件清單由**所有選取批**載入。主次分類、Hold Description、HoldItem、HoldReason、Lot/Component、Area、附件、Release EQP/Equipment State、Confirm/Close 位於 ERF 區。Lot 模式加入原因時 ComponentNo=`N/A`；Component 模式才對勾選元件逐項加原因。Area 空白時儲存 `N/A`；相同 HoldItemNo+ComponentNo+AreaNo 不重複加入。Confirm 必須有 ERFNo、MClassNo、非空 HoldDescription、至少一筆 HoldReason；OCAPNo 有值會拒絕（此批次窗不支援 OCAP）；Release EQP=Yes 必須選 Equipment State。只有站中批且實際上機時才開放設備釋放，預設受 `ERFEQPReleaseAlwaysFalse` 控制。

`ERFBatchHoldGenType` 來自系統參數：

| 值 | 視窗呼叫 | Core 行為 | 批次表 |
| --- | --- | --- | --- |
| `0` | 一次送全部 Lot，參考批共用一張 ERF | `ERFType=6`，一次組交易 SQL | 每批寫一筆 `TBLWIPERFBATCHLOT`，`RefLotFlag` 僅參考批為 1 |
| `1` | 依選取順序逐批送 Service，每次一批及新 ERFNo | Core 把 `ERFType=6` 改為 `2`（Immediate Hold） | 不寫 `TBLWIPERFBATCHLOT`；每批有自己的 ERF |

一單一批時，彈窗會依執行 Lot 保留 `ComponentNo=N/A` 的原因，帶元件號的原因只保留該批實有元件；一單多批共用全部原因。兩模式都會依 HoldItem `CreateERF` 決定報表與附件，進 Service 前處理使用者附件、PDF、ERFNo，再寫 Lot/ERF 交易。原視窗 mode `1` 逐批呼叫，中途錯誤會保留先前已成功批；不得向使用者回報全批成功。Core 在每批檢查 LotStamp、寫 LotState/Log、ERFBasis、HoldReason/Disp、Reverse/ReleaseLog、附件關聯；網狀製程 Partial 有 OPNo 與狀態特別處理。`ERFType=3` 的 FutureHoldReason/Log 清理在同一 Core 方法內，但 WP503 實際傳 `6`（或轉為 `2`），該分支**不會執行**。

## 資料表與 SQL 交接

WP503 新缺的直接表 PostgreSQL CREATE-only 參考是 [`mestest_wip_wp503_create.sql`](../../../database/reference/mestest_wip_wp503_create.sql)：`TBLWIPERFBATCHLOT` 六欄，PK `(ERFNO,LOTNO,OPNO)`。Oracle 來源 DDL 已在 [`mestest_qc409_wip_disposition_dependencies_source_ddl.sql`](../../../database/reference/mestest_qc409_wip_disposition_dependencies_source_ddl.sql)，不重複提取。ERFBasis／HoldReason／HoldReasonDisp／AttachFile 使用 WP501/QC409 refs；LotBasis/State/Log/Temp/登入狀態使用 WP101/WP201/WP305 refs；USRUserBasis 在首批表；QC FirstGroup/HoldDispGroup、主次分類/HoldItem 已有 QC refs。主 Form 設備歷史查詢三表也已有 WP201/WP305 refs。其他 helper/adapter、Reverse/ReleaseLog 仍需家用端根據部署版本追蹤，不能以直接表盤點宣稱正式資料結構完整。

公司端另唯讀取得 `TBLWIPFUTUREHOLDLOG`、`TBLWIPFUTUREHOLDREASON` 的 MESTEST 結構，因它們屬同一 Core 的 `ERFType=3` 路徑；**不列為 WP503 migration**，留待 Future Hold 功能規格處理。公司端未查 Oracle 業務列、未執行 Oracle DDL/DML、未連 YMES PostgreSQL。

## Vue DEV 與正式 API

公司端 Vue 頁 `/YMES/WIP/BatchImmediateHold` 位於 `web/src/components/WipBatchImmediateHold.vue`，使用 `ymes-dev-mock:wip-batch-immediate-hold:state:v1`。RO-501 可查兩批，示範 Select All、彈窗、0/1 模式、分類／原因、版本重查、假 ERFNo、批狀態與 HoldTimes；所選模式在 DEV 彈窗可切換，正式值由 server 系統參數決定。DEV 以 Running+EquipmentNo 近似「上機」來展示 Release EQP，假 Equipment State 選項不是正式碼表；Equipment/CheckIn 查詢僅查假資料欄位，沒有歷史 JOIN。附件只記檔名，不上傳、產 PDF、寄信或執行 Reverse/ReleaseLog；無真實 IPQC 入口。正式 non-DEV 頁不讀假資料、不回報假交易。公司端依交接規則只做靜態核對，未執行 build/test/browser。

家用端 API 需提供授權且分頁的 Lot 候選／lookup、ERF 主次分類及 HoldItem、設備狀態、元件與 Area；嚴格重建上述查詢，尤其 `ERFMultipleHold`、Partial 與設備時間範圍。POST 由 server 讀 `ERFBatchHoldGenType`，接受 LotNo+OPNo+版本及明確原因／附件資訊；鎖定重查所有批、RefLot、元件、LotStamp、ERFNo 分配、權限、設備釋放與系統參數。模式 0 要整單原子；模式 1 需明定是全批原子，或相容逐批並回傳逐筆成功/失敗及冪等鍵。ERFNo、UserNo、時間和狀態不可相信 browser 值。PG live schema/history 先核對，僅對實際缺項做 forward migration；不能直接執行 CREATE-only 參考覆蓋既有結構。正式附件/PDF/通知需交易外補償或 outbox，SQL 必須參數化，不沿用舊 Core 字串拼接。
