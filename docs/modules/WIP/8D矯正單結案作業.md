# WP803 8D 矯正單結案作業（8D CLOSE）

## 來源與界線

- 選單：WIP → 8D 管理 → 8D 矯正單結案作業；FunctionNo `8D CLOSE`，FunctionKey `WP803`，`WP_8DClose.dll`。
- 主窗 `STD/MESWin/WIP/WP_8DClose/frmWP8DClose.vb`，編輯窗 `frmWP8DCloseDef.vb`，Service `STD/MESws_STD/wsSTD/wsWIP/wsWIP.cs`，Core `STD/MESkc/kcWIP/clsWIP.cs`。進頁前 D8 由 [WP802](8D矯正單維護作業.md) 產生結案申請；來源 `SysInfo.8DReportAutoClose=Y` 時直接自動結案，不需 WP803 申請。
- WinForms `8DQuery (Q)` 依目前 QRSNo 打開 `WP_8DMaintainDef` 並傳 `QRSClose=1` 唯讀；Web 沿 WP802 十頁畫面，以記憶體傳 QRSNo 並設定唯讀。正式 API 必須重查主單及權限。

## 主窗查詢與按鈕

`funLoad8DSummary` 呼叫 `wsWIP.Load8DSummaryJoinBasis`。Core 從 `TBLWIP8D_RELEASE A` 與 `TBLWIP8DBASIS_FACTORY B` 以 QRSNo 內連接，`SELECT A.*`。勾選才送出的查詢欄位為 QRSNo（包含搜尋）、FactoryNo、ProjectDepartment、Release 的 CreateDate 起迄、ReleaseDate 起迄；WinForms 的 `CloseDate` 勾選**實際過濾 ReleaseDate**，不是 Basis.CloseDate。四個單選狀態為 Unfrozen=0、Pending=1、Active=2、Unused=-1，查得後也能單純切換 DataView 狀態。Grid 僅九欄且 QRSNo 升序：QRSNo、ReleaseMemo8D、ReleaseDepartment、Releaser8D、ReleaserName、ReleaseDate8D、Description、Creator、CreateDate。尾三個帶 `8D` 的顯示名由 Release 原欄位重新命名。右側 `8DClose`、`Approve`、`8DQuery (Q)`、`Close (&X)`。

`8DClose` 開目前列編輯窗；主窗舊 IssueState 守門被註解，但 `AfterRowActivate` 僅在 Unfrozen radio 啟用按鈕。編輯窗保留 QRSType=8DFACTORY、QRSNo、QRSSummary、FactoryNo、ProductNo/Name、ProjectDepartment、ProjectManager/Name、PlanCloseDate 只讀；黃色欄為 CloseDepartment、CloseUserNo/Name、CloseDate、CloseDescription，另有 Comment、Creator/CreateDate。部門 `...` 從本 QRS 的 D1 TeamMember 取得不同 DepartmentNo/DepartmentName；選部門清空人員；人員 `...` 按部門過濾 D1 成員。`Load8DTeamMember` Core 以 `TBLWIP8D_TEAMMEMBER` 左連 `TBLUSRDEPARTMENTBASIS` 取得 DepartmentName。編輯確定必填 QRSNo、CloseDepartment、CloseUserNo、CloseUserName、CloseDescription；呼叫 `wsWIP.Update8DCloseData`，Core 只更新 `TBLWIP8D_RELEASE` 的 ReleaseMemo/Department/Releaser/Name/Date/Description，**尚未結案**。

主窗 `Approve` 支援選多列、確認後逐列呼叫 `wsWIP.Approve8DCloseData`，只接受 IssueState=0 且 ReleaseDate8D 已有值。Service 的 Issue Job Map key 是 **`8D CLOSE`**：無 JobNo 或無 Detail 直接將 Release.IssueState 改 2；有 Job/Detail 建簽核單、Release.IssueState 改 1 並通知第一群組。來源每筆成功後呼叫 `funAdd8D_ReleaseLog` → `wsWIP.Add8D_ReleaseLog` → `clsWIP.Update8DSummary(..., CloseFrom8DClose=true)`，寫 ReleaseLog(ReleaseType=2)、Basis CloseType=2/CloseDate/CloseDepartment/User/Description、CurStage=D9。ReleaseLog 的主鍵僅 QRSNo。

### 來源衝突，正式 API 必須處理

1. 有 Issue Job 時，`Approve8DCloseData` 已把 Release 設 Pending=1，但主窗**仍立即**呼叫 `funAdd8D_ReleaseLog` 結案。正式交易應在最終簽核通過後才寫 ReleaseLog 與 Basis D9；退回只將 Release 回 0。DEV UI 的 Pending 路徑採此順序，另有明示的「DEV 模擬簽核通過」。
2. 有 Job 的 ApproveSQL/RejectSQL 在 Service 裡更新的是 `TBLWIP8DBASIS_FACTORY.IssueState`（2/0），而申請狀態屬 `TBLWIP8D_RELEASE.IssueState`。這會牽動主單簽核狀態；新 API 應修為 Release，並核對歷史資料/簽核 job 設定後決定遷移補救。
3. 多選迴圈傳每一列 QRSNo 給 Approve Service，後續 `funAdd8D_ReleaseLog` 卻從 **ActiveRow** 取資料，可能反覆結案同一筆。新 API 應明確以每個 QRSNo 處理，整批回傳逐筆結果或全批原子語意。
4. Core 寫 ReleaseLog、階段與 Basis 更新由多次命令完成，非單一交易，且 ReleaseLog PK 只允許同 QRS 一筆；重送或部分成功會產生不一致。新 API 應以同一交易、主單鎖/版本條件、冪等及唯一鍵衝突處理這一組變更。
5. 編輯窗 CloseDate 寫到 Release.ReleaseDate，最後 `Update8DSummary` 把 Basis.CloseDate 設為**執行當下**，ReleaseLog 的日期亦為執行當下；不要把申請日期誤當實際結案時間。Service `Add8D_ReleaseLog` 即使收到 `closefrom8dclose`，實際傳入 Core 時也硬指定 `true`。

## 資料表與家用端 API

`TBLWIP8D_RELEASE`、`TBLWIP8D_RELEASELOG`、`TBLWIP8D_TEAMMEMBER` 的 MESTEST 來源 DDL/metadata/index 與 PG CREATE-only 已在 `database/reference/mestest_wip_wp802_*`；8D 主表在 WP508 的 `mestest_wip_wp508_*`。本批新增 `TBLUSRDEPARTMENTBASIS` 的 Oracle **唯讀** DDL `mestest_wip_wp803_department_source_ddl.sql`、metadata `mestest_wip_wp803_department_metadata.txt`、PostgreSQL CREATE-only `mestest_wip_wp803_department_create.sql`。公司端 PowerShell 5.1 + Oracle.ManagedDataAccess 查得 14 欄、DepartmentNo PK、單一 PK unique index、無 trigger。先前 `mestest_first_phase_create_tables.sql` 欄位/PK 已全有，但**少四個 Oracle default**：IssueState=0、ControlDtConect=0、DtConectQty=0、DataStamp=0；家用端應核 live schema/history，缺哪個才 forward migration。

家用端 2026-11-27 已依 Oracle source DDL 核對正式 `YMES.tblusrdepartmentbasis`，並以 migration `0087_wp803_department_source_defaults.sql` 補齊 `issuestate`、`controldtconect`、`dtconectqty`、`datastamp` 四個 `DEFAULT 0`；執行前已備份，既有部門資料列未讀寫。結案申請從 WP802 D8 建立 Release 時，來源 `Add8D_Release` 只先寫 QRSNo、IssueState=0、Creator、CreateDate；其他結案欄位由 WP803 編輯補入。DEV D8 假資料已補 Creator/CreateDate，以便 WP803 九欄清單接續顯示。

建議正式端點與語意：

- `GET /api/wip/8d-close`：伺服器端分頁/排序，狀態 0/1/2/-1 與五個勾選條件；查 Release Join Basis，只回顯示所需欄位與授權範圍。日期使用含時區約定與明確閉區間。
- `GET /api/wip/8d-close/{qrsNo}`：重查 Release/Basis；`GET .../{qrsNo}/team-members` 依 QRS、部門回傳 D1 團隊及部門名。
- `PUT /api/wip/8d-close/{qrsNo}`：僅 Release.IssueState=0、主單未結案；驗欄長、必填、部門/成員一致性、ACL、並發條件，只更新 Release；不接受 client 傳 Creator、IssueState、Basis 欄位。
- `POST /api/wip/8d-close/approve`：伺服器讀 Issue Job Map `8D CLOSE`；無流程原子更新 Release=2 與 ReleaseLog/Basis D9；有流程寫 Pending=1，最終核准事件才原子結案，退回回 0。簽核 job、郵件通知與重送要冪等；不得沿用來源錯表 SQL。若有多列，明確訂整批交易或逐筆結果。`8DQuery` 沿 WP802 唯讀 GET。
