# WP914 生產批緊急狀態／優先權調整

## 來源與範圍

- 選單：在製品管理 → 例外處理 → 生產批緊急狀態／優先權調整。`FunctionNo=LOT HOTLOT AND PRIPORITY CHANGE`（原選單拼字如此）、`FunctionKey=WP914`、`WP_HotLotAndPriorityChange.dll`。公司端頁面：`web/src/components/WipHotLotPriority.vue`，路徑 `/YMES/WIP/HotLotPriority`。
- WinForms：`STD/MESWin/WIP/WP_HotLotAndPriorityChange/frmWIPLot_HotLotAndPriorityChange.vb` 及 `.Designer.vb`；Service：`STD/MESws_STD/wsSTD/wsWIP/wsWIP.cs` 的 `LoadLotBasisJoinState`、`EditLotBasis_Confirm`；Core：`STD/MESkc/kcWIP/clsLot.cs` 的 `LoadLotBasisJoinState`、`EditLotBasis`。查找另外呼叫 `wsOE.LoadROBasis`、`wsSMD.LoadAreaBasis(AreaClass=0)`、`wsOP.LoadOPBasis`、`wsPRD.LoadProductBasis`。

## WinForms 版面與操作

原 Form 標題 `Lot HotLot/Priority Change`，ClientSize 834×598、最大化。上方 `Lot Query` 群組是兩列三欄：第一列 RO No（查找）、MO No、Product No（查找），第二列 Area No（查找）、OP No（查找）、Lot No，右側 Query。下方 `Lot` 群組上緣有 Select All、UnSelect All、掃描用 Lot No（按 Enter 勾選結果列），中間可橫捲的 Grid。Grid 顯示 Select checkbox、LotNo、MONo、HotLot、Priority、Status、ProductNo、AreaNo、PSNo、ProcessNo、OPNo、OPName、BRNo、CurQTY、CurUnitNo、SysQTY、SysUnitNo、OPGroupNo；除 Select 外各欄唯讀。底部是 HotLot 的 No／Yes、Priority、Set、Close。公司頁維持黃色輸入及資料格底色，提供假資料的四種查找。

Query 至少要有六個篩選欄之一；值離開欄位時轉大寫去空白。呼叫 `LoadLotBasisJoinState` 時固定 `Status=0|1|2|3|4|5`、`LotState=1`，其餘非空欄一起傳入。回傳另加本地 `CheckFlag=False` 欄，按 `HotLot desc, Priority, LotNo` 排序。Query 後 Priority 預設 99；Select All／UnSelect All 改變目前結果列選取，並清空掃描欄；掃描 Lot No 按 Enter 只在目前結果中尋找，找到就勾選並清空。

Set 要有已勾選列、明選 HotLot Yes／No、Priority 非空且數字落在 0–99。原 Form 對每個選中列逐筆把 **BaseLotNo**、HotLot、Priority 送到 `wsWIP.EditLotBasis_Confirm`；成功或中途失敗後重查，清 HotLot 選擇並將 Priority 設回 99。若多筆 Lot 共享 BaseLotNo，實際修改的是同一筆 LotBasis；重複選取會造成多次相同呼叫。原流程逐筆呼叫，前幾筆成功而後續失敗時可能有部分完成，沒有一個整批交易。公司 DEV 模擬以唯一 BaseLotNo 去重後一起變更共享基礎資料，並顯示實際影響列數。

Status ValueList 為 0 Queue、1 Running、2 Wait、3 Hold、4 Complete、5 OS；HotLot 0 No、1 Yes。`funLoadOPBasis` 在查 OP 前誤刪 `tblAreaBasis` 快取，應視為來源缺陷，Web 查找各自管理，不沿用這個錯誤。

## Service／Core 與 API 守門

`EditLotBasis_Confirm` 的必要值是 BaseLotNo；HotLot、Priority、Description 都是選用解析，Service 本身不重新驗證 HotLot 只可 0／1 或 Priority 0–99。它呼叫 `clsLot.EditLotBasis(BaseLotNo, Priority, HotLot, Description)`，並記錄 `EditLotBasis_Confirm` event log。Core 只組 `UPDATE TBLWIPLOTBASIS SET Priority=..., HotLot=... WHERE BaseLotNo=...`，交 `ExecuteSQLNoneQuery_UPD`；此方法沒有 LotStamp／版本 compare-and-swap、沒有確認被影響列數，也不先確認所選的 LotNo 仍屬該 BaseLotNo。正式 API 須重查後做權限、範圍、狀態、基礎批歸屬與版本守門；用參數化 SQL，拒絕重複／過期提交，逐筆結果或單一整批交易的語義需明確。建議以唯一 BaseLotNo 清單提交原子更新，回傳每個基礎批及影響 Lot 數、更新後 HotLot／Priority 與審計資訊；登入使用者來自 server，不能信任 browser 自報。

查詢 API 需登入保護，支援 RO／MO／Product／Area／OP／Lot 六欄及可授權的查找，回傳 LotNo、BaseLotNo、目前 HotLot／Priority、Status、LotState、顯示欄與版本。只讀清單與更新需分頁／限制數量。正式 API 不應從瀏覽器 localStorage 取 MES 資料。

## 表與兩端交接

Core 直接更新 `TBLWIPLOTBASIS`；查詢讀 LotBasis／LotState 與作業顯示資料，Lookup 涉及 `TBLOEROBASIS`、`TBLSMDAREABASIS`、`TBLOPBASIS`、`TBLPRDPRODUCTBASIS`。這些表在 `database/reference/` 已有 Oracle source DDL／PostgreSQL CREATE 參考：LotBasis／LotState 見 `mestest_wip_wp101_*`，RO 見 `mestest_oe_receiving_order_*`，Area 見 `mestest_smd_area_basis_*`，OP 見 `mestest_operation_and_system_*`，Product 見 `mestest_prd_product_basis_*`。本功能沒有新表，無新 CREATE SQL；家用端仍須核對 live PostgreSQL schema/history，若服務 helper 有其他間接依賴要另追。

公司 DEV 假資料可用 `RO-01`、`MO-501`、`DEV-HOT-001`；含兩筆不同 LotNo 共享 `DEV-BASE-HOT-01` 的案例。狀態只存 `ymes-dev-mock:wip-hotlot-priority:state:v1`，正式 non-DEV 禁用操作。本輪只核來源與做靜態檢查，依使用者既有約束未執行 build/test/browser；未連 YMES PostgreSQL，也未對 Oracle 做業務資料查詢或寫入。
