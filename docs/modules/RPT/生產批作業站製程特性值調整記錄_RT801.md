# RT801 生產批作業站製程特性值調整記錄

## 功能與來源

- MES 選單 FunctionNo：`LOT OP CONT ATTRIB ADJUSTLOG`；FunctionKey：`RT801`；模組：RPT；Form：`frmCont_Attrib_AdjustLogQuery`。
- WinForms：`D:\iMES\CSiMES\STD\MESWin\RPT\RT_Cont_Attrib_AdjustLogQuery\frmCont_Attrib_AdjustLogQuery.vb` 與同目錄 Designer。
- Service：`STD/MESws_STD/wsSTD/wsWIP/wsWIP.cs::LoadLotLog_ReportJoinLotBasis`、`LoadCont_Attrib_AdjustLog`。
- Core：`STD/MESkc/kcWIP/clsWIP.cs::LoadLotLog_ReportJoinLotBasis`、`LoadCont_Attrib_AdjustLog`。
- 異動表的 MESTEST metadata 與 CREATE-only reference 已由 WP912 唯讀交付，沿用 [metadata](../../../database/reference/mestest_wip_wp912_metadata.txt) 與 [CREATE-only SQL](../../../database/reference/mestest_wip_wp912_create.sql)；報工歷程表沿用 [WP201 report log reference](../../../database/reference/mestest_wip_wp201_create.sql)。公司桌機本次未連 Oracle，也未新產 DDL。

## WinForms 與舊查詢行為

1. 使用者輸入 Lot No，按 Query 或 Enter。Form 先檢查字串是否為空，再 trim 並轉大寫；只含空白的輸入會通過前置檢查後變成空字串。由於 Core 以 `defString` 判斷是否略過 LotNo 條件，正式 API 必須在 trim 後再次拒絕空白，避免空查詢條件。
2. Service 呼叫 `LoadLotLog_ReportJoinLotBasis`，傳 `LotNo`、`Status=1`、`ReportMode=true`。Core 以 `tblWIPLotLog_Report` 為主表，按 `BaseLotNo` inner join `tblWIPLotBasis` 取得 `MONo`，並以 `OPNo` left join `tblOPBasis` 取得 `OPName`；LotNo 是等號條件。Form 在 client side 依 `StartTime` 遞增排序。
3. 報工歷程 Grid 顯示 `LotNo`、`OPNo`、`OPName`、`InputQty`、`GoodQty`、`FailQty`、`StartTime`、`EndTime`，其餘回傳欄位隱藏。
4. 選取一筆非群組報工列後按 Detail，Form 以該列 `LogGroupSerial` 呼叫 `LoadCont_Attrib_AdjustLog`，同樣傳 `ReportMode=true`。Core 查 `tblWIPCont_AttribAdjustLog` 並以 `AttribNo=ElementNo` left join `tblSYSElementBasis.ElementName` 作為 `AttribName`。
5. Form 將 `Description` 欄改名為 `AdjustReason`，以 `ComponentNo IS NULL` 顯示 Lot Attrib，以 `ComponentNo IS NOT NULL` 顯示 Component Attrib。前者依 `AttribNo, ReviseDate` 排序，後者依 `ComponentNo, AttribNo, ReviseDate` 排序。切換分頁時只更換同一結果集的篩選檢視。
6. 新查詢、選取其他報工列或關閉畫面會清除明細。此功能唯讀，不調整特性、不新增歷程。

## Oracle 結構與語意

WP912 的 MESTEST metadata 記錄 `TBLWIPCONT_ATTRIBADJUSTLOG` 有 `LOGGROUPSERIAL`（VARCHAR2 BYTE 50，NOT NULL）、`ATTRIBNO`（20，NOT NULL）、nullable `COMPONENTNO`（50）、原值／新值（各 50）、`DESCRIPTION`（255）、`REVISOR`（10，NOT NULL）及 `REVISEDATE`（DATE，NOT NULL）。沒有 PK／UK／FK；有非唯一索引 `LOGGROUPSERIAL`。

Oracle 將空字串視為 NULL；Core 寫入批層異動時送空 `ComponentNo`，因此 YMES 查詢需將空字串正規化為 NULL，確保 Lot／Component 分頁與舊系統一致。

## 舊程式限制與正式 API handoff

- Core 以字串串接 SQL；正式 API 必須參數化 LotNo、LogGroupSerial，不能接受 browser 傳來的任意 `AdditionalXml`。
- Service/Core 的 `LogGroupSerial` 是 optional；若漏傳，Core 會讀取全部異動歷程。正式明細 API 必須要求單一 LogGroupSerial，並驗證它屬於目前 LotNo 下可見的 `Status=1` 報工列。
- 報工歷程與明細都沒有 Core paging／row cap。正式 API 應限制必要 LotNo、結果上限及分頁，並使用穩定排序；明細以 ComponentNo、AttribNo、ReviseDate 及可用的 row identity 作穩定 tie-break。不要假設歷程表有唯一鍵。
- `ReportMode=true` 使用舊 report connection；YMES 正式 API 必須核實部署資料來源及授權，不把 connection string 暴露給前端。
- Form 的 `LoadCont_AttribAdjustLog` 在 `Finally` 無條件把回傳碼設為 0，可能遮蔽 Service 錯誤；新 API 應正確回報錯誤。

## 公司端 DEV

- 新增 `/YMES/RPT/ContAttribAdjustLogQuery`；假資料模擬必填 LotNo 查詢、`Status=1` 報工清單、StartTime 升冪、選取報工列、Detail 與 Lot／Component 分頁。
- Fixture 以 `DEV-ATTR001` 為示範 Lot，與 WP912 DEV 樣本命名一致；所有操作只在頁面記憶體內，不呼叫 Service/API/Oracle/PostgreSQL，不寫入調整歷程。
- 正式模式僅顯示等待 API 的訊息與 Close；公司端不實作 API/schema，也未執行 build、test 或 browser 驗收。

## 家用端接續

請依可信 source DDL 核對正式 schema 與 `ymes_app` 權限後，實作登入及 `RPT/RT801` 授權的唯讀 API。建議分為指定 Lot 的 Status=1 報工歷程列表與指定 Lot／LogGroupSerial 的異動明細；兩端皆參數化、有限結果及穩定排序。明細按 `ComponentNo` 分批／元件結果，處理空字串與 NULL 的 Oracle 相容性。詳細來源片段及未確認項目見本文件。
