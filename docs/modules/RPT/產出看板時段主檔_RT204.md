# RT204 產出看板時段主檔

## 模組識別

- FunctionNo：BILLBOARD TIME_STEP BASIS；FunctionKey：RT204；FunctionName：產出看板時段主檔。

- 維護 RT205、RT206、RT207 使用的產出時段；三個看板只讀取 IssueState=2 的時段，依 TimeStepNo 排序。

## 畫面與操作規則

- 初次載入預設 UNFROZEN；可切換 UNFROZEN=0、PENDING=1、ACTIVE=2、UNUSED=-1。Core 依 TimeStepNo 排序載入；Form 以 IssueState 篩選 DataView。
- 欄位顯示 TimeStepNo、TimeStepName、FromTime、ToTime、Description、Creator、CreateDate；IssueState 在原 Grid 隱藏。
- Add 建立狀態 0；Edit 僅允許狀態 0，TimeStepNo 唯讀；Copy 複製所選記錄的名稱、時間、描述，TimeStepNo 可改，新增後狀態為 0。
- Confirm 儲存並關閉；Apply 儲存但留在編輯視窗，成功後按鈕停用直到欄位再變更。TimeStepName 必填、最多 50 字；TimeStepNo 為 01–15 選項，輸入數字需大於等於 1 並補左側零。Form 沒有明確驗證 FromTime 必須早於 ToTime，跨午夜由 Core 處理。
- Approve 只核准狀態 0，直接改為 2；不經狀態 1。Delete 對 0／-1 實體刪除，對 2 改為 -1；狀態 1 不允許刪除。多筆操作按選取順序處理，遇到不支援狀態時停止，之前成功的筆數不回復。
- 描述為空時 Core Add 不寫 Description 欄；Edit 只在 Description 不等於 defString 時更新，因此舊服務不能以空白清除既有 Description。
- Service 從登入者取 Creator；新增時 IssueState=0，建立時間取服務端目前時間。SQL 在舊 Core 以字串組合，家用端須使用參數化查詢。

## 時段重疊規則與舊程式疑點

- Add／Edit 的 Core 只拿 IssueState 0 或 2 的資料比較；IssueState 1 與 -1 不參與重疊檢查。時間依最早 TimeStepNo 的起始時間轉換成一日加跨午夜區間，To 不晚於 From 會推至隔日。
- 舊重疊條件檢查新增起點落入既有區間、終點落入既有區間、或終點跨過第一個區間的次日邊界；此條件可能漏掉完整包住既有區間的新增區間。Approve 僅將狀態設為 2，不再次檢查是否與啟用時段重疊。
- 公司端 DEV 使用完整區間相交判斷，涵蓋跨午夜並允許一段 To 與下一段 From 相接。這比舊 Core 的部分判斷嚴格；家用端應修正為完整重疊檢查，並在交易內再次核准，而不是照搬可能漏檢的條件。
- DEV Approve 仍照舊 Form／Service 直接將狀態 0 改為 2，不重查重疊；家用端 API handoff 建議在交易中重查，以處理資料併發變更。
- Main Form 有 PENDING 篩選，但這組 Form／Service 沒有將記錄轉成 IssueState=1 的操作。PENDING 只作既有資料狀態檢視；核准按鈕要求來源狀態必須為 0。
