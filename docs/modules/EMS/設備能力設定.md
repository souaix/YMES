# ES108 設備能力設定

## 範圍與來源

本功能維護「設備」與「設備能力項目／條件」的對應。公司端交付 Vue DEV 假資料頁及家用端 handoff；頁面不呼叫正式 API，也不連 YMES PostgreSQL。

- 清冊：`EMS / EMS設定 / EQP CAP MAPPING`，FunctionNo `EQP CAP MAPPING`、FunctionKey `ES108`，Form `frmEQPCapMapping`、執行檔 `ES_EQPCapMapping.dll`。
- 主 Form（Designer 內嵌）：`D:\iMES\CSiMES\STD\MESWin\EMS\ES_EQPCapMapping\frmEQPCapMapping.vb`；定義窗及內嵌 Designer：同目錄 `frmEQPCapMappingDef.vb`。
- Service：`D:\iMES\CSiMES\STD\MESws_STD\wsSTD\wsEMS\wsEMS.cs` 的 `LoadEMSEQPCapMapping`、`LoadEMSEQPCapMapping_EQP`、`UpdEMSEQPCapMapping`、`SetEMSEQPCapMapping_OpenStatus`、`DelEMSEQPCapMapping`。
- Core：`D:\iMES\CSiMES\STD\MESkc\kcEMS\clsEMSEquipment.cs` 的同名讀寫方法及 `ShowEMSEQPCapMapping`／`ShowEMSEQPCapMapping_EQP`。

## WinForms 畫面與操作

- 查詢欄為 Equipment Type、Equipment No、CapItem；只處理勾選欄位，已勾選但空白會提示。Equipment Type 透過 `tblEQPEquipmentBasis` 篩 EquipmentNo；設備及能力項目由 `wsEQP.LoadEquipmentType`、`wsEQP.LoadEquipmentBasis`、`wsEMS.LoadEMSEQPCapBasis` 提供查找。
- 左 Grid 由 mapping 表取得不重複的 EquipmentNo，只列出已有對應的設備。選取設備後才載入該設備的完整能力明細；即使查詢帶有 CapItem，右側仍顯示該設備全部能力條件。
- 右 Grid 顯示 CapItem、CondOperand、CapValue、OpenStatus、Description、Creator、CreateDate。主畫面可新增、編輯、複製至設備、刪除設備設定，以及對選取條件開啟／關閉。
- 定義窗 Add／Edit／Copy 以設備為單位編輯整組條件。Add 若選到已有 mapping 的設備，會載入現況；Copy 到已有 mapping 的目標設備時，可選擇載入目的現況或保留來源條件後整組覆寫。Edit 固定原設備。
- 條件運算子為 `=`、`>`、`>=`、`<`、`<=`；非 `=` 的 CapValue 必須可轉數字，`=` 可輸入文字。新增條件會拒絕重複的 `(CapItem, CondOperand, CapValue)`。CapItem／EquipmentNo 最長 50、CapValue 最長 20、Description 最長 255；主要識別欄位離開輸入時 trim 並轉大寫，Description trim。新條件預設開啟。
- 儲存至少要有一筆條件，無法用空清單清空整台設備；清空需由主畫面的刪除操作完成。Core 的 `UpdEMSEQPCapMapping` 對指定 EquipmentNo 先刪所有 mapping，再插入送入清單，因此編輯及 Copy 都是整組替換，並以此次 Creator／CreateDate 重建資料，不保留舊列建立者及建立時間。
- 開／關操作逐條件呼叫 Service，識別值為 EquipmentNo、CapItem、CondOperand、CapValue，並寫 OpenStatus、Reviser、ReviseDate。沒有傳入預期舊狀態或 DataStamp。主畫面多選設備刪除時逐台執行，先成功的設備不會因後續失敗而回復。

## 資料表與 Oracle metadata 狀態

- Core 直接讀寫 `tblEMSEQPCapMapping`；查找還使用 `tblEQPEquipmentBasis`、`TBLEMSEQPCAPBASIS`。能力項目主檔的已知 Oracle DDL／PostgreSQL CREATE-only 依 ES107／PD102 沿用。
- 本機 Core SQL 只能證實 mapping 操作會引用 `EquipmentNo`、`CapItem`、`CondOperand`、`CapValue`、`OpenStatus`、`Creator`、`CreateDate`、`Reviser`、`ReviseDate`，以及可選的 `Description`。這是來源程式使用欄位的紀錄，不代表已核實實體欄位型別、NULL、PK／唯一鍵、索引、FK、預設值或 trigger。
- Repo 目前沒有 `TBLEMSEQPCAPMAPPING` 的 Oracle source DDL／metadata 或 PostgreSQL CREATE-only。桌機受保護 Oracle profile 檔不存在，本次未能以 PowerShell 5.1 + ODP.NET 唯讀連線 MESTEST。**不可依 Core SQL 猜測實體 schema 或提交 CREATE SQL。** 家用端先比對 live schema／migration；若同樣缺表或欄位資訊，需取得允許的 Oracle metadata 後再整理 DDL。
- `UpdEMSEQPCapMapping` 將 Delete 與多筆 Insert 傳給 `ExecuteSQLNoneQuery_UPD`。本次只確認呼叫點，未讀到 helper 的具體交易／回滾保證，因此原程式是否原子未知。Core 將條件值直接串接 SQL，正式實作不可照搬。

## Vue DEV 頁

- fallback 路由 `/YMES/EMS/EquipmentCapabilityMapping`，位於「設備管理 / EMS設定」。頁面含勾選式三條件查詢、已設定設備與能力明細雙 Grid、Add／Edit／Copy、重複條件防止、整組覆寫、逐條件開／關、多設備整組刪除及確認提示。
- 所有設備、能力條件、使用者和時間都是虛構假資料，只存在目前頁面記憶體；沒有呼叫 Service/API 或寫入資料庫。整組替換與刪除提示已標示舊程式的資料範圍及部分成功風險。

## 家用端 API／schema handoff

- Pull 最新 main 後，先檢查 `tblesmseqpcapmapping` live schema、migration history、權限及引用；目前無可核實的 CREATE-only。不得僅根據 Core 欄位名建 migration。完成 schema 對照與欄位／鍵確認後，再補必要 CREATE-only reference。
- 依登入者及 FunctionNo `EQP CAP MAPPING` 授權提供有分頁／上限的設備條件查詢。Equipment Type、Equipment No、CapItem 篩選使用參數化條件；CapItem 篩選左側設備集合後，明細仍應依舊 Form 行為回傳選取設備的全組條件。限制授權設備範圍並提供穩定排序。
- 整組新增／編輯／複製 API 必須在單一交易內驗證設備與能力項目，再替換該設備全組 mapping。使用伺服器建立的 Creator／時間；定義 expected-set／版本衝突保護，避免兩人同時整組覆蓋。僅接受 `=`, `>`, `>=`, `<`, `<=`，驗證非等號值為數字、三欄複合條件不重複及對應能力項目有效。處理描述與識別欄位長度時以已核實的 DB byte／字元限制為準。
- 開／關 API 需在伺服器端確認完整條件鍵及當前狀態，使用 expected status 或 row version 防止覆蓋並發修改；多筆狀態變更要明確定義全有或全無，或逐筆結果。
- 刪除設備 mapping 會刪除該 EquipmentNo 的全部條件。多設備刪除需先定義原子批次或回傳每台結果；不能把部分成功回報成整批成功。所有 SQL 參數化；錯誤回應區分設備／能力不存在、重複條件、版本衝突及權限拒絕。公司端不實作或驗收正式 API/schema。
