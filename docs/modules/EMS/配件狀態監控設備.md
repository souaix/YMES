## WinForms 畫面與互動

- 上方有 Equipment Type、Equipment No、Total Page／Page 與 Refresh；選設備類別後清除設備編號並載入該類別所有已掛載配件；選設備編號後載入該設備已掛載配件。類別與設備使用 `frmCOMSearch`，Equipment Type／Basis lookup 傳 IssueState=2。
- 中間以五欄排列 20 個配件卡顯示每頁資料。卡片編號與色塊代表配件及狀態，狀態名稱透過配件狀態基礎 tooltip 呈現；資料依 AccessoryCategory、AccessoryNo 排序。Service 回傳累積量、維修量及總使用量，但 Form 不顯示這些欄位。
- 點選卡片後，依該配件的 AccessoryCategory 讀分類狀態按鈕與互斥 pair；已設定的互斥目標及目前狀態按鈕停用。按鈕可開啟 ES301／ES302 或狀態描述介面，沒有對應控制介面時呼叫通用狀態變更。
- 右鍵可開啟 Accessory State Log、Equipment ACC State Log、Accessory State；雙擊開啟 Equipment Accessory State。外部視窗由 ObjectFileHandler 依 AccessoryNo 呼叫。
- 來源 `CountPage` 與 ES304 一樣以 `Count \ 20` 後比較 `TotalPage * 10 < Count`，在筆數為 20 的倍數時多算一頁；DEV 使用正確 `ceil(count / 20)`。

## Service／Core 行為與差異

- 設備類別 lookup 由 `wsEQP.LoadEquipmentType` 傳 `IssueState=2`；設備編號 lookup 由 `LoadEquipmentBasis` 傳 `IssueState=2` 和可選 EquipmentType。選類別會自動 Refresh，重選不同類別時清除 Equipment No 並清掉狀態操作按鈕。
- `wsEMS.LoadAccessoryStatebyEquipment` 接受可選 EquipmentType／EquipmentNo，呼叫 `clsAccState.LoadAccessoryNoByEquipment`。Core 查 `TBLEMSEQPACCSTATE` 中 `EquipmentType IS NOT NULL` 的掛載編號，再接 `TBLEMSACCESSORYSTATE`、`TBLEQPACCSTATEBASIS` 及 `TBLEQPACCESSORYBASIS` 取狀態、累積／維修／總使用數與分類；若兩個設備條件都未傳，Core 會回傳全部掛載配件。
- 上述 Core SQL 僅以 `AccessoryNo` 連 `TBLEMSACCESSORYSTATE` 及 `TBLEQPACCESSORYBASIS`，未限制 `AccessoryVersion` 或 `CurVersion=1`。若有多版本資料，可能重複卡片或把舊版狀態混入；家用端查詢應以目前掛載的 AccessoryNo+Version 連結，並以設備授權範圍限制和穩定分頁。
- 點選卡片後 Form 依 AccessoryCategory 載入狀態控制及 `TBLEMSACCVIOLATESTATUSCHANGE`，停用互斥狀態。通用 `ChangeAccessoryState` 傳目標狀態、目前狀態及固定描述，但不傳分類；Core `CheckACCPrivileged` 依配件主檔查分類，再檢查狀態權限和目前狀態。Core 不重查互斥 pair；正式 API 必須在伺服器端重查互斥與狀態權限。
- `Apply`／`Return` 會呼叫 ES301／ES302 外部流程；通用狀態變更不會更新設備掛載關聯。舊式 SQL／AdditionalXml 是字串串接，不能直接沿用到 API。

## 表與 Oracle metadata 狀態

- 主要查詢表：`TBLEQPEQUIPMENTTYPE`、`TBLEQPEQUIPMENTBASIS`、`TBLEMSEQPACCSTATE`、`TBLEMSACCESSORYSTATE`、`TBLEQPACCESSORYBASIS`、`TBLEQPACCSTATEBASIS`；分類動態操作會讀 `TBLEQPACCCATEGORYSTATEBASIS`、`TBLEQPACCSTATECONTROL`、`TBLEMSACCVIOLATESTATUSCHANGE`。狀態更新沿 ES304 使用 `TBLEMSACCESSORYSTATE`／`TBLEMSACCESSORYSTATELOG`，權限另讀系統及使用者群組設定。
- 配件掛載／狀態／基礎／分類狀態與控制表已有 repository Oracle source DDL 及 PostgreSQL CREATE-only，沿用 `mestest_accessory_basis_*`、`mestest_accessory_state_*`、`mestest_accessory_category_state_*` references；設備基礎沿用 WP201 references。
- `TBLEQPEQUIPMENTTYPE` 目前 repo 只有 PostgreSQL CREATE-only，缺同版 Oracle source DDL；`TBLEMSACCVIOLATESTATUSCHANGE` 缺 Oracle source DDL 與 PostgreSQL CREATE-only。桌機受保護 Oracle profile 不可用，本次未連 MESTEST，沒有猜欄位或新增 SQL。家用端須比對 live schema／migration，取得核准 DDL 後補足互斥表。
- 本項沒有新增 SQL 或 migration。公司端不連 YMES PostgreSQL、不實作正式 API/schema、不部署。

## 家用端正式 API handoff

- 提供登入授權設備類別／設備 lookup 與掛載配件分頁 GET；至少要求設備類別或設備編號一項，限制每頁 20 筆並使用穩定排序。不得接受任意 `AdditionalXml` 條件；伺服器須驗證使用者對設備的可見範圍。
- 配件卡片以目前掛載 relation 的設備類別／編號、AccessoryNo、AccessoryVersion 作關聯，回傳同一有效版本的 current state 與累積／維修／總使用量；不可複製 legacy 只按 AccessoryNo join 的查詢。
- 通用狀態更新須由伺服器重新取得配件分類，檢查登入者分類狀態權限、互斥 pair、Current State／版本與可見設備範圍，交易內寫入狀態歷程、更新現況並安全配置 ACCSerialNo。`Apply`／`Return` 導向 ES301／ES302 專用交易；右鍵與雙擊視窗導向正式歷程／現況 endpoint。
