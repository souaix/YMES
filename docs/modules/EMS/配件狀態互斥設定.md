## WinForms 畫面與互動

- 上方選擇 Accessory Category。選取類別後載入狀態基準與該類別已設定的互斥對，矩陣以狀態顏色呈現；Y 軸是目前狀態，X 軸是禁止轉換到的狀態。內部格雙擊切換禁止標記，左上及最外框為軸標題／狀態標籤。
- Confirm 初始停用；若 Confirm 權限允許，任一矩陣格雙擊後啟用。Confirm 將每個目前狀態的完整禁止目標集合送出，沒有禁止目標的狀態也會送空集合以清除舊設定。成功後頁面不關閉；Close 直接關閉。
- 目前 Form 的類別專屬 `LoadDistinctAccyCategoryStateBasis`／`funLoadAccCategoryStateData` 路徑已註解；選取類別時固定走 `blnAccCategory=False` 與 `LoadEQPACCStateBasis`，所以矩陣軸採共用狀態基準，類別只用於載入／更新互斥組合。舊 `fun_LoadEQPACCStateControl` 也不是此流程的目前呼叫路徑。
- Form 的 Grid 全域 `AllowUpdate=False`，初始化時內部格也設 `Activation.Disabled`，但 `DoubleClickCell` 仍直接切換格子背景圖片。DEV 保留雙擊互動。Confirm 權限來自 `ExeGroupControlPriv`；DEV 假設操作者有權限。

## Service／Core 與資料參照

- `wsEQP.LoadEQPACCStateBasis` 取得 `TBLEQPACCSTATEBASIS` 狀態名稱／色彩，Form 依 `AccessoryState` 排序建 N×N 矩陣。既有違規組合由 `wsEMS.LoadViolateStateAndShowNowName` 查詢；Core join 狀態基準兩次取得目前狀態與禁止狀態名稱，並依 `AccessoryCategory` 過濾。
- Confirm 對每個目前狀態呼叫一次 `wsEMS.UpdACCViolatStateChangeData`。Service 先刪除該類別／目前狀態的既有組合，再依 client 傳來的目標狀態與名稱逐筆新增；使用同一個 `ViolativeSerial` 並以 `AddACCViolateStateChange` 同步寫互斥設定及互斥歷程。清除全部禁止項目時會刪除設定，但不新增歷程。
- Confirm 沒有覆蓋所有狀態列的單一交易：每個狀態列是獨立 Service 呼叫；Service 內 Delete 與多次 Add 亦分開執行。中途失敗可能留下部分狀態已更新、單一狀態先刪除再只新增部分目標的結果。
- Core SQL 以字串串接類別、狀態及名稱；正式 API 必須參數化，狀態名稱應由 server-side `TBLEQPACCSTATEBASIS` 查得，不採信 client 傳來的 `AccessoryStateName`／`ViolativeStateName`。
- repo 有作用中矩陣所讀取的 `TBLEQPACCSTATEBASIS` Oracle source DDL／CREATE-only，見 `database/reference/mestest_accessory_state_source_ddl.sql`／`mestest_accessory_state_create.sql`。repo 也有 `TBLEQPACCSTATECONTROL` DDL，但它只供 Form 未呼叫的舊 helper，並非目前矩陣來源。`TBLEMSACCVIOLATESTATUSCHANGE` 與 `TBLEMSACCVIOLATESTATUSLOG` 缺 Oracle source DDL／metadata 及 PostgreSQL CREATE-only；桌機受保護 Oracle profile 不可用，本次未連線、未猜欄位或建表。

## DEV 與家用端 handoff

- DEV 提供假類別選擇、狀態色矩陣、雙擊／Enter 切換 X、修改後 Confirm、Close 丟棄未確認變更；Confirm 只更新本頁記憶體並顯示假儲存時間，不呼叫 API／Service、Oracle、YMES PostgreSQL 或 localStorage。
- 家用端先比對 `tblemsaccviolatestatuschange`、`tblemsaccviolatestatuslog` live schema／migration；取得核准 Oracle 唯讀 DDL／metadata 後再新增 CREATE-only。公司桌機本次缺受保護 Oracle profile，未取得表欄位、PK 或 index；Core SQL 及 Form 只能確認需要的資料欄位，不能當作建表依據。
- 正式 API 需登入及配件類別設定權限；一次提交類別完整目標矩陣，在單一資料庫交易內鎖定／重讀原設定、以核准的完整矩陣原子替換並新增歷程，失敗全部回滾。由 server 取得狀態名稱；明確定義清空矩陣的稽核紀錄、serial 及重複提交行為。
- Core 的讀取與更新不分頁（矩陣規模依狀態基準），但仍須限制合法類別及狀態集合、參數化所有值，拒絕未知／停用狀態及跨類別輸入；回傳原子提交結果和版本／衝突資訊。
