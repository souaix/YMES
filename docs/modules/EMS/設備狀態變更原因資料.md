## WinForms 欄位與狀態流程

- 主畫面只載入 `ReasonType=6`（EQP），以 ReasonNo 查詢；繼承表單的狀態篩選值為 `0=Unfrozen`、`1=Pending`、`2=Active`、`-1=Unused`。Grid 顯示 ReasonNo、ReasonName、ReasonType、ReasonSubType、ReasonLevel、Description、Creator、CreateDate、Reviser、ReviseDate；其他欄位（如 IssueState、DataStamp）作為行為識別。
- Add／Copy 會開 Def Form。ReasonType 固定選 `EQP (6)`；`ReasonSubType` 唯讀，按查找從 `wsQC.LoadReasonSubTypeBasis(IssueState=2)` 的 EQP 子類別選擇，但主 Form 只要求 ReasonNo／ReasonName，子類別可留空。ReasonLevel 範圍 0–9，Description 可空；Apply 儲存後留在對話框，Confirm 儲存並關閉。Copy 以原列帶入名稱、子類別、Level、描述，但新 ReasonNo 由使用者輸入，新增狀態為 Unfrozen。
- Edit 主畫面只允許目前選取列 `IssueState=0`；編輯時 ReasonNo 唯讀，保留 Creator/CreateDate，更新後填 Reviser/ReviseDate。
- Delete 可多選並逐列呼叫 Service：IssueState 0 或 -1 實體刪除；2 轉為 -1（停用）；1 不允許。逐筆處理遇錯即停止，前面成功的列不回復，來源沒有顯示整批交易。
- Approve 可多選，但只接受 IssueState=0。`ApproveReasonBasis` 依 IssueJobMap：無簽核 Job 時直接設為 2；有流程則建立 Issue Master、設定 approve→2／reject→0、把資料轉為 1（Pending），並通知第一關負責群組。來源未證明跨 Issue／原因更新／郵件為原子交易。

## Service／Core 與資料表

- 表單載入以 `LoadReasonBasis` 查 ReasonType 6，狀態 radio 在本機 DataView 篩選；Def Form 的子類別查詢依 ReasonType 6、IssueState 2。Service 對 Add／Edit 等欄位解析、檢查 ReasonNo／Name／Level，記錄 EventLog 或 ErrorLog。
- Core 讀寫 `TBLQCREASONBASIS`。Add 設 IssueState 0 並寫 Creator/CreateDate；Edit 更新 ReasonName、ReasonLevel、ReasonType、ReasonSubType、Description；wsQC Edit Service 接受 IssueState 0 或 2，但 Form 僅讓 IssueState 0 進入編輯；刪除分支為單筆 SQL；`SetReasonBasisIssueState` 更新狀態。Legacy Core 用字串串接 SQL。
- 本機 wsQC Service 呼叫 `EditReasonBasis` 與 `SetReasonBasisIssueState` 時傳 `DataStamp`、`Reviser`、`ReviseDate` named arguments；但同一份 `clsQCBasis.cs` 中對應 method 宣告未包含這些參數，狀態更新 SQL 也只設 IssueState。這是本機 Service/Core 來源版本不一致或資料戳處理缺失，不能據此假設 Core 已實作樂觀並發或修訂稽核；家用端需核對原建置版本並以交易／版本條件保護正式寫入。
- `TBLQCREASONBASIS` Oracle metadata 欄位：`REASONNO VARCHAR2(20)` PK、`REASONNAME VARCHAR2(100)`、`REASONTYPE NUMBER(1,0)`、`REASONLEVEL NUMBER(1,0)`、`DESCRIPTION VARCHAR2(255)`、`CREATOR/REVISER VARCHAR2(10)`、`CREATEDATE/REVISEDATE DATE`、`ISSUESTATE NUMBER(1,0) DEFAULT 0 NOT NULL`、`REASONSUBTYPE VARCHAR2(50)`、`DATASTAMP NUMBER(11,0) DEFAULT 0`。唯讀核實的 Oracle DDL/constraint/index 及 PG CREATE-only 參考：[`mestest_qc_reason_basis_source_ddl.sql`](../../../database/reference/mestest_qc_reason_basis_source_ddl.sql)、[`mestest_qc_reason_basis_create.sql`](../../../database/reference/mestest_qc_reason_basis_create.sql)。
- 子類別 lookup 讀 `TBLQCREASONSUBTYPEBASIS`；其唯讀來源 DDL 和 CREATE-only 參考為 [`mestest_qc_reason_subtype_basis_source_ddl.sql`](../../../database/reference/mestest_qc_reason_subtype_basis_source_ddl.sql)、[`mestest_qc_reason_subtype_basis_create.sql`](../../../database/reference/mestest_qc_reason_subtype_basis_create.sql)。本項沿用既有 Oracle metadata，沒有查業務列或新增 Oracle 查詢，不新增表 DDL。

## Vue DEV 與家用端 handoff

- Vue DEV 提供四個 IssueState 分頁、ReasonNo 查詢、欄位 grid、Add/Edit/Copy modal、EQP subtype lookup、Apply／Confirm、勾選多筆 Delete／Approve。DEV 以固定 fixture 模擬資料與 DataStamp，未呼叫正式 API、未寫 localStorage 或資料庫；核准對話框可切換「直接 Active」和「送簽 Pending」兩種 IssueJobMap 結果。
- 建議家用端提供權限保護的 `GET /api/ems/equipment-reasons?issueState=&reasonNo=` 和 `GET /api/ems/equipment-reason-subtypes?reasonType=6&issueState=2`；新增 POST、未凍結編輯 PUT、狀態動作端點分開處理。服務端固定 `reasonType=6`；子類別可空，非空時須驗證為有效 Active EQP 子類別。字串條件全部參數化，限制欄位長度及 ReasonLevel 0–9，確認空字串轉 NULL 的 Oracle 相容行為。
- Delete API 維持狀態語意：0／-1 實體刪除前檢查依賴；2 轉 -1；1 拒絕。Approve 依正式 IssueJobMap 建立直接核准或完整送簽流程，原子處理狀態、簽核資料、審計紀錄及通知；任一失敗需回滾，或以 outbox 確保通知可靠。
- Pull 最新 `main` 後先比對 live schema；若欄位／型別已存在就不重建。寫入需在交易中檢查預期 `DataStamp` 並原子增加，寫 Creator/CreateDate／Reviser/ReviseDate；先釐清 legacy Service/Core named-argument 差異。公司端未連 PostgreSQL、未建 migration、未實作或驗收 API、未 SSH／部署。
