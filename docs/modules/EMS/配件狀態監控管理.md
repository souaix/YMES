## WinForms 畫面與互動

- 上方以 `Accessory Category` 選類別，再以 `Accessory Type` 選類型；選擇類型後自動查詢現況。類別 lookup 使用 `wsEQP.LoadAccessoryCategory`，類型 lookup 傳類別給 `wsEQP.LoadAccessoryType`。
- `STATES` 頁顯示所選類型現況 Grid，提供 0–5 六個狀態按鈕。使用者可選取多筆配件後逐筆送出目標狀態；已是目標狀態的列略過，結束時回報成功／略過／失敗數。有成功列時會更新該列狀態並重新載入 LOG。
- `LOG` 頁以 `Refresh LOG` 重載狀態歷程。Designer 還宣告配件歷史／設備配件歷史／配件現況 ContextMenu，但 Form 未找到其事件處理器或對 Grid 的掛接，DEV 不呈現未接線選單。
- Form 透過 `GETACCSTATE_FIELD` 取得狀態欄位資料，但 Designer 的六個按鈕仍是固定數字 0–5，click handler 直接以按鈕序號當目標狀態，未用該資料動態產生按鈕。
- Grid Designer 未設定 `SelectionMode=FullRowSelect`，bulk handler 卻只讀 `SelectedRows`；依預設 cell-selection 操作可能沒有完整選取列。DEV 用明確的列勾選支援多選，視為操作性簡化。
- Form 查詢現況及 LOG 都直接呼叫 REST `GETACC_STATE`／`GET_ACCLOG`，並附加 SAP `MANDT`／`WERKS` 系統參數。換狀態則 POST `AccessoryNo`、目標／預期現況、類別、UserNo、描述、`MANDT`／`WERKS` 及電腦名稱。這些 REST endpoint 的 server source 不在本機來源樹，未猜其 response schema 或授權邏輯。

## Service／Core 與資料參照

- `wsEMS.ChangeAccessoryState` 解析目前狀態、目標狀態、類別、UserNo、描述及 optional reasons，呼叫 `clsAccState.ChangeACCState`。Core 執行 `CheckACCPrivileged`，只找 `CurVersion=1` 的配件現況，若傳入的 expected current state 與資料庫不符則拒絕；成功時將舊現況寫入 `TBLEMSACCESSORYSTATELOG`，更新 `TBLEMSACCESSORYSTATE` 的狀態、時間、使用者、描述並換發 `ACCSERIALNO`。客戶版 POST 與 SOAP Service 的連接細節因 REST Controller 缺失而未確認。
- 多筆狀態更新是 Form 逐列發出 REST POST，不是整批請求；部分成功時會留下部分變更。正式 API 要明確回報每筆結果，避免 UI 將部分成功誤報成整批成功。
- Form 呼叫 Core 的配件狀態變更未帶理由；Core 雖接受 optional reasons，現行客戶版呼叫路徑沒有新增理由列。
- `clsEMSEquipment.LoadAccessoryStateByCategory` 的 SQL 以 `TBLEMSACCESSORYSTATE`、`TBLEQPACCSTATEBASIS` 及配件類別／類型／基礎查現況，返回配件編號、狀態及顏色；條件為字串串接且未限制目前版。客戶版 Form 的現行 `GETACC_STATE` REST 呼叫未走此 Core 方法。
- 現況、歷程、配件基礎及狀態基礎的 Oracle DDL／CREATE-only 已在 repo，見 `database/reference/mestest_accessory_basis_source_ddl.sql`／`mestest_accessory_basis_create.sql` 與 `database/reference/mestest_accessory_state_source_ddl.sql`／`mestest_accessory_state_create.sql`。本項無新增 DDL；REST API 背端未找到，沒有查或推測額外資料表。

## DEV 與家用端 handoff

- DEV 提供類別／類型假選擇器、STATES／LOG 分頁、現況 Grid、列勾選、0–5 多筆狀態模擬、成功／略過／失敗摘要與 Refresh LOG。所有配件、狀態、顏色、歷程及更新皆為虛構且只留本頁記憶體；不呼叫 Service、REST API、Oracle、YMES PostgreSQL 或 localStorage。
- 家用端先核對現況／歷程／基礎／狀態 live schema 與 migrations，並從 API 實作來源或 owner 取得 `GETACC_STATE`、`GET_ACCLOG`、`GETACCSTATE_FIELD`、`AccessoryApi.ChangeAccessoryState` 的 SQL、response、驗證及權限契約。公司端未找到這些 REST server 專案，故 response 欄位只依 Form/Core 已確認使用的欄位建立 DEV fixtures。
- 新正式 API 應以登入者身分及伺服器授權推導 UserNo／可管理類別／SAP 範圍，不接受 client 自報的 `GUserNo`、`MANDT`、`WERKS` 作為授權依據；參數化查詢、限制目前版本、穩定排序／分頁，避免 generic SQL execution endpoint。
- 狀態更新需在伺服器端重驗類別權限、目標狀態規則及 expected current state，按 `AccessoryNo+AccessoryVersion` 明確選取目前版並原子寫入歷程／現況／新序號。多選更新要保留逐筆結果或定義可回滾的批次語意；禁止將 client 送出的多筆假成功當正式交易結果。
