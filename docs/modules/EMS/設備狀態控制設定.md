# ES102 設備狀態控制設定（EQP STATE CONTROL SETTING）

## 選單與來源

- 選單識別：Module `EMS`、FunctionNo `EQP STATE CONTROL SETTING`、FunctionKey `ES102`、Form `frmEQPStateControlSet`、執行檔 `ES_EQPStateControlSet.dll`，選單分類 `EMS設定`。
- 公司端 DEV 路徑：`/YMES/EMS/EqpStateControlSet`。正式頁面尚未開放，不連家用端 API。
- WinForms Form、Designer 控制項配置與事件均在 `D:\iMES\CSiMES\STD\MESWin\EMS\ES_EQPStateControlSet\frmEQPStateControlSet.vb`，沒有獨立 Designer 檔。
- Service：`D:\iMES\CSiMES\STD\MESws_STD\wsSTD\wsEQP\wsEQP.cs` 的 `LoadStateControlType`、`UpdStateControlType`；表單另呼叫 `LoadEQPStateBasis` 載入狀態選擇清單。
- Core：`D:\iMES\CSiMES\STD\MESkc\kcEQP\clsEQPStateControl.cs` 的 `LoadStateControlType`、`DelStateControlType`、`AddStateControlType`。Form 寫入實際只走批次 `UpdStateControlType`，沒有直接呼叫單筆 Add/Edit/Delete。

## WinForms 欄位與互動

表單有三個分頁，狀態代碼與名稱均唯讀，按 `...` 開 `frmCOMSearch`，從 `TBLEQPSTATEBASIS` 選設備狀態：

| ControlType | ControlNo | 表單欄位 |
| --- | --- | --- |
| `PM Work Order` | `PMWoReleased` | PM WO Release State |
| `PM Work Order` | `PMWoFinished` | PM WO Finish State |
| `WIP Tracking` | `CheckInConfirm` | Check In Confirm |
| `WIP Tracking` | `CheckOutRelease` | Check Out Release |
| `EQP Break Down` | `BreakDown` | Break Down |
| `EQP Break Down` | `Idle` | Idle |
| `EQP Break Down` | `ContinueToProduction` | Continue to Produce |

- 開頁時一次讀取 `TBLEQPSTATECONTROL`，依 ControlType／ControlNo 將七個設定放入欄位。點選狀態只標記該分頁有修改；同群組送出時會一起送完整控制項。
- `Apply` 與 `Confirm` 都檢查七個狀態代碼及名稱皆有值，再只送有修改的群組。Apply 成功後留在頁面並清除修改狀態；Confirm 成功訊息後關閉頁面；Close 不寫入。
- Form 以 `PM Work Order`、`WIP Tracking` 分頁標題篩資料，第三類固定用 `EQP Break Down`。正式 API 應使用固定 ControlType／ControlNo key，不可把翻譯後的標題當資料鍵。
- 原始確認程式有一個檢核 typo：檢查 `ContinueToProduction` 代碼後，名稱檢查仍引用 `txtBreakDownStateName`，沒有檢查 `txtProductionStateName`。Web/API 契約應核對其名稱和狀態碼，不複製此錯誤。

## Service／Core 行為與資料結構

- `LoadStateControlType` 解析可選 ControlNo／ControlType，Core 查 `TBLEQPSTATECONTROL`；表單不傳條件，因此載入全部設定。`LoadEQPStateBasis` 提供可選狀態。
- `UpdStateControlType` 逐筆解析 ControlType、ControlNo、EquipmentState、StateName，對每筆呼叫 Core 先 Delete 再 Add；使用者可以只提交修改分頁，但該分頁所有固定控制項都會重新寫入。
- Core Add／Delete 以串接 SQL 寫入。Service 的批次循序執行，來源沒有證明七筆或同群組多筆共用交易；中途失敗可能留下部分新值。正式服務須參照固定 key、參數化查詢，並用單一 PostgreSQL transaction 完成同一群組全部設定。
- Service 成功事件紀錄使用最後解析的 ControlNo。正式 API 應保留實際 actor、所有被修改的 ControlType／ControlNo 和前後值，並遵守登入與 ES102 權限；Form 的 `ExeGroupControlPriv` 不是伺服器端授權。
- `MESTEST.TBLEQPSTATECONTROL` 有 `CONTROLTYPE varchar(50) NOT NULL`、`CONTROLNO varchar(50) NOT NULL`、`EQUIPMENTSTATE number(2,0) NOT NULL`、`STATENAME varchar(50) NOT NULL`；複合 PK `(CONTROLTYPE, CONTROLNO)`，無額外索引、外鍵或 DEFAULT。既有 [Oracle DDL](../../../database/reference/mestest_equipment_state_references_source_ddl.sql)、[PostgreSQL CREATE-only](../../../database/reference/mestest_equipment_state_references_create.sql) 及 [表／metadata 規格](../EQP/設備設定/設備狀態設定.md) 已核實；本項沒有重查或複製 Oracle 結構，也不連 YMES PostgreSQL。
- `TBLEQPSTATEBASIS` 是狀態 lookup 主檔，欄位和結構參照既有 `mestest_equipment_state_create.sql`；來源表間沒有 FK，服務仍須驗證選取狀態存在且保留有效主檔名稱。

## Vue DEV 與家用端 API handoff

- Vue DEV 以 in-memory fixtures 顯示三個分頁、七個固定控制項、狀態搜尋選擇器、未套用提示及 Apply／Confirm／Close；Apply 模擬只寫已修改群組的完整列集，Confirm 模擬成功訊息後返回。狀態代碼、名稱和現有設定皆為示意值；不呼叫正式 API、不用 localStorage、不代表 MES/YMES 寫入。
- 建議正式讀取端點 `GET /api/ems/state-control-settings` 回傳七個 key 的目前狀態，以及可用設備狀態清單；角色與 MES 功能權限需在 server 端驗證。
- 建議批次更新端點 `PUT /api/ems/state-control-settings` 接受 `controlType`、`controlNo`、`equipmentState`、`stateName` 陣列，只允許三種固定 ControlType 和上述七個 ControlNo。先核對 live schema，已存在表不重建；只在確認缺項後新增 forward migration。
- 一個請求涵蓋同一個已修改群組的完整控制項，server 端重新讀狀態主檔／目前設定，校驗七項必要值與名稱一致，再以參數化 upsert 在同一 PostgreSQL transaction 完成群組更新；任何一列失敗全部回滾。Oracle 原批次 Delete+Add 的部分寫入行為不沿用。以 `(CONTROLTYPE, CONTROLNO)` 作唯一鍵，不另造 `EQUIPMENTSTATE` 唯一限制或 FK。
- 寫入完成記錄登入者、請求識別與每個控制鍵的前後值；必要時以交易內鎖定／expected current values 防止兩個維護者互相覆蓋。確認來源表的 `VARCHAR2` BYTE／CHAR 長度語意與 YMES 欄位型別相容。
