# ES107 設備能力項目設定

## 範圍與來源

本功能維護 EMS 設備能力項目主檔 `TBLEMSEQPCAPBASIS`，供產品設備能力項目等功能選用。公司端完成 Vue DEV 假資料頁及家用端 handoff；本頁不呼叫正式 API，也不連 YMES PostgreSQL。

- 清冊：`EMS / EMS設定 / EQP CAP BASIS`，FunctionNo `EQP CAP BASIS`、FunctionKey `ES107`，Form `frmEQPCapBasis`、執行檔 `ES_EQPCapBasis.dll`。
- 主 Form 與 Designer：`D:\iMES\CSiMES\STD\MESWin\EMS\ES_EQPCapBasis\frmEQPCapBasis.vb`（`InitializeComponent` 內嵌）；定義窗及 Designer：同目錄 `frmEQPCapBasisDef.vb`。
- Service：`wsEMS.LoadEMSEQPCapBasis`、`AddEMSEQPCapBasis`、`EditEMSEQPCapBasis`、`DelEMSEQPCapBasis`、`ApproveEMSEQPCapBasis`。
- Core：讀取／新增／實體刪除由 `kcEMS.clsEMSEquipment.ShowEMSEQPCapBasis`、`LoadEMSEQPCapBasis`、`AddEMSEQPCapBasis`、`DelEMSEQPCapBasis`；修改及狀態更新走 `kcBasis_UPD.clsBasis_UPD.EditEMSEQPCapBasis`／`SetEMSEQPCapBasisIssue`。

## WinForms 畫面與操作

- Main Form 初始選取「未凍結」，搜尋欄只有 `CapItem`。載入 Service 時傳未指定的 IssueState，再在本機 DataView 按 0 未凍結、1 簽核中、2 已核准、-1 已停用切換。搜尋條件由共用 `frmBasisTemplat` 送為 SearchFieldName／SearchFieldValue，SQL 條件由共用 Additional XML parser 產生；該 parser 的比較運算子未從本機可讀來源確認，DEV 以不分大小寫的包含式搜尋模擬。
- Grid 隱藏 IssueState、DataStamp 等欄，只顯示 CapItem、Description、Creator、CreateDate、Reviser、ReviseDate；日期格式 `yyyy/MM/dd HH:mm:ss`。工具列提供 Add、Edit、Delete、Copy、Approve、Close，可多選刪除及核准。
- 定義窗只有 CapItem 與 Description。CapItem 必填、TextBox 最多 50 字元，離開欄位時 trim 並轉大寫；Description TextBox 最多 255 字元。Edit 鎖定 CapItem，保留建立資訊，更新 Reviser／ReviseDate 並傳 DataStamp。Add/Copy 建立 IssueState=0；Copy 帶入 Description、需輸入新 CapItem。Apply 儲存後留在定義窗，Confirm 儲存後關閉。
- Add 由 `clsEMSEquipment` 寫 IssueState=0、Creator、CreateDate 和可選 Description；DataStamp 使用表格預設。Edit 由 `clsBasis_UPD` 以 `(CapItem, DataStamp)` 條件更新 Description／Reviser／ReviseDate，並遞增 DataStamp。
- Delete 對 IssueState 0 或 -1 實體刪除；對 2 將資料轉為 -1 並遞增 DataStamp；1 不允許刪除。Service 逐筆處理已選資料，遇錯會中止後續列，先前成功列不會回復。
- Approve 只處理 IssueState=0。Service 查 `EMS_EQP_CAPBASIS` 簽核 Job：沒有 Job 或沒有 Detail 時直接轉 2；否則建立 Issue process、轉為 1，並嘗試通知第一簽核群組。簽核設定與流程必須由正式端 server 決定，不能讓瀏覽器選擇實際路徑。

## 資料表及 DDL 交接

- 直接表為 `TBLEMSEQPCAPBASIS`，PK `CAPITEM`。欄位為 CapItem VARCHAR2(50 BYTE) NOT NULL、Description VARCHAR2(255 BYTE)、IssueState NUMBER(1,0) NOT NULL、Creator VARCHAR2(10 BYTE) NOT NULL、CreateDate DATE NOT NULL、Reviser VARCHAR2(10 BYTE)、ReviseDate DATE、DataStamp NUMBER(11,0) DEFAULT 0 NULL；已知唯一索引是 PK，無資料字典列出的 FK 或 trigger。Form 限制字元數，正式端仍須依 DB 位元組長度檢查多位元字元。
- 本功能重用 2026-11-18 PD102 已保存的 [Oracle logical DDL](../../../database/reference/mestest_prd_eqp_cap_item_source_ddl.sql) 與 [PostgreSQL CREATE-only reference](../../../database/reference/mestest_prd_eqp_cap_item_create.sql)。前次 `DBMS_METADATA.GET_DDL` 對此表回 `ORA-03135`，欄位與鍵依 Oracle data dictionary 還原；本次沒有重新查 Oracle，也沒有新增或猜測 DDL。CREATE-only 檔同時含 `TBLPRDOPCAPITEM`，家用端核對 live schema 後只採用真正缺漏部分。
- `TBLPRDOPCAPITEM` 以 CapItem 作為產品設備能力的 lookup；PD102 的舊 lookup 呼叫沒有指定 IssueState。不得在 ES107 中假定產品端只會選取已核准項目，正式規則要與產品流程共同核定。

## Vue DEV 頁

- fallback 路由 `/YMES/EMS/EquipmentCapabilityBasis`，位於「設備管理 / EMS設定」。DEV 頁包含四種狀態、CapItem 查詢、六欄 Grid、多選、Add/Edit/Copy、Apply/Confirm、Delete 與 Approve 假操作。
- 假資料只存在目前頁面記憶體。DEV 依 IssueState 模擬實體刪除／停用及直接核准／送簽，送簽模式切換只供展示；正式路徑由 server 的 `EMS_EQP_CAPBASIS` 設定決定。未呼叫 API、未寫入資料庫。

## 家用端 API／schema handoff

- 先 Pull 最新 main，再核對 YMES live schema 與 migration history 的 `tblemseqpcapbasis`；此表已有第一階段 CREATE reference，不要重複建表或只因本功能新增 migration。
- 提供登入與 FunctionNo `EQP CAP BASIS` 授權保護的 CapItem 查詢，支援四個 IssueState 及受限搜尋；回傳欄位限上述 Grid 與必要的 IssueState／DataStamp。查詢須參數化、有穩定排序、分頁／筆數上限；舊 Core 把 Additional XML 條件拼入 SQL，不照搬此做法。
- 新增要求 CapItem（trim、upper、Form 50 字元／Oracle 50 BYTE）、Description（Form 255 字元／Oracle 255 BYTE），server 設定 Creator／CreateDate／IssueState=0。修改僅限 IssueState=0，CapItem 不可變，使用 DataStamp compare-and-swap 並遞增。錯誤須區分重複鍵、狀態不允許、資料不存在及版本衝突。搜尋比較方式需由家用端和共用 lookup 使用者共同定義；舊 Form 將字串欄位條件交給共用 parser，不能只從 ES107 證據定為包含式或完全相等。
- Delete 保留舊語意：0/-1 實體刪除、2 轉 -1、1 拒絕；先檢查 `TBLPRDOPCAPITEM` 等引用後再決定正式端是否允許實體刪除，舊 Core 沒有呈現此引用檢查。多選刪除需明確採整批原子或逐筆回報結果，避免部分成功被誤報為全成功。
- Approve 僅接受狀態 0，由 server 查 `EMS_EQP_CAPBASIS` Job/Detail 並決定直接核准或送 Issue process；需保證 Issue 流程資料與主檔狀態更新一致，避免重複簽核及舊 DataStamp 更新。授權、通知及任何 issue data 均由正式端處理；公司端不實作或驗收 API。
