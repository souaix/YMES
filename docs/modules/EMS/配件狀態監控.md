- WinForms Form／內嵌 Designer：`D:\iMES\CSiMES\STD\MESWin\EMS\ES_AccessoryStateMonitor\frmAccessoryStateMonitor.vb`；THEIL 與 DEV_SILVA checkout 的同名 Form SHA-256 與 CSiMES 相同。
- Service：THEIL `Customer\Production\MESws_STD\wsSTD\wsEQP\wsEQP.cs` 的 `LoadAccessoryCategory`、`LoadEQPACCStateBasis`、`LoadAccessoryType`、`LoadAccessoryBasis`、`LoadAccessoryCategoryStateBasis`、`LoadACCStateControlJoinStateBasis`；`wsEMS.cs` 的 `LoadAccessoryStatebyCategory`、`LoadACCViolateStateChange`、`ChangeAccessoryState`。

## WinForms 畫面與互動

- Designer ClientSize 約 1008×591。上方為 Accessory Category、Accessory Type、Total Page／Page 和 Refresh；中間是配件圖片／編號卡片區；下方依分類狀態控制與狀態基礎動態生成狀態操作按鈕。右鍵選單提供配件狀態歷史、設備配件歷史、配件現況；雙擊卡片開啟設備配件現況。
- Form 載入時取 IssueState=2 的配件分類及配件狀態基礎。選分類後讀配件控制設定、分類狀態定義、分類互斥 pair，按 AccessoryState 排序建按鈕；選類型後讀該類型的配件基礎與分類／類型配件狀態，再建立卡片並分頁。
- 每頁 20 張配件卡。選卡片後，同狀態按鈕及互斥設定禁止的目標狀態按鈕會停用。來源 `CountPage` 以 `Count \ 20` 後檢查 `TotalPage * 10 < Count`，在整除 20 的數量會多算頁數；DEV 使用正確的 `ceil(count / 20)`。
- 狀態按鈕先依配件狀態控制設定找操作介面：`Apply`／`Return` 開啟 ES301／ES302，其他已設定控制會開啟 `frmACCStateChangeDescription`；沒有專用介面時才呼叫 `ChangeAccessoryState`。DEV 用描述欄及記憶體更新模擬這些動作，不複製外部 DLL 流程。

## Service／Core 行為

- `wsEMS.LoadAccessoryStatebyCategory` 要求 `AccessoryCategory`，可選 `AccessoryType`，再呼叫 Core。`clsEMSEquipment.LoadAccessoryStateByCategory` 由 `TBLEMSACCESSORYSTATE` 與 `TBLEQPACCSTATEBASIS` 取狀態／顏色，並以 `TBLEQPACCESSORYCATEGORY`、`TBLEQPACCESSORYTYPE`、`TBLEQPACCESSORYBASIS` 限定配件集合。舊式 SQL 以字串拼接分類／類型與 `AdditionalXml`。
- `wsEMS.LoadACCViolateStateChange` 讀取指定分類的 `TBLEMSACCVIOLATESTATUSCHANGE`；Form 依 `(ACCESSORYSTATE, VIOLATIVESTATE)` 停用互斥狀態按鈕。Core `ChangeACCState` 本身未重查互斥 pair，因此正式 API 必須在伺服器端重驗，不能只依賴 UI。
- Form 變更狀態會送 AccessoryNo、目標狀態、分類、登入者、固定描述及目前狀態。Service 將目前狀態轉給 `clsAccState.ChangeACCState`。Core 先呼叫 `CheckACCPrivileged`，再讀取 CurVersion=1 的現況；若 Form 傳入的 `AccessoryCurState` 已不同則拒絕。通過後把舊狀態寫入 `TBLEMSACCESSORYSTATELOG`、更新 `TBLEMSACCESSORYSTATE` 的狀態／StartTime／ACCSerialNo／UserNo／Description，並可寫原因資料。Form 這條直接變更路徑不傳 reasons。
- Form 卡片未攜帶版本；Core 以 `CurVersion=1` 找現況。並發保護依傳入的目前狀態比較，不是版本 token／資料列鎖；現代 API 應使用伺服器端版本與交易鎖。

## 表與 Oracle metadata 狀態

- 本功能查詢及直接狀態轉換使用 `TBLEQPACCESSORYCATEGORY`、`TBLEQPACCESSORYTYPE`、`TBLEQPACCESSORYBASIS`、`TBLEQPACCSTATEBASIS`、`TBLEQPACCCATEGORYSTATEBASIS`、`TBLEQPACCSTATECONTROL`、`TBLEMSACCESSORYSTATE`、`TBLEMSACCESSORYSTATELOG`；狀態權限另讀 `TBLSYSPARAMETER`、`TBLUSRUSERGROUP`、`TBLUSRGroupPriv_Class`；可選原因為 `TBLEMSACCESSORYREASONS`。
- 配件分類／類型／基礎／狀態／現況及歷程多數已有 repository Oracle source DDL 與 PostgreSQL CREATE-only，分置 `mestest_accessory_type_dependencies_*`、`mestest_equipment_type_accessory_catalog_*`、`mestest_accessory_basis_*`、`mestest_accessory_state_*`、`mestest_accessory_category_state_*` references；`TBLSYSSERIALNO` 沿用既有 reference。
- `TBLEMSACCVIOLATESTATUSCHANGE`（本功能讀取）及 `TBLEMSACCESSORYREASONS`（Core 選擇性寫入）在 repository 缺同版 Oracle source DDL／CREATE-only。公司桌機受保護 Oracle profile 不可用，這次沒有執行 MESTEST 查詢；未推測欄位，也未新增 SQL。家用端先比對 live schema／migration，取得核准 DDL 後再補齊互斥表；如果正式 API 接收原因，先核對原因表結構。
- 配件基礎、現況、狀態與歷程 DDL 已在先前模組 handoff；本項不新增 CREATE SQL 或 migration。公司端不連 YMES PostgreSQL、不實作正式 API/schema、不部署。

## 家用端正式 API／schema handoff

- 建議提供授權且參數化的分類／類型 lookup 與分頁監控 GET，`pageSize` 上限 20；由伺服器限制使用者可見資料，不接受任意 `AdditionalXml` 或 SQL 條件。
- 一般狀態轉換 API 應由伺服器鎖定目前 CurVersion 配件狀態、核對 expected current state／版本、使用者分類狀態權限及 `TBLEMSACCVIOLATESTATUSCHANGE`，再以單一交易新增狀態歷程、更新目前狀態並安全配置 ACCSerialNo。將使用者、日期、理由與來源作稽核；原因資料表需先補 DDL 才能納入。
- `Apply`／`Return` 操作導向 ES301／ES302 專用交易，不用通用狀態 API 假裝完成設備掛載／下機；其他控制表指定的外部介面也須由正式 API 明確支援或回報不支援。
- 舊 Core SQL 為字串串接，API 必須參數化；在伺服器端重查互斥、權限、版本及操作類別，並使狀態現況、歷程、原因與流水號具原子性及併發保護。
