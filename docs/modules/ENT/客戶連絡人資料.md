# 客戶連絡人資料（ET102）

## 功能來源

- 第一層：客戶資料（ENT）。
- 第二層：客戶資料設定。
- 第三層：客戶連絡人資料。
- FunctionNo：`CUSTOMER CONTACTOR`；FunctionKey：`ET102`；FunctionName：`客戶連絡人資料`；Form：`frmCustomerContactor`；資料編輯 Form：`frmCustomerContactorDef`；來源目錄：`STD/MESWin/ENT/ET_CustomerContactor`。
- Vue 頁：`web/src/components/CustomerContactorMaster.vue`；路徑：`/YMES/Customer/Contactors`。
- 來源行為追查：Form/Def、`wsENT.Load/Add/Edit/DelCustomerContactor`、`kcENT.clsCustomerBasis`。

## 主畫面

WinForms 主視窗最大化，左上先選客戶編號，旁邊以 `...` 開啟 `LoadCustomerBasis` 查找視窗；搜尋欄位是 CustomerNo。選定後載入該客戶連絡人，依 ContactorName 排序。未選客戶時不載入連絡人，也不能新增或刪除。

UltraGrid 隱藏分組區，顯示資料表欄位（DataStamp 隱藏）：

| Oracle 欄位 | 用途 |
| --- | --- |
| ContactorName | 連絡人姓名／複合主鍵之一 |
| CustomerNo | 客戶編號／複合主鍵之一 |
| TelNo | 電話 |
| FaxNo | 傳真 |
| EMail | Email |
| Title | 職稱 |
| DeptName | 部門 |
| Creator | 建立人 |
| CreateDate | 建立日期 |
| Description | 說明 |
| Reviser | 修改人 |
| ReviseDate | 修改日期 |

操作按鈕依來源順序為新增、修改、刪除、複製、關閉；Print 控制項在 Designer 設為隱藏，沒有可用列印流程。Grid 初始化程式把 Reviser/ReviseDate 的 Caption 設成 `Creator`/`CreateDate`，因此後兩個稽核欄位標題會重複顯示建立人/建立日期；Vue 也保留這個來源畫面行為。新增、修改、複製、刪除均在前端更新完成後重新載入目前客戶資料；Vue 版以狀態更新，不整頁重載。關閉按鈕在 Vue 清除客戶與清單，回到等待選取客戶的狀態。

## 編輯視窗與資料規則

- 固定大小視窗；欄位依序為 CustomerNo（唯讀）、ContactorName、TelNo、FaxNo、Title、DeptName、EMail、Description。CustomerNo 顯示目前所選客戶。
- ContactorName 必填，最多 50 字元；CustomerNo 必填且最多 50 字元。
- Edit 模式將 ContactorName 設為唯讀，因它是複合主鍵的一部分，來源 Edit API 不提供更換主鍵的流程。
- TelNo/FaxNo 最多 25 字元，EMail 最多 50 字元，DeptName 最多 25 字元，Description 使用多行文字；WinForms 沒有替 Description 設定 MaxLength，Oracle 欄位為 255 字元。
- Designer 將 Title 的 MaxLength 設為 50，但 Oracle 欄位為 `VARCHAR2(25)`；保留來源 UI 限制以復刻畫面，輸入超過 DB 長度的值會由資料庫拒絕。API 應回傳可讀的欄位驗證錯誤，不應默默截斷。
- Add/Copy 由目前客戶編號建立新資料；Copy 複製電話、傳真、Email、職稱、部門與說明，清空 ContactorName，並建立新的稽核欄位；不複製 DataStamp。
- Edit 帶原始 DataStamp。舊 `wsENT` 解析並傳遞 DataStamp、Reviser、ReviseDate；目前檢視的 `kcENT.clsCustomerBasis.EditCustomerContactor` 方法宣告未包含這些命名參數，來源檔與服務呼叫存在版本不一致，家用端需在 Modern API 採用明確的伺服器稽核欄位與樂觀鎖定。
- Confirm 儲存後關閉視窗；Apply 儲存後保留視窗開啟。刪除支援多選，WinForms 逐筆刪除並在第一筆錯誤時停止；Vue Production 依此順序逐筆呼叫 API，若中途錯誤重新載入目前清單。
- Vue Development 以具名 DEV 假資料與 `localStorage` 操作；Production 僅呼叫 API，API 未建時顯示待建訊息，不將假資料送入 Production。

## 原公司端 API handoff（歷史）

沿用設備供應商聯絡人的巢狀資源模式：

| Method | Endpoint | 用途 |
| --- | --- | --- |
| GET | `/api/ent/customer-basis` | 客戶查找視窗；保留所有 IssueState，支援 CustomerNo/名稱搜尋 |
| GET | `/api/ent/customer-basis/{customerNo}/contactors` | 依客戶載入連絡人，按 ContactorName 排序 |
| POST | `/api/ent/customer-basis/{customerNo}/contactors` | 新增；伺服器設定 Creator/CreateDate/DataStamp |
| PUT | `/api/ent/customer-basis/{customerNo}/contactors/{contactorName}` | 修改；複合鍵定位，帶 DataStamp，更新 Reviser/ReviseDate |
| DELETE | `/api/ent/customer-basis/{customerNo}/contactors/{contactorName}?dataStamp=` | 刪除單筆；DataStamp 作為 YMES 併發保護 |

API 驗證字數須服從 Oracle DDL（尤其 Title 25）；DataStamp 為 nullable source 欄位，YMES 寫入建議正規化新資料為 0 並在每次修改遞增。來源沒有 FK，刪除客戶主檔的 API/交易需先刪除出貨地址與客戶連絡人，再刪客戶主檔；連絡人 API 只刪指定連絡人。

### Query-key 路由與真實 DTO

API base為 `/api/ent/customer-contactors`，正式環境前綴組合後為 `/YMES/API/api/ent/customer-contactors`。CustomerNo／ContactorName以 `URLSearchParams` query編碼，合法的slash、pipe、星號、百分號均為字面值，不拼入URL path。

| Method | 相對路徑／query | Body／結果 |
| --- | --- | --- |
| GET | `/lookups/customers` | `{items:[{customerNo,customerName,customerSName,issueState}]}`；真實全狀態客戶，含NULL／未知狀態 |
| GET | `?customerNo=` | `{items:[ContactorDto]}`，按姓名排序 |
| GET | `/item?customerNo=&contactorName=` | 單筆真實ContactorDto |
| POST | `?customerNo=` | 新增業務欄位，回200保存DTO |
| PUT | `/item?customerNo=&contactorName=` | 完整業務欄位＋明確nullable `dataStamp`，回200保存DTO |
| DELETE | `/item?customerNo=&contactorName=` | Body `{dataStamp}`，property必須出現但允許NULL；成功204，不解析空response為JSON |

ContactorDto僅十三個來源欄位，物理順序為 `contactorName,customerNo,telNo,faxNo,email,title,deptName,creator,createDate,description,dataStamp,reviser,reviseDate`；來源PK順序仍是 `(CustomerNo,ContactorName)`。僅前兩欄NOT NULL，其餘十一欄均可NULL。正式JSON日期使用 `createDate`／`reviseDate`，不以舊DEV cache的createdAt／revisedAt替代，不造IssueState或parent aggregate token。

Write body為 `contactorName,telNo,faxNo,email,title,deptName,description`，CustomerNo取query context。ContactorName必填50、CustomerNo50；Tel／Fax／Title／Dept25、Email50、Description255。Title採資料庫25字元限制；不截斷、不另造電話／Email格式算法。PUT須送完整業務欄位；明確NULL可清欄，空字串保留空字串，省略optional欄位按full-PUT為NULL，前端不得因此省略未變來源值。

### 寫入、並發與原值保留

- 所有endpoint個別 `[Authorize]`；依專案目前決策仍未導入FunctionNo／角色ACL引擎。新增Creator／修改Reviser取登入principal，最多來源10字元；前端audit／stamp／狀態假值不作為新建來源。新增時間明確 `now() AT TIME ZONE 'UTC'`，回ISO Z，前端轉使用者本地時間；既有nullable audit原樣，沒有COALESCE現在時間／假使用者。
- 每次寫入（含metadata Edit／Delete）都確認唯一真Customer存在，`FOR SHARE`持續至commit，**不限IssueState**，未簽核／簽核中／核准／不使用／NULL／未知狀態均按ET102來源可用。缺parent回422，保留舊連絡人，不自行延伸成孤兒可編輯或刪除策略。不可直接重用OPB03只回state2的lookup。
- CustomerNo及姓名不可換鍵。新增姓名只trim ASCII邊緣空白，不轉大寫；Edit body必須保留原raw姓名。查詢以PG trim／lower識別logical key，但DTO及UPDATE／DELETE使用實際raw CustomerNo／姓名，單筆舊padding／大小寫owner不被改寫成picker canonical。多筆相同logical複合鍵或真Customer別名回409，不能任選、隱藏或接管；這是明載YMES識別完整性延伸。
- UPDATE與DELETE的nullable `dataStamp`皆JSON-required。缺property400，明確NULL合法且與0不同；CAS採 `IS NOT DISTINCT FROM`，NULL成功修改變1。只用Contact原生stamp，不加parent CAS、不bump Customer stamp／audit。numeric(11,0)最大值需遞增時409，匹配最大值的實刪可成功。
- 每次寫入明確ReadCommitted transaction，固定順序為Customer advisory namespace（`YMES:ENT:Customer:`＋PG trim/lower）→真Customer SHARE→Customer＋姓名JSON array/hash namespace→Contact UPDATE row鎖。使用JSON array避免pipe等字面鍵碰撞；真parent／child鎖維持到commit。未來ET101 parent硬刪writer須合作同Customer namespace／parent UPDATE及child-first transaction；本模組沒有交付ET101刪除API，也不宣稱任意直接SQL會受同一協定保護。
- Edit只改六個可編輯聯絡欄與revision／stamp，保留既有Creator／CreateDate、raw owner／姓名與未變NULL。這是依真schema與舊Service／Core參數版本不一致處實作的YMES稽核／CAS修正，不宣稱原方法簽章完全相同。
