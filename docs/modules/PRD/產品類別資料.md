### 資料與 API

- `tblprdtype` 使用 migration `0044_pd101_product_type.sql` 的原生 11 欄；家用端已核對 PK `producttype`、長度、nullable/default 和 `ymes_app` CRUD。0044 由 root 備份並套用；本模組程式沒有補建假表、額外欄位或改寫歷史資料。
- DTO 回傳 `ProductType`、`Description`、`Creator`、`CreateDate`、`IssueState`、`ExPrdtype1`、`ExPrdtype2`、`ProductTypeCode`、`DataStamp`、`Reviser`、`ReviseDate`。可空的說明、代碼、隱藏 EX、稽核日期及版本戳記保留真實 NULL，沒有補成空字串、0 或假日期。
- `GET /api/prd/product-types?search=&issueState=`：狀態選用 `0/1/2/-1`，search 對 ProductType 做不分大小寫的 literal contains。`GET /api/prd/product-types/item?productType=...` 回單筆原 DTO；大小寫/前後空白同 identity 卻有多筆原始鍵時回 409，避免任選一筆。
- `POST /api/prd/product-types`：寫入 ProductType（最多 50，新增 trim + uppercase）、ProductTypeCode（最多 10，可空）、Description（最多 255，可空）；state=0，Creator/CreateDate 由 server 產生，DataStamp 使用來源 default 0。大小寫重複檢查及 INSERT 在同一 ReadCommitted 交易，identifier advisory lock 協作本 API 併發新增。
- `PUT /api/prd/product-types/item?productType=...`：修改時 key 唯讀，僅 state 0 可改代碼/說明；EX、建立者/建立日期原樣保留。body 必須明確提供 `issueState` 及 `dataStamp`，後者允許明確 NULL；省略任一 token 為 400，NULL 與 0 不等同。先鎖原列再比 token，UPDATE 同時用 state/stamp 條件防漏，成功回真實新 DTO。
- `POST /api/prd/product-types/approve?productType=...`：相同 required CAS body，僅 0→2，不強制先設流程。無 Issue/Job 時依本批既定決策直接核准；若發現已存在的四個共用 Job 來源表，回 503 且交易不變更，避免假裝已走完整簽核。
- `DELETE /api/prd/product-types/item?productType=...`：相同 required CAS body。2→-1 回 `{ outcome: 'UNUSED', item }`，0/-1 實體刪除回 `{ outcome: 'DELETED', item }`；1 禁止。硬刪前有產品類別實際引用或共享 -1 設定時回 409，保留原資料。
- 所有寫入用明確 ReadCommitted、server 登入 actor（最多 10）、server 日期；編輯/核准/停用遞增 `COALESCE(DataStamp,0)+1`，超過 numeric(11,0) 的下一次變更回 409。整數 stamp 範圍檢查、row lock、nullable CAS 都在 server 執行。每筆成功的 create/update/approve/delete 亦有 server 操作 log，未記錄密碼或憑證。
- 所有 endpoint 明確 `[Authorize]`。資料庫錯誤回乾淨 ProblemDetails 503；唯一鍵衝突 409，不把 SQL/HTML 錯誤頁送進編輯表單。原已核准類別 lookup `GET /api/products/options/product-types` 仍讀同一張真表，沒有另造類別目錄。

### PD102 類別參照與鎖序

`PrdProductTypeReference` 與既有 `PostgresMasterDataRepository.Products.cs` 在同交易協作。Create、Update 真正更換 Type、CreateProductVersion 都必須讀到唯一且 state=2 的真類別，對類別列 `FOR SHARE` 到 commit；新列使用 master canonical key。Update 若 requested Type trim/不分大小寫 identity 未變，使用 server 的原始 ProductType，包含舊大小寫、空白、空字串或已失效/缺主檔值，允許只維護其他欄位，沒有把無效舊值開放成新候選。

PD102 新 Create 先取得下述 ProductNo/TypeNo 共用 namespace，再依「產品 identity/row → 類別 SHARE」；既有 Update/Version 不取得新編號 namespace，維持原產品 row → 類別 SHARE。PD101 修改/刪除先鎖類別 UPDATE，之後只以普通 SELECT 查 `tblprdproductbasis.producttype` 的所有狀態/版次實際引用，不反向鎖 Product row。ReadCommitted 讓等候 SHARE/UPDATE 後的下一 statement 能看見已提交參照；先提交的新產品會阻止 Type 硬刪，Type 先被刪則等待中的新增/換 Type 必須失敗，不留下新 orphan。停用類別可保留既有產品引用，之後新建/換入會被拒絕。

### 新增編號 namespace 防重

[PD102 來源規格](產品主檔.md) 明確要求 AddProduct 的 ProductNo 不得與產品類別或模組同號。本批在 new Product Create 交易內，以 trim/不分大小寫檢查 `tblprdtype.producttype` 的所有狀態；真 `tblprdmodulebasis` 由 pg_catalog 證實存在才查 `moduleno`，也不限狀態/版次。任一衝突回 409，不寫入產品。module 表缺少時不建立假表；表存在但無讀權則 503，不能假設沒有模組。

PD101 Type Create 也拒絕與 `tblprdproductbasis.productno` 任一狀態/版次同號。這個反向防重是 YMES 為共享 TypeNo/-1 設定所加的保守完整性規則，不冒稱舊 Core 具有完全相同的雙向政策；既有同名資料保留不掃刪。兩個 Create 在所有 identity/row lock 之前，共用 `PrdProductTypeReference.LockCreationNamespace`，鎖值使用 PostgreSQL `lower(btrim(@no))`，持有到交易提交，讓 Type/Product 同時新增同名時只可能一方成功，另一方在等候後看到已提交資料而回 409。Type/Create 大小寫重複也使用此相同 namespace，不再另持舊的 PD101 mutex。

此規則只放在新 Product/Type Create。既有產品 Update（含維護其他欄位、未變類別）及原身份的 Version 不套用新的編號防重，仍依既有 parent/類別核准鎖及 CAS。新 Version 的 Type 仍須已核准。未來正式新增模組的 writer 亦須先參與同一編號 namespace，才能涵蓋跨模組的同時新增；本輪未宣稱未知模組 writer 已接入。

2026-11-19 初次 PPK 唯讀 metadata 核對 `tblprdmodulebasis` 確實存在但 `ymes_app` 缺 SELECT；root 已以 migration `0047` 補 SELECT，正式回歸再次核對通過。Product/Type SELECT 原已具備。模組表讀權與下述六張硬刪 guard 權限分開處理，沒有讀權時 new Product 必須明確 503。本輪沒有授予這七張既存參照表的 INSERT/UPDATE/DELETE，回歸用 postgres 建立自己的來源表 fixture，沒有放寬應用 DML。

來源/現有 PostgreSQL 產品鍵長度為 ProductNo=50、ProductType=50、ProductVersion=5，本批同步校正 `ProductWriteRequest` 這三個 annotation，避免合法 50 碼類別在 PD102 被舊 40 碼限制擋住；新建/換 Type 的必填與核准驗證由 server helper 執行。移除 ProductType model-level Required 是為讓 unchanged legacy 空值可到達上述保留分支，不表示允許新增空類別。

### 實際畫面操作結果

| 操作 | 畫面實測結果 |
| --- | --- |
| 新增與連續 Apply | ADD 首次 Apply 成功後轉 EDIT，類別鍵唯讀；第二次 Apply 更新同一列。另一筆使用 Confirm 新增成功並關閉編輯器。空白必填類別無法送出。 |

| 勾選、篩選與核准 | 兩筆勾選後取消 Approve，資料不變。套用篩選後只處理畫面可見的一筆選取目標。兩筆核准遇 B 的過期版本時，A 已成功、B 回 409 並保留；畫面顯示已完成 1 筆及衝突訊息。重新取得 B 後核准成功；state 2 的 Edit／Approve 禁用。 |
| 停用與實刪 | state 2 的 DEL 取消時保留資料；確認後轉 -1 且保留該列，再對 -1 執行 DEL 才實體刪除。A、B 的刪除結果另以 SQL 核對。 |
