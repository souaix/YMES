## WinForms 入口與畫面

PD102 `btnProgram_Click` 從作用中的產品列帶入 `ProductNo`、`ProductVersion`、`IssueState`，以 modal 開啟 `frmProductProgram`。按鈕入口沒有額外 `IssueState` gate。

- 標題 `Product Program`，ClientSize 684×486，置中顯示。
- 上方 Product No、Product Version 是唯讀欄位。
- `Programs` 群組內為單一可勾選 Grid，沒有新增、修改、刪除、搜尋或版本選擇按鈕。
- 可見欄位：Select checkbox、ProgramNo、ProgramType、Description；其他來源欄位隱藏。
- 底部只有 Confirm、Close；沒有 Apply 或 audit 區。
- Form 載入時呼叫 `LoadProductProgramsDefine`，一次載入 Program Basis 與目前產品版次的 Program 關聯。所有 Program Basis 列均供清單選擇，來源呼叫 `LoadProgram()` 未指定 IssueState 篩選。
- 已指派列依 ProgramNo 對應並勾選。Grid `AllowUpdate=True`；當產品 IssueState 不為 0 時，Confirm 停用，但 Grid checkbox 本身仍可暫時切換，關閉後不保存。

## 確認與資料更新

Confirm 收集目前勾選的 ProgramNo，呼叫 `wsPRD.UpdProductProgram`，Core `clsProgram.UpdProductPrograms` 會先刪除該 ProductNo/ProductVersion 的所有 `TBLPRDPRODUCTPROGRAMS` rows，再插入整份勾選清單，並透過 `ExecuteSQLNoneQuery_UPD` 執行 SQL collection。空清單也會執行刪除，所以代表清除該產品版次的所有 Program 指派。成功提示後關閉視窗；Close/X 不儲存。

Program Basis 候選列由 `TBLPRDPROGRAMBASIS` 提供，沒有在此 Form 過濾 IssueState。產品版次關聯表只有 ProductNo、ProductVersion、ProgramNo 三欄，沒有 audit/DataStamp 欄位。

## Oracle 結構

| Oracle 表 | 欄位與 PK |
| --- | --- |
| `TBLPRDPROGRAMBASIS` | ProgramNo VARCHAR2(50) NOT NULL PK；ProgramType VARCHAR2(10) NULL；IssueState NUMBER(1,0) DEFAULT 0 NOT NULL；Creator VARCHAR2(10) NULL；CreateDate DATE NULL；Description VARCHAR2(255) NULL |
| `TBLPRDPRODUCTPROGRAMS` | ProductNo VARCHAR2(50)、ProductVersion VARCHAR2(5)、ProgramNo VARCHAR2(50) 全部 NOT NULL；複合 PK `(ProductNo, ProductVersion, ProgramNo)` |

兩表各有 PK unique index；沒有 FK、trigger 或額外 index。雖然關聯表的 ProgramNo 對應 Program Basis，Oracle 未建立 FK。

- Oracle source DDL：`database/reference/mestest_prd_program_source_ddl.sql`
- PostgreSQL CREATE-only 對照：`database/reference/mestest_prd_program_create.sql`

`tblprdprogrambasis` 已出現在 YMES first-phase bootstrap SQL。家用端需先比對 live schema 和 migration；不可重建既有主檔，也不可因 CREATE-only reference 直接執行。只有確認關聯表或必要欄位不存在時才新增 forward migration。

## 家用端正式整合（2026-11-19，正式驗收見末節）

### 檔案與共用產品真實來源

- 正式 API：`src/YMes.Api/Products/PrdProgramController.cs`、`PrdProgramModels.cs`、`PrdProgramRepository.cs`；前端沿用 `web/src/components/ProductProgramSetup.vue`，`ProductBasisMaster.vue` 只補 Program 的 API base／儲存通知接線。沒有增加獨立選單或另一份產品主檔。
- 與 RecipeGroup 共用既有產品 repository owner 的 `PostgresMasterDataRepository.ProductContext.cs`：`ReadProductVersionContext(connection,transaction,productNo,version,forUpdate)` 直接讀 `YMES.tblprdproductbasis` 的 ProductNo、ProductVersion、IssueState、DataStamp。這是最小投影，保留實際 NULL 與 decimal DataStamp，不沿用舊 `ProductDto` 將 NULL stamp 壓成 0／int 的映射，也不複製完整產品資料模型。
- 共用 reader 只驗身份／版次長度、存在性與大小寫歧義，回傳資料庫正式儲存鍵，不包含「狀態一定為 0」的政策。查詢用 `FOR SHARE`，異動用 `FOR UPDATE`，鎖保留在呼叫者交易內；Program 自己再以伺服器狀態決定能否儲存，避免影響 RecipeGroup 等允許其他狀態的子功能。存在多個大小寫不同的同鍵時回 409，不任意選第一筆。

### API 契約

全部 endpoint 明確 `[Authorize]`。本階段按使用者已決定方向先做登入後操作，角色／產品版次 ACL 仍待共用權限服務；不假稱已實作完整 PD102 ACL。Actor 只從 principal 取值，所有 SQL 參數化，資料庫例外回一般中文 ProblemDetails，不回 SQL／連線資訊。

| 方法 | 路徑 | 行為 |
| --- | --- | --- |
| GET | `/api/products/options/programs` | 回 `{programNo,programType,description,issueState}[]`，ProgramType／Description 可 NULL；按 ProgramNo 排序，不過濾 Program IssueState，沒有新增或修改 Program 主檔能力 |
| GET | `/api/products/{productNo}/versions/{version}/programs` | 在真實產品版次 `FOR SHARE` 鎖內讀目前指派，回 `{productNo,productVersion,issueState,programNos,version}`，任何產品狀態均可讀 |
| PUT | 同上 | body `{programNos:[...],version:"..."}`，真實產品版次 `FOR UPDATE` 後核對狀態與指派快照；只有 state0 可保存，`[]` 明確清除全部，成功回新的真實指派快照 |

- Program 關聯來源沒有 audit/DataStamp。`version` 為實際產品 context（含 nullable master stamp／狀態）及有序真實關聯列的 SHA-256，不新增資料表欄位，屬 YMES 併發保護擴充。PUT 必須帶載入所得的完整 64 字元版本，缺少／格式錯誤回 400，產品或關聯已變更回 409，不能將 client 提供的 IssueState 當成授權或狀態依據。
- `programNos` 必須明確存在，空值或漏欄位不是清除；空陣列才清除。ProgramNo 最長 50 字元，trim 後大小寫不敏感去重，逐筆驗證主檔存在並取得 `FOR SHARE`，以主檔實際 ProgramNo 保存；不要求核准狀態。找不到回 422，主檔大小寫歧義回 409。單次上限 10,000 個輸入項目。
- 整份舊關聯刪除及新關聯插入在同一交易，任一錯誤回滾，不留下部分取代。所有此子功能寫入都先鎖產品主列，再以固定編號順序鎖 Program 主檔，避免兩個操作者互相覆蓋清單。產品核准／停用的真正主列異動會與此鎖互斥。關聯本身不添加 audit，也不為此任意更動產品 DataStamp；操作帳號與保存筆數記錄於服務 log。

### Vue 操作與失敗處理

- 正式模式同時取得 options 與指定產品版次的 assignments；兩者完整成功後才允許 Confirm，回應失敗不能拿空清單覆蓋真正指派。畫面使用 API 的實際 IssueState 控制保存，NULL 不會當成 0；非 0 狀態依來源仍可暫時勾選，Confirm 停用。
- DEV 假資料限定 `import.meta.env.DEV && developmentPreview`，正式模式不讀 props 裡的 DEMO Program 清單、localStorage 或假狀態代替 API。儲存成功才關窗並顯示產品主頁通知；錯誤顯示 API ProblemDetails 並保留視窗與勾選，409 要關閉後重新開啟載入。
- 現存關聯若引用已不存在的 Program 主檔，畫面明確顯示該真實關聯及缺失原因，讓使用者取消勾選；不悄悄隱藏並刪除。仍勾選不存在的主檔時，後端回 422，不建立假 Program。
- 保存中停用 X／Close；Program overlay 不以點擊外部遮罩直接關閉，避免保存尚在進行時誤以為已放棄。平常 Close／X 不保存，沒有增加來源不存在的 Apply 或額外功能鈕。

### 既有產品版本與刪除協作

- 為已存在的 `CreateProductVersion` 流程提供同交易 helper `PrdProgramRepository.CopyAssignmentsForVersion(connection,transaction,productNo,sourceVersion,targetVersion)`。產品 owner 先鎖來源主列、建立／鎖定目的版次，按固定 RecipeGroup→Program 順序呼叫，再提交同一交易；保留來源真實 Program 關聯，不加入 Program 狀態篩選或虛構欄位。helper 先收集來源關聯，依 ProgramNo 排序取得真實 Program 主檔 `FOR SHARE`，驗證存在性及大小寫歧義，再清理新目的版次關聯並複製來源，目的與來源不得相同。不存在的來源主檔回 422、主檔歧義回 409，整個新版本交易拒絕，不將懸空引用帶入新版；這是 YMES 的明確完整性限制。此是目前已存在的 Version API 整合，不等於一般 Copy／Detail Source／產品類別複製全部完成。
- 若 Program 關聯表實際不存在，代表此可選子模組尚未部署，沒有持久化來源關聯可複製，Version helper 不執行 Program copy；不得把它報成已成功複製 Program。存在性查 `pg_catalog`，不因缺少表級 SELECT 權限而誤認表不存在。表存在但權限／schema／插入失敗時回 503，整個新產品版本交易回滾，不只跳過失敗的子表。
- 為產品 owner 提供 `EnsureNoAssignmentsForProductDelete(...)`，同一真實產品 `FOR UPDATE` 交易內有 Program 關聯即回 409，沒有自行猜測 cascade；狀態 2 軟停用不觸發實體刪除 guard。這是 YMES 防止來源無 FK 形成懸空關聯的明確改善。
- 來源 Program 只允許產品 state0 清除指派，因此已有關聯的 -1 版次仍受刪除保護，不能在本子窗格越權改成可保存；需後續受控的產品生命週期／維護流程處理，不杜撰反核准或非0修改。一般產品 Copy／Detail Source 的原生完整流程尚待核實，本批不宣稱完成。

### Schema／權限部署建議（root live audit 後決定）

1. `tblprdprogrambasis` 已在 first-phase bootstrap；先核對 ProgramNo 等既有 mapping，該表實際應為 ProgramNo varchar(50) PK、ProgramType varchar(10) NULL、IssueState numeric(1,0) DEFAULT0 NOT NULL、Creator varchar(10)、CreateDate timestamp、Description varchar(255)。保留既有資料及 YMES 擴充，不建立第二張主檔。API 不提供 Program 主檔寫入，但驗證／複製使用 `FOR SHARE`，應用角色除 SELECT 外需至少一欄的 UPDATE 權限（例如 ProgramNo），或沿用既有表級 UPDATE；這是 PostgreSQL row-lock 權限需求，不等於新增可修改主檔的 Web 功能。依據：[PostgreSQL SELECT 權限說明](https://www.postgresql.org/docs/17/sql-select.html)。
2. 僅當 live 確認 `tblprdproductprograms` 缺少時，新增 forward migration：ProductNo varchar(50)、ProductVersion varchar(5)、ProgramNo varchar(50) 全部 NOT NULL，PK 三欄，沒有新增 FK、audit、DataStamp 或額外索引。應用角色需要 SELECT／INSERT／DELETE（來源沒有單列 update 需求）；若既有維護原則一律給 CRUD，可由 root 統一決定。
3. 共用產品 context reader 需要既有 `tblprdproductbasis` SELECT 及 row-lock 所需權限（應用角色原本已由產品 owner 授權）。實際 migration 號、schema 差異、備份及部署由 root 處理；本批未建立或執行 migration，沒有接觸 Oracle 業務列。
