# PD206 產品抽樣頻率規則

- `PRD / PRD QCRULE BASIS`，Web `/YMES/PRD/QCFrequencyRules`。來源 `STD/MESWin/PRD/PD_QCRuleBasis/frmPRDQcRuleBasis.vb` 與 `frmPRDQcRuleBasisDef.vb`（含內嵌 Designer）。依產品、設備、作業站維護抽樣頻率，未指定的鍵以 `*` 儲存。修改保持複合鍵與模組唯讀。
- 三種頻率依序為多批抽一批、每天第一批、每班第一批。多批模式要有抽樣批次數；每天要有 A 班時間；每班要有 A、B 班時分。DEV 依庫表兩位數精度檢查 1–99，時分沿用原表單的時 00–24、分 00–59。
- DEV 支援篩選、CRUD、複製與套用。新資料使用 WIP，因 Designer 隱藏 SPC 選項。既有 SPC 資料保留品管項目，複製成 WIP 時清除品管項目。產品候選共用 PD102 核准產品，其餘候選使用固定假資料。正式設備／站點候選、SPC 品管選取和抽樣執行待家用端接續。

### 結構與 live audit

- 家用端以 PPK/plink SSH 在 `BEGIN READ ONLY` 交易查 PostgreSQL catalog，確認此表在所有 schema 均缺少；缺表不寫成 0 筆或已授權。既有 `tblprdproductbasis`、`tbleqpequipmentbasis`、`tblopbasis` 存在，`ymes_app` 均有 SELECT/INSERT/UPDATE/DELETE 及可支援 row-locking SELECT 的 UPDATE 權限，CONNECT／YMES USAGE 為 true。只查 metadata，未查 Oracle 或 PostgreSQL 業務列。
- `database/migrations/0043_prd_qc_frequency_rules.sql` 已由主流程套用；套用前 `/opt/ymes/backups/ymes_before_0043_pd206_20261119.dump` 已以 pg_restore --list驗證。只建立核實的空表、來源PK與ymes_app CRUD；獨立讀回16欄／4個NOT NULL／0個DEFAULT、三欄PK及僅PK index、四CRUD皆true，初始count0。未新增FK、額外index或複製業務資料。API/Web 已隨本批部署，正式 API／DB 實證見後節；GUI 尚未驗收。

### API 與來源行為

檔案為 `src/YMes.Api/Products/PrdQcFrequencyController.cs`、`PrdQcFrequencyModels.cs`、`PrdQcFrequencyRepository.cs`；controller 使用既有 NpgsqlDataSource 直接建立 repository，不需 Program／DI 變更。全端點明確 `[Authorize]`；依目前使用者決策暫不擴 FunctionKey/角色 ACL。

- `*` 是來源已知的真實全部範圍鍵，明確傳入，不是查詢 wildcard 或假查找列。新建參照使用 master 的真實拼字；不分大小寫查找有歧義時拒絕，不選第一筆。所有使用者值參數化；SQL identifier 僅由程式固定 allowlist 組成。
- `qcMethod=0` 要求整數 `qcNum=1..99`；1 要求 A 班，2 要求 A/B 班。時分維持來源表單的 `00–24:00–59` 接受範圍，保存原五字字串，不擅自把 24:xx 改成次日，也不增加班別前後順序或相異限制。
- 保存時非作用欄位清為 NULL：method0 清 A/B，method1 清 count/B，method2 清 count。這與現有 DEV 表單的頻率切換保持一致，是本 Web 全欄位保存契約；不把它描述為已驗證舊 Core sparse update 的全部細節。Description 空白存 NULL、最多255字。Create/Update 回完整真 DTO，既有未參與編輯的模組、SPC 欄與 audit 不以瀏覽器預設覆寫。

### nullable CAS、鎖與稽核

- PUT／DELETE 的 `dataStamp` 使用 JsonRequired：省略400，明確 null 只匹配 DB NULL；不是數字0的別名。數字須為來源11位整數範圍。新增 NULL，更新以 `COALESCE(datastamp,0)+1`，最大值拒絕409並保留資料，不讓 numeric overflow 變成一般503。
- 同組合異動先取 transaction identifier advisory lock，鍵使用 PostgreSQL lower 後的 JSON 三元組，不靠 `|` 等可出現在編號中的分隔符。建立／修改再按產品、設備、作業站的固定順序取得 `FOR SHARE`，核對真實存在／核准產品，最後 `FOR UPDATE` 鎖規則列並比對版本；SQL UPDATE／DELETE 再以 `IS NOT DISTINCT FROM` 精確 CAS。新增的大小寫防重檢查及 PK 同在交易中。
- 產品因來源沒有 ProductVersion，會鎖定同 ProductNo 的實際各版次，至少有一版已核准，不假造特定版。設備與作業站只按已知來源檢查存在。Delete 只取 identifier／目標列鎖，不需要改動或鎖定不存在的父列。任何失敗回滾本筆，沒有批次清空或同步修改其他表。
- 修訂只記登入 principal／server 時間，更新保持 Creator/CreateDate。controller 記錄動作、三鍵、操作者與實際版本；硬刪除的操作紀錄在 API log，沒有來源未定義的 audit history 表。缺表／權限以503明示，版本衝突409、參照不合法422，不回成功假資料或暴露連線秘密。
- 父列共用鎖保證當次提交的資格檢查，不代表永久存在性。依本次已核實來源，父刪除/停用不對 PD206 新增 block/cascade；規則可保留待復用，讀取與自身刪除皆可進行。明確政策及新回歸項目見下節，不再把「未加 parent hook」視為主檔部署 blocker。

### 已核實的父主檔生命週期政策

公司端 `025309d` / `3192964` 已補入上方完整 Form／Service／Core 與 Oracle metadata 證據，先前「PD206 部署前必須補 parent guard/cascade」的待查判斷已由來源釐清，不再作為強制 hook blocker。YMES 本批沿用可讀來源的保留策略：

- PD206 規則只存 ProductNo，沒有 ProductVersion。刪除其中一版、最後已核准版、最後存在版，或將父版次停用/取消核准，都不會因 PD206 新增阻擋，也不連動清除該規則。設備、作業站刪除/停用亦保留對應規則。既有其他模組的刪除防護仍由各 parent owner 處理，本批沒有擴充、移除或繞過它們。
- 這些歷史規則可保留待後續復用，不因暫無父主檔或核准產品版次就認定資料庫損毀。List/Get 直接讀真規則，不以 parent inner join 隱藏；PD206 自身 Delete 按三鍵及 nullable CAS 刪除，無須先復原父主檔。
- 新增/修改仍須在 server 按當次提交驗證真父資格：產品至少一個已核准版次、設備/作業站存在；不合格回 422，保留原規則全文與 stamp。`FOR SHARE` 只維持本次交易的資格檢查，不承諾父主檔永遠存在，也不引入來源沒有的多版永久引用規則。
- 每欄 literal `*` 代表該欄全域範圍，獨立於某個具體父編號的生命週期；不把 `*` 當成需要存在的真 master，也不因一個具體產品/設備/站點刪除就改寫全域規則。
- 原生 WIP 選規則的八組優先順序已有上方來源證據，但本批仍只交付主檔管理；不以保留策略測例宣稱已完成 WIP 班別、計數或實際抽樣執行引擎。

因此不再要求 Products／Equipment／OP 補上 PD206 專屬 namespace、反向引用 block 或 cascade。現有 PD206 程式本來未改這些 parent writer，與此已核實政策一致；政策釐清時只更新文件與受 gate 保護的回歸腳本，沒有改動 parent 刪除交易。本批已透過真 parent API 完成後述生命週期測例，browser 操作仍待驗。
